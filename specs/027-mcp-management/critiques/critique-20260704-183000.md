## Part 2: 新发现的产品风险（Product Lens）

### 🎯 Must-Address（5 项）

#### P2-MA1: Deferred loading 与"配置即可用"承诺的根本张力

spec 核心承诺：FR-009"AI MUST 能自动发现并调用 MCP 工具"、US-001"AI 自动发现并调用"、SC-001"3 次迭代内自动调用"。

但 deferred loading 实际路径：`配置 → McpToolRegistry 注册 → prompt 只含工具数 → AI 必须主动 search_tools(kind="mcp") → get_tool_detail 激活 → 下一轮才能调用`。

**关键缺口**：spec/contracts 没有定义 AI **怎么知道要去搜 MCP 工具**。spec.md L145 反而写"无需专门修改 prompt"——与 deferred loading 必需的 prompt 引导**自相矛盾**。

**建议**：
1. contracts 新增"能力目录 prompt 文案"小节，明确 deferred 模式下的 MCP 触发引导文案
2. spec.md 删除"无需专门修改 prompt"，改为"主助理 prompt MUST 在 deferred 模式下含 MCP 工具计数和触发引导"
3. **强烈推荐**：预置 server（GitHub/filesystem，工具数少）绕过 deferred loading **直接全量注入**（约 6-15k token，可接受）；用户自定义 server 才走 deferred。这同时保住"配置即可用"承诺和控制 token 爆炸

#### P2-MA2: tools.changed 事件触发时机完全未定义

CC-007/FR-008 说"复用 tools.changed 事件域"，但整个 spec/contracts 没定义 MCP 场景下何时触发。前端 MCP tab 列表刷新和 AI 能力目录 stale 判定都依赖此事件。

**建议**：contracts 新增"tools.changed 触发条件"小节，列至少 4 个触发点（首次注册/注销/重连成功/动态变化）。server 状态变更但工具列表未变时走 `backend.resync_required`，不发 tools.changed（语义滥用）。

#### P2-MA3: SC-001 "3 次迭代"在 deferred loading 下需明确达成路径

deferred 下最小路径：search_tools(1) → get_tool_detail(2) → call(3)，刚好 3 次但要求模型首轮主动搜 MCP + 一次命中 + 无重试，实际常 4-6 次。

**建议**：若采纳 P2-MA1 预置 server 全量注入建议，则 SC-001 的 3 次对预置 server 成立；用户自定义 server 放宽到 5 次。spec 明确这条 happy path。

#### P2-MA4: US-001 acceptance 2 在 deferred loading 下不可靠

"未配置时 AI 告知用户可配置 MCP"——配置数为 0 时 prompt 该不该提 MCP？提了会噪声，不提 acceptance 2 不可达成。

**建议**：acceptance 2 改为弱化版本："未配置时 AI 不主动误导；用户主动询问扩展能力时介绍 MCP"。或加规则："MCP 工具数为 0 时 prompt 不含 MCP 提示；配置第一个 server 后 prompt 永久含 MCP 引导"。

#### P2-MA5: 重连成功主动通知没有实现机制

spec Edge Case 写"重连成功后主动通知"，但 contracts 的 reconnect_server() 只返回 server 对象，没定义 emit 事件。

**建议**：lifecycle contract 明确 reconnect 成功后 MUST emit tools.changed（工具重新注册）；spec 细化"前端通过 tools.changed 触发 toast"。

## Part 3: 新发现的工程风险（Engineering Lens）

### 🎯 Must-Address（SDK 兼容性 bug + 集成缺口，10 项）

#### N1: `create_subprocess_exec` 与 `stdio_client` 重复创建子进程

lifecycle contract L69-74 同时调 `create_subprocess_exec` 和 `stdio_client`。**SDK 的 stdio_client 内部自己 spawn 子进程**（从 `StdioServerParameters(command, args, env)`），不接受外部 subprocess。两个调用 = 两个孤立子进程，我们手里的那个没人读写管道。

**建议**：删除 `create_subprocess_exec` 步骤，全部走 `StdioServerParameters`，让 SDK 拥有子进程完整生命周期。

#### N2: Windows 进程清理与 SDK Job Object 机制冲突

contract 声称"复用 ProcessManager._terminate_tree（taskkill /T /F）"。但 SDK 在 Windows 上用 **Job Object**（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`），不暴露 PID 给我们，`stdio_client.__aexit__` 内部调 `TerminateJobObject`。双重终止会竞争。

**建议**：改为"主要依赖 SDK Job Object；stop_server 走 `event.set() → await stack.aclose()`；`_terminate_tree` 仅作 stack.aclose() 失败时的 fallback"。

#### N3: stderr 读取协程路径不可行

contract 声称"stderr=PIPE + 读取协程"。SDK 的 `stdio_client(server, errlog=sys.stderr)` 只接受一个 TextIO 参数转发 stderr，**不暴露 stderr 管道**。

**建议**：传入自定义 TextIO-like 对象给 `stdio_client(errlog=_StderrCapture())`，在 `write()` 内脱敏记日志。不再需要"stderr 读取协程"。

#### N4: "子进程 exit 回调即时检测"承诺落空

contract 声称"注册子进程 exit 回调即时触发 disconnected"。但 SDK 的 `stdio_client.__aexit__` 只在 `event.set()` 让控制流离开 `async with` 块时才执行——进程死了我们感知不到，只能靠 60s ping 兜底。

**建议**：删除"即时检测"承诺，改为"ping 60s + call_tool 失败立即标 disconnected"，即时检测列为 future work。

#### N7: `read_timeout_seconds` 接受 `timedelta` 不是 `int`

contract 写 `read_timeout_seconds=30`。SDK 实际签名是 `read_timeout_seconds: timedelta | None`，**传 int 30 会 raise TypeError**。

**建议**：全部改为 `read_timeout_seconds=timedelta(seconds=30)`，明确 `from datetime import timedelta`。

#### N8: DynamicToolManager 集成面远大于 contracts 描述（E13/X1 落地严重不足）

contracts 说"扩展 deferred loading"，但实际 DynamicToolManager **没有 MCP 注入点**，需 9 处横切改动：
1. `CapabilityKind` 加 `"mcp"`
2. `_KIND_ORDER` 加 `"mcp": 2`
3. `search_capability_catalog` kind 校验加 `"mcp"`
4. `_current_catalog_items()` 注入 McpToolRegistry 数据源
5. `_register_activated_definition` 的 short_id 命名约定（`utool_`/`comp_` vs `mcp__`）
6. `get_tool_detail` parser 不识别 `mcp:` selector
7. `DynamicToolManager.__init__` 缺 `allowed_mcp_server_ids`（绕过授权过滤，违反 Constitution）
8. `MAX_ACTIVATED=10` LRU 与用户技能争用
9. `tool_registry.py` 3 处 `DynamicToolManager(...)` 构造都要传 MCP 注册表

**建议**：二选一——
- **方案 A**：单写 `mcp-deferred-loading-integration.md` 列清 9 处改动
- **方案 B（推荐 MVP）**：MCP 工具走**独立路径** `McpToolRegistry.get_activated_tools()`，在 `tool_factory()` 末尾追加，不碰 DynamicToolManager 的 LRU/激活缓存。结合 P2-MA1 预置 server 全量注入，用户自定义 server 通过 search_tools 发现后也走独立激活

#### N9: McpSessionProtocol 签名与 SDK 不匹配 + 泄漏 SDK 类型

contracts 的 Protocol 定义 `list_tools() -> list[McpToolInfo]`、`call_tool() -> CallToolResult`、`send_ping() -> bool`。SDK 实际返回 `ListToolsResult`/`CallToolResult`/`EmptyResult`——Protocol 不 structural-match ClientSession。更严重：`CallToolResult` 是 SDK 类型，业务层 `from mcp.types import CallToolResult` 会破坏 E7 的 SDK import 隔离。

**建议**：定义业务层自有 `McpCallResult` dataclass（`is_error/text_parts/image_count`，不含 SDK 类型）；Protocol 返回业务类型；McpProcessManager 内部做 SDK↔业务类型适配。

#### N15: stdio_client 内部 anyio task group 异常传播

`stdio_client` 用 `async with anyio.create_task_group()`。任一子任务异常会 cancel 整个 group 并冒泡到我们的 `async with stdio_client(...)` 块。我们的 `await event.wait()` 周围没有 try/except，异常被忽略。

**建议**：contracts 补"stdio_client 异常传播处理"：`await event.wait()` 周围 try/except，异常时 `_mark_disconnected(server_id, exc)`。

#### N17: McpServerConfig 合并 env dict 的缓存泄漏风险

`from_row` 返回的 `McpServerConfig` 实例本身含合并后的 env dict，在实例生命周期内一直存在。被日志/异常/序列化碰到就泄漏——`__repr__` 遮罩不够（N6）。

**建议**：拆成 `McpServerConfigPublic`（不含 env，可缓存可日志）+ `McpLaunchPayload`（含合并 env，只在 spawn 那刻构造，用完丢弃）；McpProcessManager 内部完成转换，不暴露 launch payload 给上层。

### 🔴 SDK 隐式行为未处理（3 项）

| ID | 发现 | 建议 |
|----|------|------|
| N10 | SDK `call_tool` 成功后自动 `_validate_tool_result`，outputSchema 不匹配会 raise RuntimeError（即使执行成功） | contracts 加已知限制：handler 捕获后按 `tool_schema_validation_error` 返回 |
| N16 | `anyio.create_memory_object_stream(0)` 0 缓冲背压：同一 server 并发 call_tool 被 SDK 串行化 | contracts 明确"同 server 串行，跨 server 才能并发" |
