## Part 2: Engineering 新发现（5 个 SDK 兼容性 Must-Address）

### 🎯 RC1: `_StderrCapture` 纯 TextIO 无 fileno，subprocess 拒绝

**SDK 证据**：`stdio_client` L128 把 `errlog` 透传给 `_create_platform_compatible_process`，后者 L176-178/L213 把 `stderr=errlog` 透传给 `subprocess.Popen`。Python subprocess 在 `stderr is not None and not PIPE/DEVNULL` 分支调 `stderr.fileno()`——纯 Python TextIO（无 fileno）会 `AttributeError`，`io.StringIO` raise `UnsupportedOperation`。

**后果**：spawn 阶段直接 TypeError，**server 启不来**。

**建议**：三选一（推荐方案 1）：
1. **MVP 推荐**：`tempfile.TemporaryFile()`（有 fileno）做 errlog，定时 seek+read 提取脱敏记日志
2. `os.pipe()` + `os.fdopen()` write 端，独立任务读 read 端（实时但有 64KB 缓冲区满阻塞风险）
3. 直接传 `sys.stderr`（默认值），靠全局日志重定向兜底

**禁止**：继续用 `_StderrCapture` 纯 TextIO。

### 🎯 RC2: `ClientSession` 没用作 async context manager，initialize() 必然 timeout（最严重）

**SDK 证据**：`mcp/shared/session.py:221-225` 的 `BaseSession.__aenter__` 才启动 task group + `_receive_loop`：
```python
async def __aenter__(self) -> Self:
    self._task_group = anyio.create_task_group()
    await self._task_group.__aenter__()
    self._task_group.start_soon(self._receive_loop)
    return self
```

`__init__` 只创建空 AsyncExitStack，没 task group。不进 `async with`，没人读 read_stream，`send_request()` 在 `response_stream_reader.receive()` 上 hang 到超时。

**后果**：`session.initialize()` 必然 timeout，**MVP 一个 server 都启不来**。

**建议**：lifecycle 用 AsyncExitStack 进 context：
```python
session = await stack.enter_async_context(
    ClientSession(read_stream, write_stream, read_timeout_seconds=timedelta(seconds=30))
)
await session.initialize()
```

### 🎯 RC3: N10 模式 `"validate" in str(exc)` 匹配不到任何 SDK 错误

**SDK 证据**：`mcp/client/session.py:432-441` 的 `_validate_tool_result` 实际抛的 3 条 RuntimeError：
1. `f"Tool {name} has an output schema but did not return structured content"`
2. `f"Invalid structured content returned by tool {name}: {e}"`
3. `f"Invalid schema for tool {name}: {e}"`

**全部不含 "validate"**。模式永远 false，schema 校验失败全被当连接错误 → `McpServerDisconnectedError` → 标 disconnected 重连。**用户看到的语义错**：明明是工具返回结构错，却被告知"server 断开"。

**建议**：改匹配实际消息前缀：
```python
msg = str(exc).lower()
if "structured content" in msg or "invalid schema" in msg or "output schema" in msg:
    raise McpToolSchemaValidationError(tool_name, str(exc))
raise
```

### 🎯 RC4: lifecycle 存 raw ClientSession，FakeMcpSession 无法注入（N9 测试策略失效）

**证据**：`mcp-tool-registration.md` 定义 `McpSessionProtocol` + `_SdkSessionAdapter`，但 `mcp-server-lifecycle.md` 的 `_start_server_coro` 直接 `self._sessions[server_id] = session`（raw ClientSession），`_sessions: dict[str, ClientSession]` 而非 `dict[str, McpSessionProtocol]`。

**后果**：测试无法塞 FakeMcpSession（类型不匹配），**N9/E14 测试策略不可达成**。

**建议（方案 A，符合 N9 原意）**：lifecycle 把存入 `_sessions` 的对象统一换成 `_SdkSessionAdapter(ClientSession(...))`，类型 `dict[str, McpSessionProtocol]`，内部方法用 Protocol 接口。

### 🎯 RC5: `McpLaunchPayload.__post_init__` 的 repr override 不生效（secret 仍泄漏）

**Python 证据**：dunder 方法在 `type(obj)` 上查找，**不在实例上查找**。`object.__setattr__(self, "__repr__", ...)` 只给实例加普通属性，`repr(payload)` 仍走 dataclass class-level `__repr__`，**完整暴露 merged_env 的 secret**。

**建议**：
```python
@dataclass
class McpLaunchPayload:
    command: str
    args: list[str]
    merged_env: dict[str, str] = field(repr=False)  # dataclass repr 不显示
    merged_headers: dict[str, str] = field(default_factory=dict, repr=False)

    def __repr__(self) -> str:  # class-level，repr() 会调用
        return f"McpLaunchPayload(command={self.command!r}, args={self.args!r}, <{len(self.merged_env)} env vars masked>)"
```
加门卫测试 `assert "ghp_xxx" not in repr(payload)`。

## Part 3: Product 新发现（3 个 Must-Address）

### 🎯 P3-MA1: 预置 MCP "全量注入"与 capability_catalog prompt 生成路径未定义（核心）

**矛盾**：contracts L37 声称"保住'配置即可用'承诺——无需先 search_tools"，L339 说"预置全量注入所以不需要 deferred 提示"。但**整个 contracts 没钉死 capability_catalog.py 怎么把预置 MCP 工具放进 AI prompt**。

- 若 prompt 不含预置工具名 → AI 必须先 search_tools → "无需先 search"承诺落空，SC-001 "理想 1 次迭代"不可能
- 若含完整 ToolDefinition → 撞 021 deferred 阈值（20 项）
- contracts L341 prompt 文案是 deferred 专用还是所有模式专用？未明确

**建议**：contracts 新增"capability_catalog prompt 生成"小节：
1. 非 deferred 模式下预置 MCP 工具 MUST 作为完整 ToolDefinition 出现在 prompt（迭代 `McpToolRegistry.get_preset_tools()`）
2. deferred 模式下预置 MCP 工具退化为计数（此时 SC-001 "1 次迭代" 不成立，Known Issues 明示）
3. 自定义 MCP 工具始终只走计数 + search 引导

### 🎯 P3-MA2: dual-track 差异无 UI 反馈，自定义 server 用户会以为"功能坏了"

**问题**：用户添加完 server 后卡片一致，但 AI 行为完全不同：
- 预置 GitHub → 配置完成 AI 立即可用（理想 1 次迭代）
- 自定义 Jira → AI 不知道工具名，必须先 search_tools；用户第一句"列出 Jira ticket"，AI 可能答"我没有 Jira 工具"，用户困惑"我刚加了呀"

**建议**：
1. server 卡片状态徽章：预置"✓ AI 可直接调用"；自定义"AI 通过 search 按需发现"
2. 自定义 server 首次添加成功后 tooltip："工具较多，AI 会在需要时搜索发现。如未触发，可在对话中提到 server 名称"
3. spec User Story 2 增 acceptance：自定义 server 卡片显示 deferred loading 提示

### 🎯 P3-MA3: test-connection 15s < npx 首次下载 30s+（R1 E12 误判关闭）

**矛盾**：SC-006（spec L169）"首次下载可能需 30 秒+"，contracts L170"test-connection 超时 15 秒"。15s < 30s。

**后果**：用户首次添加 GitHub 预置 → 填 token → 测试连接 → 等 15s → **超时失败**。用户以为 token 错或网络坏，反复重试都失败（npx 还在下载）。**GitHub 预置 aha moment 的首次体验障碍**。

**建议**（任选）：
1. test-connection 超时放宽到 60s，UI 显示"首次启动可能需 30s+ 下载"
2. 探测到 npx 下载阶段显示 indeterminate progress，不计时
3. 预置 server 启用流程内置预热步骤
