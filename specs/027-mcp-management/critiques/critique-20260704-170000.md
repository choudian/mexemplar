# Critique Report: MCP Management

**Feature**: 027-mcp-management
**Date**: 2026-07-04
**Reviewers**: Product Lens (CEO/Product Lead) + Engineering Lens (Staff Engineer)

## Executive Summary

spec 和 plan 的技术深度扎实，MCP SDK 集成、异步桥接、凭证安全、高危确认穿透和 output governance 复用都考虑周全。但存在一个结构性偏差：**设计重心偏向"系统能力实现"而非"用户价值交付"**，以及一个核心工程风险：**StdioReadWriter 不存在于 MCP SDK 公开 API**，直接威胁 start_server 核心路径的可行性。

**Verdict**: ⚠️ **PROCEED WITH UPDATES** — Must-address 项可解决，但需在编码前完成 SDK API 验证 spike 和关键 spec/plan 修订。

## Engineering Lens Findings

### 4a. Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | **StdioReadWriter 不存在于 MCP SDK v1.x 公开 API**——ClientSession 期望 anyio MemoryObjectStream，不是裸 subprocess 管道。核心启动路径不可行 | 编码前做 SDK API 验证 spike；改用 `stdio_client` 上下文管理器并在后台线程中 hold 住，或用 anyio 中继流 |
| E2 | 🎯 | `run_coroutine_threadsafe` + `future.result(timeout=30)` 在 AgentLoop worker 线程中可能死锁 | MCP 事件循环线程必须完全自包含只做 I/O；pre_hook 在 handler 前执行不在 MCP 线程中——显式声明此不变式 + 门卫测试验证 |
| E3 | 🎯 | McpToolRegistry._tools 是普通 dict 无线程安全保护——tool_factory() 和注册/注销在不同线程 | `get_all_tools()` 返回 snapshot 浅拷贝；注册/注销用 RLock；handler 容忍 session 已关闭 |
| E4 | 💡 | McpServerConfig.from_row 的 secret key 发现机制不明确 | mcp_servers 表增加 `secret_env_keys_json` / `secret_header_keys_json` 字段 |

### 4b. Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E5 | 🎯 | Windows 上 MCP 子进程僵死——ping 失败只标 disconnected 不终止进程，残留进程占资源 | 复用 ProcessManager._terminate_tree 逻辑（taskkill /T /F）；disconnected 时也终止子进程；补 stderr 读取协程 |
| E6 | 🎯 | 事件循环线程崩溃后无恢复路径——所有 MCP 工具永久超时 | 事件循环线程加全局 try/except + 自动重建；call_tool_sync 检测循环不运行时尝试重建 |
| E7 | 🎯 | MCP SDK import 失败会阻塞 sidecar 启动 | 所有 `from mcp import` 延迟导入；lifespan 中 MCP 启动整体 try/except；SDK 不可用时 CRUD API 仍可工作 |
| E8 | 💡 | 缺少工具调用断路器——持续错误/超时的 server 会耗尽 AgentLoop 迭代 | 每个服务器维护连续失败计数器，超阈值直接返回错误，手动重连重置 |

### 4c. Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E9 | 🎯 | 粘贴导入 secret key 自动检测不可靠——遗漏时凭证存入 env_json 明文 | 后端启发式检测（TOKEN/KEY/SECRET/PASSWORD/CREDENTIAL/AUTH 关键词）；导入 API 返回 detectedSecretKeys 供确认 |
| E10 | 🎯 | McpServerConfig env 合并路径凭证泄漏风险——dataclass 可能被日志/异常包含 | `__repr__` 必须遮罩 env 和 headers；合并后 env dict 只传 create_subprocess_exec 不缓存；门卫测试验证 |
| E11 | 💡 | MCP 工具 prompt injection 风险——恶意 server description 可嵌入指令 | description 长度截断 500 字符 + envelope 标记 source=mcp；Known Issues 记录 |

### 4d. Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E12 | 🎯 | npx 冷启动延迟远超 5s 目标——首次下载可能 30s+ | start_all_enabled 并发启动；test-connection 超时 15s；性能目标改为"已缓存启动 <5s" |
| E13 | 🎯 | MCP 工具全量注入 tool_factory() 的 token 开销——500 个工具 = 100k token | MCP 工具走 deferred loading（通过 search_tools 按需发现），与 CC-002 一致 |

### 4e. Testing Strategy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E14 | 🎯 | MCP SDK 依赖的集成测试如何 mock 未定义 | 定义 McpSessionProtocol（Protocol 类）+ FakeMcpSession；集成测试用真实 filesystem server 标 @pytest.mark.integration |
| E15 | 🎯 | 异步桥接线程安全测试缺失 | 用 threading.Barrier 同步多线程同时提交 coroutine；测试事件循环崩溃恢复 |

### 4f. Operational Readiness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E16 | 🎯 | MCP server stderr 无人读取——管道满后子进程僵死 | 补 stderr 读取协程 + 脱敏后写入日志 |
| E17 | 🎯 | v24 migration 缺 downgrade 逻辑 | 补 DROP TABLE IF EXISTS + 清理 app_settings LIKE 前缀删除 |
| E18 | 💡 | MCP 子系统可观测性不足 | 扩展 agent_tool_health 增加 MCP 计数器 + 状态变更 INFO 日志 |

### 4g. Dependencies & Integration Risks

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E19 | 🎯 | MCP SDK v1.x 与 anyio 版本冲突风险 | 添加依赖前检查 uv lock 解析结果；CI 增加 import mcp 冒烟测试 |
| E20 | 🎯 | ClientSession 长连接稳定性未验证——SDK 主要为短生命周期设计 | 补长连接验证 spike（1 小时持续调用）；考虑 session 定期重建机制 |
| E21 | 🎯 | server name 到工具名前缀映射有歧义——name 含 `__` 导致解析错误 | McpToolRegistry 维护 server_name→set[tool_name] 映射，注销按集合删除不依赖前缀匹配；name 禁止 `__` |
| E22 | 🤔 | call_tool 的 read_transport_timeout_seconds 参数需验证 | SDK spike 验证；不支持则用 asyncio.wait_for 包装 |
| E23 | 💡 | HTTP transport 扩展点应预留但不实现 | API 中 transport=http 返回 422；前端 HTTP 选项灰显 |

## Cross-Lens Insights

两个视角的交汇点——产品简化同时也降低工程风险：

| ID | Lenses | Finding | Suggestion |
|----|--------|---------|------------|
| X1 | Both 🎯 | MCP 工具全量注入既浪费 token（工程）又违背 deferred loading 设计（产品） | MCP 工具走 deferred loading，通过 search_tools(kind="mcp") 按需发现——这是最重要的单一架构修正 |
| X2 | Both 🎯 | StdioReadWriter API 不存在（工程）意味着需要重设计进程管理——这恰好是评估"按需启动 vs 长连接"的时机（产品） | SDK API spike 先行；根据 spike 结果决定是用 stdio_client 长连接还是按需启动 |
| X3 | Both 💡 | 空状态引导（产品）和可观测性（工程）都需要 server 状态通知 | 统一为：server 状态变更 → 日志 + UI 事件（复用 tools.changed 或 backend.resync_required） |
| X4 | Both 💡 | FR-015 全量暴露（产品担心安全，工程担心 token）和启发式确认（工程担心误报/漏报） | 预置 server 配置带读写分类元数据 + deferred loading 减少暴露面 |
