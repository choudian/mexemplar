## Executive Summary

The prior must-address items have been resolved. The spec and plan now consistently define:

- a durable Task graph as the new task truth source;
- TaskAttempt fencing and idempotency recovery;
- Main Assistant as graph coordinator, not user-work executor;
- persisted agent-to-agent question/resource/capability routes while user answers remain process-local;
- default clean-start cutover with optional explicit backfill;
- phase gates for P1/P2 before P3/P4 implementation;
- UI-safe display projections and public event contract sync;
- session archive/delete soft-hide behavior for normal task APIs.

No constitution conflicts were found. The feature is ready for `/speckit.tasks`. Remaining notes are task-generation guardrails, not blockers.

## Product Lens Findings

### 3a. Problem Validation

**P1 — ✅ Problem evidence is now sufficient**

The spec ties the feature to concrete current pain: child progress reconstructed from sessions and `workflow_transitions`, unclear stop/recovery semantics, duplicate-work risk, incomplete failure ownership, and insufficient visibility into dependencies, board claims, meetings, and Todo.

**Suggestion**: No blocking edit required.

### 3b. User Value Assessment

**P2 — ✅ MVP boundary is clear enough for tasks**

P1/P2 form the durable task and adjudication foundation; P3/P4 are explicitly gated. The product value is not reduced by keeping board/meeting/Todo in the feature because the plan prevents them from racing ahead of recovery correctness.

**Suggestion**: During `/speckit.tasks`, preserve phase headings and dependencies exactly: P1 durable graph, P2 adjudication/stop/failure bridge, P3 collaboration paradigms, P4 Todo/UI states.

### 3c. Alternative Approaches

**P3 — ✅ Cutover approach is pragmatic**

The default clean-start guard is appropriate for a single-user unpublished feature branch. Backfill remains available only as an explicit opt-in before schema work, which avoids accidental legacy-state interpretation.

**Suggestion**: Treat backfill as optional/non-MVP unless implementation discovers active legacy delegation data that must be preserved.

### 3d. Edge Cases & User Experience

**P4 — ✅ UX risks are covered at the right level**

The spec now hides internal terms behind display phases, requires progressive task views, and quickstart includes empty/loading/resync/focus/accessibility checks. This is enough for task generation.

**Suggestion**: Ensure generated frontend tasks include both store/API behavior and visual states, not only backend event wiring.

### 3e. Success Measurement

**P5 — ✅ Recovery metric now matches safety design**

`SC-003` now distinguishes safe checkpoint resume from unsafe recovery entering parent adjudication. This resolves the prior contradiction between product promise and idempotency protocol.

**Suggestion**: No blocking edit required.

## Engineering Lens Findings

### 4a. Architecture Soundness

**E1 — ✅ Boundaries align with constitution**

The architecture preserves `UI -> desktop_api -> business -> data`, uses repositories for SQLite state, keeps Tauri out of business logic, and routes public events through the UI Event Registry.

**Suggestion**: No blocking edit required.

### 4b. Failure Mode Analysis

**E2 — ✅ Recovery and ordering rules are implementable**

TaskAttempt leases/fences, operation idempotency records, stop/cancel/replan ordering, late-result rejection, and parent adjudication for unsafe retry are all specified clearly enough for implementation tasks.

**Suggestion**: Generate explicit negative tests for duplicate non-failed operation keys, stale fenced results, cancelled-task late success, and unsafe recovery auto-replay.

### 4c. Security & Privacy Review

**E3 — ✅ Trust boundaries are explicit**

The plan covers sidecar token continuity, DTO/event redaction, no raw provider errors/secrets, no user-answer persistence, meeting message-only boundaries, no implicit capability expansion, and no brain distillation for Todo.

**Suggestion**: Keep privacy tests focused on public projections and session archive/delete soft-hide behavior.

### 4d. Performance & Scalability

**E4 — ✅ Local performance plan is adequate**

The target scale is bounded to <=200 tasks and <=20 active attempts. Snapshot indexes, meeting pagination, claim/question expiry indexes, and fake executor timing tests are specified.

**Suggestion**: During implementation, avoid O(n²) graph rendering or repeated full-layout recomputation on every event.

### 4e. Testing Strategy

**E5 — ✅ Test plan covers the risky paths**

Quickstart now includes migration, repositories, state-machine, dispatch, recovery, idempotency, questions, adjudication, board claims, meetings, Todo, API, events, cutover, failure bridge, guardrails, frontend store/panels, and E2E smoke.

**Suggestion**: Keep state-machine tests table-driven so illegal transitions are easy to audit.

### 4f. Operational Readiness

**E6 — ✅ Desktop-appropriate rollback and release gates are defined**

The plan states local rollback posture, debug-safe counters, and a gate that blocks unified dispatch on duplicate side effects, permanent running tasks, or unsafe recovery replay.

**Suggestion**: No blocking edit required.

### 4g. Dependencies & Integration Risks

**E7 — ✅ Integration sync is called out**

Backend registry, projector, frontend event types, validators, and contract tests must be updated together. The plan also guards against deriving task truth from `workflow_transitions`.

**Suggestion**: Generate one explicit task for backend/frontend event contract sync to avoid splitting that work across unrelated subtasks.

## Cross-Lens Insights

**X1 — ✅ Recovery promise and safety model now agree**

Product trust is expressed as "resume when safe, otherwise explain and adjudicate", not as unsafe automatic replay. That improves both UX honesty and engineering correctness.

**X2 — ✅ Broad scope is controlled by phase gates**

This remains a large feature, but the documented phase gates make it tractable. The main risk has shifted from spec ambiguity to task generation discipline.

**X3 — ✅ Privacy lifecycle is now user-safe enough for implementation**

Task artifacts follow session archive/delete visibility for normal APIs, while physical deletion is not added to task services. This avoids accidental public leakage and preserves audit/debug value.
