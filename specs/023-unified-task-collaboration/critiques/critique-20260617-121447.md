## Executive Summary

The feature is solving a real architectural problem: implicit delegation state is currently reconstructed from session transitions and cannot safely support parallel work, durable recovery, parent adjudication, board claiming, meetings, or private todos. The proposed direction, a durable Task graph with TaskAttempt fences and public snapshot/event contracts, is broadly aligned with the constitution and the existing frontend/backend split.

However, the plan is not ready for task generation without targeted updates. Four issues should be fixed first:

1. The migration/cutover strategy does not yet explain how existing implicit delegation state and `PendingAssistantTask` are handled.
2. The data model does not provide a persisted question/resource-request entity even though `FR-017` requires agent-to-agent question routing to be durable.
3. The attempt model allows `executor_type=assistant`, which is ambiguous against the 100% dispatch boundary.
4. The checkpoint/idempotency protocol is too vague to support the stated "100% no duplicate side effects" acceptance target.

These are resolvable in `plan.md`, `data-model.md`, and the contracts. After those updates, the feature can proceed to `/speckit.tasks` with a much lower risk of generating vague or unsafe implementation tasks.

## Product Lens Findings

### 3a. Problem Validation

**P1 — 💡 Internal pain is clear, external/user evidence is implicit**

The spec clearly describes the system pain: implicit subtask state is scattered across sessions, events, and memory. The user value is plausible because users need observable, resumable multi-step work. What is missing is a compact statement of evidence: which current user-visible failures prove the need, such as lost child progress, unclear stop behavior, duplicate work after restart, or invisible specialist progress.

**Suggestion**: Add a short "Evidence / Current Pain" paragraph to `spec.md` tying the feature to existing failures and user-visible consequences. This makes the feature easier to defend if scope pressure appears later.

### 3b. User Value Assessment

**P2 — 💡 MVP boundary is implied but not enforceable**

The stories are prioritized P1-P4 and plan phases mirror them, but `/speckit.tasks` could still generate one large implementation batch. P3 meetings/board and P4 Todo have real value, but they are not required to validate the core durable Task graph and recovery promise.

**Suggestion**: Add explicit phase gates to `plan.md`: P1+minimum P2 is the MVP, P3/P4 tasks must be grouped after the foundation, and each phase must have independent acceptance tests before moving on.

**P3 — 💡 User-facing complexity needs progressive disclosure**

A task graph, board, meeting drawer, adjudication state, and Todo checklist can easily overload the Assistant screen. The spec requires observability but does not say what is visible by default, what is collapsed, and how internal terms are translated into user language.

**Suggestion**: Add UX guidance: default to a compact current-task progress strip, expandable graph details, hidden board/meeting panels unless active, and user-facing labels that avoid internal state terms like `TaskAttempt`, `fenced`, and `adjudication`.

### 3c. Alternative Approaches

**P4 — 🤔 Stakeholder decision: should board/meeting/todo ship in the same release batch?**

The user explicitly chose one large spec, so this is not a contradiction. Still, for implementation execution, there is a product question: whether P3/P4 must ship with the first usable release or can remain planned but not enabled until P1/P2 pass real smoke tests.

**Suggestion**: Decide before task generation whether `/speckit.tasks` should create all tasks in one list with phase gates, or create only the first shippable slice first.

### 3d. Edge Cases & User Experience

**P5 — 💡 "running while awaiting adjudication" may confuse users**

The data model says a delivered/stuck Task remains `running` with no active attempt while the parent-side adjudication is pending. This preserves the six-state executor model, but the UI must not show it as ordinary execution. Otherwise users will see a task "running" even though it is waiting for review.

**Suggestion**: Add a projected display phase such as `reviewing` / `awaiting parent review` that is derived from a pending adjudication and is distinct from Task status.

### 3e. Success Measurement

**P6 — 💡 Launch/rollback metrics are not defined**

The success criteria include good deterministic test metrics, but there is no operational success signal after release and no rollback threshold.

**Suggestion**: Track rates for fenced attempts, late-result rejections, duplicate-claim attempts, graph resyncs, user stops, run-level failures, and task graphs abandoned after P1. Define rollback triggers such as increased terminal assistant failure rate or repeated graph recovery failures.

## Engineering Lens Findings

### 4a. Architecture Soundness

**E1 — 🎯 Migration and cutover strategy is under-specified**

The constitution requires schema/serialization/migration changes to include a compatibility plan. The spec also requires existing implicit delegation state to migrate as a whole. The plan names v15 tables and says "single user, no double-write", but it does not define whether existing active/suspended subagents are backfilled, ignored behind a clean-start gate, or converted at sidecar startup. It also mentions `PendingAssistantTask` rename without a concrete preservation or migration rule.

**Suggestion**: Add a v15 migration/cutover section that states:

- existing `pending_assistant_tasks` remains for codify/bug queue or is renamed with a compatibility view/repository;
- existing `assistant_delegation_started` transition rows are either backfilled into Task rows or explicitly not migrated with a startup guard that prevents mixed legacy active runs;
- active/suspended child sessions at upgrade are resolved to suspended tasks, failed tasks, or legacy-only debug records;
- no double-write means one cutover commit where UI reads only the new snapshot endpoint.

**E2 — 🎯 Persisted question/resource-request model is missing**

`FR-017` requires agent-to-agent question routing to be persistable while user-facing pending answers remain in memory. The current data model only has `TaskEdgeType=question` and `resource_request`, but no entity that stores question text, route status, timeout, answer summary, or escalation chain. Without that, a restart cannot know which agent question should be re-sent to the user.

**Suggestion**: Add `AssistantTaskQuestion` or `AssistantTaskInteraction` with fields for `question_id`, `task_id`, `parent_task_id`, `kind`, `status`, `question_text`, `safe_answer_ref`, `escalated_to_user`, `created_at`, `resolved_at`, and clear rules that final user pending card/answer is still process memory only.

**E3 — 🎯 `executor_type=assistant` conflicts with the 100% dispatch boundary**

`data-model.md` lists `executor_type` as `assistant`, `ephemeral_subagent`, or `specialist`. The project rule says Assistant tasks must be dispatched to subagents/specialists; main Assistant may handle only pure dialogue/clarification and user-exclusive tools. If `assistant` is an executable attempt type, implementation tasks may accidentally reintroduce direct main-assistant execution.

**Suggestion**: Replace executable `assistant` with a non-executing `coordinator` / `owner` role, or explicitly state that TaskAttempt rows for user work can only use `ephemeral_subagent` or `specialist`; the Assistant owns/root-coordinates the graph but does not run work attempts.

**E4 — 🎯 Checkpoint and idempotency protocol is too vague for the recovery guarantee**

The spec promises 100% no duplicate work after pause/restart, and research chooses checkpoint/idempotency markers. The plan/data model only names `checkpoint_ref` and `result_ref`; it does not define what a checkpoint contains, when it is committed relative to side effects, which tools can provide idempotency keys, or what happens when a side effect cannot be proven idempotent.

**Suggestion**: Add a checkpoint/idempotency protocol:

- every side-effecting task step records an operation key before execution and a completion marker after success;
- non-idempotent operations require high-risk confirmation or parent adjudication before retry;
- recovery can auto-resume only from a checkpoint that proves prior side effects are complete or safe to retry;
- otherwise Task goes to pending adjudication, not automatic execution.

### 4b. Failure Mode Analysis

**E5 — 💡 Async worker/thread model needs concrete ownership**

The plan says async dispatch, parking, re-entry, and capacity=1, but not whether there is one dispatcher thread, a bounded worker pool, per-executor queues, or how SQLAlchemy sessions are scoped per worker. This is a known project risk because shared sessions and mutable caches are explicitly disallowed across threads.

**Suggestion**: Add a concurrency model section: dispatcher owns scheduling, each worker creates its own Repository/session scope, executor leases are DB-backed, activation caches are not shared unsafely, and worker count is bounded by config.

**E6 — 💡 Stop/cancel propagation needs an ordering rule**

The spec mentions graph version fences for cancel/replan, but the plan does not define the exact ordering of stop, cancel, replan, and late completion. This is a common race path.

**Suggestion**: Add a deterministic conflict rule: terminal cancel with graph version N wins over replan <=N; late success on cancelled downstream is ignored; stop is nonterminal and can be superseded only by explicit continue or cancel.

### 4c. Security & Privacy Review

**E7 — 💡 Task content retention and brain interaction are under-defined**

Task descriptions, meeting messages, Todo text, and adjudication summaries may contain sensitive user data. The contracts require redacted projections, but persistent retention, soft delete, archive behavior, and whether task data can be distilled into brain memory are not fully specified.

**Suggestion**: Add privacy rules: task collaboration tables follow assistant message retention; public DTO/event projections are sanitized; Todo is never brain-distilled; meeting/task contents are not injected into memory unless referenced through ordinary assistant messages; delete/archive behavior is soft or tied to session archive.

### 4d. Performance & Scalability

**E8 — 💡 Snapshot query/index plan is incomplete**

The target is 200 nodes in <=500ms, but the model does not list all indexes needed for graph snapshots, board listing, meeting transcript pagination, pending adjudication lookup, and attempt recovery. Contracts also do not paginate meeting messages.

**Suggestion**: Add indexes for `(graph_id, status)`, `(graph_id, parent_task_id)`, `(graph_id, task_version)`, `(task_id, status)` on attempts/adjudications/claims, `(lease_expires_at, status)`, and `(channel_id, sequence)`. Add pagination to meeting messages if transcripts can grow.

### 4e. Testing Strategy

**E9 — 💡 Tests are broad but need a state-machine model test**

The quickstart names many tests, but the highest-risk surface is the state machine. Unit examples alone may miss illegal transition combinations.

**Suggestion**: Add a table-driven state-machine test covering all allowed/forbidden Task, Attempt, Claim, Adjudication, Stop, Cancel, and Recovery transitions. If property-based testing is not desired, use exhaustive table cases.

### 4f. Operational Readiness

**E10 — 💡 Observability and rollback are not yet concrete**

The plan mentions public events and tests, but not structured logs/metrics for recovery, claim contention, meeting timeout, or task graph failure. Migration rollback is also not discussed.

**Suggestion**: Add observability counters and debug-safe logs for `task_created`, `attempt_started`, `attempt_fenced`, `late_result_rejected`, `claim_conflict`, `adjudication_decided`, `graph_stopped`, and `graph_cancelled`. State that rollback is local single-user restore/backup rather than down-migration, or define a down-migration policy.

### 4g. Dependencies & Integration Risks

**E11 — 💡 Compatibility with existing Assistant failure recovery needs a precise bridge**

The spec says task-level failures are graph-local and only top-level irrecoverable failure becomes run-level failure, but the plan does not define when `AssistantFailureService` is invoked, how partial success is summarized, or how failure cards are removed/migrated when graph retry succeeds.

**Suggestion**: Add a bridge rule: only root graph terminal `failed` creates `assistant_run_failures`; partial task failures stay in graph/adjudication; successful replan/continue resolves the graph-local failure and must not create duplicate assistant failure cards.

## Cross-Lens Insights

**X1 — 🎯 Scope × Risk: lack of explicit phase gates can turn a good architecture into an unreviewable implementation batch**

Product wants visible, resumable work. Engineering needs to rewrite core delegation and recovery. Both goals improve if P1 plus minimum P2 is an explicit MVP, with P3/P4 gated behind foundation acceptance.

**Suggestion**: In `plan.md`, require `/speckit.tasks` to group tasks by phase and mark P3/P4 as dependent on P1/P2 verification. This does not remove them from the feature; it prevents parallel implementation from outrunning the new state model.

**X2 — 💡 User clarity × State correctness: "running but awaiting adjudication" needs a display phase**

Keeping Task status to six states is technically sound, but user-facing UI needs a richer projection. Product and engineering both benefit from derived display phases that do not pollute the state machine.

**Suggestion**: Add projection fields such as `displayPhase` and `requiresReview` in snapshot contracts, derived from adjudication/Todo/attempt state.

**X3 — 💡 Recovery confidence × User trust: checkpoint limits should be visible when auto-resume is unsafe**

If the system cannot prove idempotency, it should not auto-run. Product messaging should say "需要确认后继续" rather than silently retrying or showing a generic failure.

**Suggestion**: Add user-facing safe explanation categories for suspended tasks: waiting for user answer, waiting for system recovery, stopped by user, and needs review because safe resume cannot be proven.
