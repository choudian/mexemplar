## Product Lens Findings

### 3a. Problem Validation

**P1 — ✅ Current pain evidence is now explicit**

The spec now explains concrete user-visible problems: progress reconstructed from child sessions and `workflow_transitions`, unclear pause/stop semantics, duplicate-work risk, and incomplete failure ownership. This is enough evidence for an internal product/architecture feature.

**Suggestion**: No further blocking edit required.

### 3b. User Value Assessment

**P2 — 💡 MVP value is gated, but task generation should preserve the gates**

The plan now defines P1/P2 MVP gates and postpones P3/P4 until the foundation passes. This is strong. The residual risk is operational: `/speckit.tasks` may still flatten all phases into one long list unless tasks are explicitly grouped by phase and dependency.

**Suggestion**: In `tasks.md` generation, require phase headings and dependencies: P1 durable graph first, P2 adjudication/stop/failure bridge second, P3 collaboration paradigms third, P4 Todo/UI polish last.

### 3c. Alternative Approaches

**P3 — 🤔 Clean-start vs backfill still needs an implementation-time choice**

The plan allows either clean-start guard or backfill. That is acceptable design flexibility, but tasks will be sharper if one default path is selected before schema work. Given this is a single-user unpublished feature branch, clean-start guard is simpler and lower risk unless there is known active legacy delegation data worth preserving.

**Suggestion**: Choose a default cutover path before implementation tasks, preferably clean-start guard for MVP unless stakeholder explicitly wants backfill.

### 3d. Edge Cases & User Experience

**P4 — 💡 Accessibility and empty/loading states are not called out**

The spec now covers progressive disclosure and internal terminology hiding. It still does not state expected keyboard/accessibility behavior or empty/loading/error states for graph, board, meeting, and Todo panels. These are user-facing screens, and missing states often turn good backend work into confusing UI.

**Suggestion**: Add a small UX requirement or task note for accessible controls, keyboard focus after stop/continue/adjudication actions, empty board/meeting states, and loading/resync states.

### 3e. Success Measurement

**P5 — 🎯 Recovery success metric overpromises automatic resume**

`SC-003` says paused/resumed tasks are "100%" resumed from checkpoint with no duplicate work or lost steps. The plan and data model now correctly say recovery may only auto-resume when the checkpoint proves safety; unknown or unsafe side effects must go to parent adjudication. The success criterion currently reads as if every pause/restart must resume automatically, which contradicts the safety design.

**Suggestion**: Rewrite `SC-003` to distinguish safe resume from unsafe recovery. Suggested edit:

> For tasks with a usable checkpoint/idempotency marker, 100% resume from the checkpoint without duplicate side effects or lost steps. For tasks whose prior side effects cannot be proven safe to retry, 100% enter parent adjudication with a safe explanation instead of automatic replay. In injected crash/restart tests, 0 tasks remain permanently `running`.

## Engineering Lens Findings

### 4a. Architecture Soundness

**E1 — ✅ Core architecture now matches project boundaries**

The dedicated `business/task_collaboration` layer, Repository-owned SQLite state, desktop API adapter role, and UI event registry path all align with the constitution. The Main Assistant coordinator boundary is now explicit.

**Suggestion**: No blocking edit required.

**E2 — 💡 Derived DTO fields are listed inside the entity model**

`AssistantTask.display_phase` is marked as "DTO-only projection, not persisted" but appears in the `AssistantTask` entity table. This is understandable, but it can lead implementation tasks to accidentally add a persisted column.

**Suggestion**: Move `display_phase` into a separate "Snapshot DTO Projections" section or add a stronger note: "not a DB/ORM column".

### 4b. Failure Mode Analysis

**E3 — 💡 Board lease expiry scan needs an index**

The model indexes `assistant_task_claims(task_id, status)` but board lease recovery also needs efficient scans for expired claimed tasks. Without `(status, lease_expires_at)`, lease cleanup can become full-table-ish as local history grows.

**Suggestion**: Add `assistant_task_claims(status, lease_expires_at)` to index requirements. Consider `assistant_task_questions(status, expires_at)` for expired question cleanup as well.

### 4c. Security & Privacy Review

**E4 — 💡 Retention/archive behavior remains an either/or**

The plan says session archive/delete behavior must either soft-hide task collaboration rows or document that they remain debug/audit-local data. That avoids an immediate contradiction, but privacy-sensitive task text, meeting messages, and Todo text should have a concrete behavior before implementation.

**Suggestion**: Pick one policy in `plan.md`: task collaboration rows follow assistant session archive/delete soft-hide semantics unless an existing session retention path owns stricter cleanup. If physical delete is intentionally avoided, document why and keep it out of service methods.

### 4d. Performance & Scalability

**E5 — 💡 Snapshot pagination is defined for meetings but not for very large graph views**

The plan targets <=200 tasks and <=500ms snapshots, which is reasonable for local desktop. The graph endpoint returns all tasks/edges/adjudications. That is acceptable at the stated scale, but the UI should avoid rendering everything expanded by default.

**Suggestion**: Keep full graph snapshot for <=200 nodes, but add a task note that React renders collapsed/progressive views and avoids O(n^2) layout work on every event.

### 4e. Testing Strategy

**E6 — 💡 Operation idempotency needs negative tests around partial unique constraints**

The data model requires `(task_id, operation_key)` unique for non-failed operations. SQLite can enforce this with a partial unique index, but the plan does not call out the exact test cases.

**Suggestion**: Add tests for duplicate non-failed operation keys being rejected, failed operation keys being safely superseded only when allowed, and stale fenced results being rejected without success UI events.

### 4f. Operational Readiness

**E7 — 💡 Observability counters are named but thresholds remain qualitative**

`SC-009` says rollback is triggered if root graph failure or recovery failure rises "significantly". For a desktop app, exact alerting thresholds may be overkill, but tasks should still define at least local audit criteria.

**Suggestion**: Add a local release check: compare before/after controlled smoke runs; any nonzero duplicate side effect, permanent running task, or unsafe recovery auto-replay blocks enabling unified dispatch by default.

### 4g. Dependencies & Integration Risks

**E8 — 💡 Frontend event contract sync should be explicit**

The current code has both backend registry (`src/desktop_api/ui_events.py`) and frontend typed event definitions (`frontend/src/api/uiEvents.ts`). The plan names public UI events but does not explicitly state that frontend event contract/type fixtures must be updated with backend registry changes.

**Suggestion**: Add an implementation task or plan note to update backend registry, frontend event type definitions, validators, and contract tests together for `assistant.task_graph.changed`, `assistant.task_board.changed`, `assistant.meeting.changed`, and `assistant.todo.changed`.

## Cross-Lens Insights

**X1 — 🎯 User trust × Recovery safety: "resume everything" conflicts with "do not repeat unsafe side effects"**

Product wants users to trust that work resumes. Engineering correctly refuses to replay unsafe work. The right product promise is not "always resume"; it is "resume when safe, otherwise pause with a clear reason and no duplicate side effects."

**Suggestion**: Update `SC-003` and the P1 acceptance wording to make this distinction visible.

**X2 — 💡 Scope × Delivery: P3/P4 remain valuable but should not compete with recovery correctness**

Meetings, board claiming, and Todo improve the full experience, but the durable task graph and recovery semantics are the trust foundation. Both product and engineering benefit if P3/P4 are gated by P1/P2 tests.

**Suggestion**: Preserve phase grouping in generated tasks and avoid starting P3/P4 implementation until P1/P2 gate tests pass.

**X3 — 💡 Privacy × UX: retained task artifacts need a user-understandable lifecycle**

The system will persist task descriptions, meeting messages, adjudication summaries, and Todo text. Users do not need to see database retention rules, but they need predictable behavior when sessions are archived/deleted.

**Suggestion**: Choose and document whether task collaboration artifacts follow session archive/delete visibility, then align UI resync and API 404 behavior with that policy.
