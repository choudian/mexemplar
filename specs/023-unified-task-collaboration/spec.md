# Feature Specification: 统一任务模型 + 多范式协作

**Feature Branch**: `023-unified-task-collaboration`
**Created**: 2026-06-17
**Status**: Completed
**Input**: User description: "统一任务模型 + 多范式协作：把隐式子任务/委派收口成显式一等 Task（子六态+父侧裁定）+ TaskAttempt 运行时 + 委派执行异步化，并在其上提供委派/会议/认领三种可临场切换的协作范式；含看板认领、容量=1、急停顺图传、Todo 私人清单。"

> 设计依据(主仓工作文档,gitignored):`docs/local/todo/unified-task-collaboration-design.md`。本 spec 是其用户向收口;实现层契约(异步执行、状态机映射、表结构、各协议)在 plan 阶段落实。

> 当前痛点证据:现有子任务可见性依赖子会话、`workflow_transitions` 和前端运行态重建,用户在崩溃/暂停/续跑后难以判断哪些步骤已完成;停止语义混在"可续暂停"里,与终态取消没有稳定边界;子任务失败、重试和部分成功容易被折叠成会话级失败;子任务卡片无法表达依赖、父侧裁定、看板认领、会议通道或私人 Todo。这些都会直接表现为进度不可解释、重复执行风险和失败归属不清。

## Clarifications

### Session 2026-06-17

- Q: 应用崩溃/重启后，对崩溃时仍在运行、且没有终态结果回流的 `TaskAttempt`，默认恢复策略应是什么？ → A: 围栏旧 attempt，将 Task 置为“挂起：等系统恢复”；只能从持久化检查点/幂等标记续跑，缺检查点则交父侧裁定
- Q: 子任务交回“待裁定”后，父侧裁定默认由谁执行？ → A: 派活方 agent 默认自动裁定；用户只处理顶层失败、高危确认、澄清上冒或主动介入
- Q: 两个执行者进入会议直连后，默认的死锁/失控防护应采用哪种产品规则？ → A: 会议有轮次/时长预算，必须产出结论；超限或互等则关闭通道并回父侧裁定
- Q: 执行者向上提问最终到用户，但用户待答因超时、取消、停止或应用重启而失效时，对原任务应如何落状态？ → A: 自动挂起为“等回话”，等待用户下次打开后继续回答；用户待答/答案仍不持久化，重启后重新发起澄清
- Q: 用户点击“停止”时，默认作用范围应是什么？ → A: 当前用户请求派生的整个任务图，包括该请求下多个顶层任务及其所有下游

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多步任务可观测、可恢复地完成 (Priority: P1)

用户给办公助理一个复杂多步请求(如"整理本月报销并发邮件给财务")。助理把它拆成一张带依赖的任务结构,派给多个执行者并行推进;用户**实时看见每个子任务的进度**;中途暂停(系统限流/用户喊停)后能**从断点续跑**,已花的工作不白费。

**Why this priority**: 这是整套设计的地基——把现在"散在子会话+事件+内存态、无实体兜底"的隐式子任务,收口成显式、可观测、可恢复的一等任务。没有它,下面的协调、范式、私人清单都无处依附。

**Independent Test**: 给助理一个需要 3+ 步、跨 2+ 执行者的请求;确认 UI 显示任务结构与逐项进度;在执行中触发一次暂停,再恢复,确认从断点继续且无重复执行、无丢步。

**Acceptance Scenarios**:

1. **Given** 一个复杂请求, **When** 助理拆解并派活, **Then** 用户能看到一张任务结构(节点 + 依赖)及每个节点的实时状态。
2. **Given** 多个互不依赖的子任务, **When** 它们被派给不同执行者, **Then** 它们**真并行**推进(总耗时短于逐个串行)。
3. **Given** 某子任务因系统限流暂停且具备可用检查点/幂等标记, **When** 系统恢复, **Then** 它从断点自动续跑,不从头重来;若无法证明安全重试, **Then** 进入父侧裁定而非自动重放。
4. **Given** 一次运行过程中应用崩溃重启, **When** 重启完成, **Then** 没有"永久卡在运行中"的僵任务,在跑的任务被恢复为可续或交由裁定,不重复产生副作用。

### User Story 2 - 干完/卡住都交裁定,失败有交代,随时可叫停 (Priority: P2)

执行者把活做到头(做好了或卡死了)都**交回派活的人裁定**,而不是自己宣布成败。裁定方三选一:**认可**(完成)/**打回**(返工)/**放弃**(失败)。放弃沿链向上冒泡,最终由助理告诉用户"这步没办成"。用户随时可**喊停**:全体在安全点暂停、**留工可续**,而不是作废。

**Why this priority**: 让多步执行**可控、可问责**——成果有人验收、失败有交代、用户始终能干预,且干预不毁掉已有进展。

**Independent Test**: 让一个子任务交付后被裁定方"打回",确认它回到执行并带上返工指示;让另一个被"放弃",确认失败逐级上传、最终用户收到"没办成"的说明;执行中点"停止",确认全体暂停且可"继续"。

**Acceptance Scenarios**:

1. **Given** 一个子任务已交付, **When** 裁定方认可, **Then** 该任务标记完成;**When** 打回, **Then** 回到执行并带返工指示;**When** 放弃, **Then** 标记失败、级联取消其下游子任务，并沿链向上冒泡——裁定方即派活方，放弃时已知晓，若该失败导致上级任务也无法完成则继续向上传播，直到根任务失败时桥接为 run 级失败。
2. **Given** 一条委派链上某层彻底放弃, **When** 失败向上冒泡到顶, **Then** 用户收到一条安全的"没办成"说明(不泄露原始诊断/密钥)。
3. **Given** 任务正在执行, **When** 用户点"停止", **Then** 全体在"说完当前这轮"后暂停、产出保留、可"继续";**When** 用户点"继续", **Then** 从暂停处恢复。
4. **Given** 某条方向被放弃, **When** 级联取消其下游, **Then** 下游停止且不被后续重规划复活。

### User Story 3 - 协调者临场切换协作范式(委派 / 会议 / 认领) (Priority: P3)

助理(或任意派活方)按情况**临场切换**协作方式,而不是固定一种:默认**点名委派**;当来回传话太多时**拉个会**——临时给两个专员开一条受监督直连通道让他们直接谈、谈拢回报;当就绪任务多过现成专员或缺对口专员时,把任务**丢看板**让有空的人认领,缺人就起临时工兜底。

**Why this priority**: 让复杂协作更顺(并行、专员间直连、按需认领),但它依赖 P1/P2 的任务地基与裁定闭环才能成立。

**Independent Test**: 构造一个需要两专员反复对齐的子任务,确认助理能开一条直连通道、两人谈拢后回报;构造就绪任务多于专员的情形,确认任务进看板、被认领且不会被两人重复认领。

**Acceptance Scenarios**:

1. **Given** 两个专员就一处反复传话, **When** 上级"拉个会"开直连通道, **Then** 两人可直接交流、达成共识后回报上级,上级可随时查看但不必在场。
2. **Given** 多个就绪任务且可用执行者有限, **When** 任务进看板, **Then** 有空的合适执行者认领之,且同一任务**不会被并发双认领或重复执行**。
3. **Given** 某就绪任务无对口专员, **When** 无人认领到达兜底, **Then** 系统起临时执行者顶上(若该类缺口反复出现,沉淀成固定专员)。
4. **Given** 会议直连通道, **When** 一方在其中行动, **Then** 其能力**不被放大**(不能借对方工具、不扩授权),通道只传消息。

---

### User Story 4 - 执行者私人清单(Todo)防遗忘 (Priority: P4)

执行者(尤其专员)把自己**单个被派任务**拆成步骤,记在一份**私人 checklist** 上自己一条条做,防止长任务丢步骤;该清单进度也能展示给用户。它**不是**对外委派、不进任务图、不需裁定——纯自用追踪。

**Why this priority**: 提升单个长任务的可靠性与可见性,是独立的体验增量(承接历史"模型自管理任务列表"设想),可在地基稳定后再做。

**Independent Test**: 让一个专员处理一个内部多步的任务,确认它能维护一份私人清单并逐项勾掉,且该清单与任务图/裁定流程互不混淆(不同的展示、不同的状态词)。

**Acceptance Scenarios**:

1. **Given** 专员领到一个多步任务, **When** 它列出私人清单并推进, **Then** 清单逐项更新且对用户可见。
2. **Given** 私人清单存在, **When** 会话因压缩/重启中断后恢复, **Then** 清单仍在(持久化),不随对话丢失。
3. **Given** 同时存在任务图与私人清单, **When** 用户查看, **Then** 两者展示清晰可分(不共用状态命名与渲染),不会被误认为同一种东西。

### Edge Cases

- **跨专员并行下的崩溃**:运行中应用重启,在跑的任务(及其运行时占用)如何恢复,不留永久"运行中"僵任务、不重复副作用。
- **同步子树崩溃**:专员与其临时子代理是同线程同步执行,这条子树崩溃时如何释放专员占用、恢复状态。
- **取消 × 重规划竞态**:取消正在沿任务图传播时,上级重规划给图加了新下游,新下游不能漏掉取消。
- **一条用户消息派生多个顶层任务、部分成功部分失败**:run 级失败如何归属(不能把部分失败误判成整体失败,也不能漏报)。
- **执行者向上提问无人能答**:问题逐层上冒到顶,最终需用户回答;超时/取消/停止/重启导致待答失效时,原任务挂起为"等回话",但用户待答/答案不持久化,重启后重新发起澄清;全程 fail-closed,不猜答案继续副作用。
- **会议死锁**:两专员在直连通道里互相等待对方回答 → 需防"等待环"。
- **资源/权限被拒**:缺密钥、用户拒绝、越权操作被挡,落为明确的"放弃"输入而非静默卡住。
- **暂停态的混淆**:同一"暂停"可能因"等回话/等系统恢复/用户停"三种原因,唤醒方式不同,不能一刀切自动续。

## Requirements *(mandatory)*

### Functional Requirements

**任务模型与执行(地基)**

- **FR-001**: 系统 MUST 把一次复杂请求拆解为一张**显式任务结构**(节点 + 依赖关系,支持串行/并行),并把每个"子任务/委派"表示为一个**显式的一等任务实体**,而非散落于子会话、事件流与内存态。
- **FR-002**: 每个任务实体 MUST 具备明确的生命周期状态:待派、进行中、挂起、完成、失败、取消(共六种执行者侧状态);"等待裁定"MUST 作为**派活方侧**的待裁定项管理,而非执行者自身的状态值。
- **FR-003**: 系统 MUST 支持**跨执行者真并行**:互不依赖的任务可同时推进;**单个执行者一次只执行一件**任务(容量=1),需要更多并行时通过增加执行者实现。
- **FR-004**: 派活方派出任务后 MUST 能**非阻塞地继续等待**:在所等结果尚未回流前不擅自继续对话或轮询,由结果回流事件唤醒重入。
- **FR-005**: 系统 MUST 记录每次任务运行的**运行时执行**,并在应用崩溃/重启后恢复:重启时围栏崩溃前仍运行且无终态结果的旧 `TaskAttempt`,将对应 Task 置为"挂起:等系统恢复";只能从持久化检查点/幂等标记续跑,缺检查点则交父侧裁定;不留"永久运行中"的僵任务;迟到的结果被幂等拒绝,不污染状态、不重复副作用。
- **FR-006**: 用户 MUST 能**实时观察**每个任务/子任务的进度。

**裁定、失败与停止/取消**

- **FR-007**: 执行者干完或卡住 MUST 都把结果**交回派活方裁定**,不自行宣布成败;父侧裁定默认由派活方 agent 自动执行,用户只在顶层失败、高危确认、澄清上冒或主动介入时参与;裁定方 MUST 能三选一:**认可**(→完成)、**打回**(→返工,可带指示)、**放弃**(→失败)。
- **FR-008**: 失败 MUST 分两级:**任务级**(被其父放弃,局部终态,沿链向上冒泡)与 **run 级**(冒到顶仍无法挽回);run 级失败 MUST 只暴露**安全投影**(不泄露原始 provider 错误、密钥、堆栈)。
- **FR-009**: 系统 MUST 区分**可恢复**(限流/网络/超时等)与**不可恢复**(认证/请求非法等)情形:可恢复进挂起;不可恢复不挂起也不自判死,作为"卡住"交回裁定。
- **FR-010**: 用户点"停止" MUST 作用于当前用户请求派生的整个任务图(包括该请求下多个顶层任务及其所有下游),使范围内全体在**安全点**(说完当前这轮)暂停、**保留已产出、可续**(挂起,而非作废);用户点"继续" MUST 从暂停处恢复。
- **FR-011**: "停止/继续"信号 MUST 顺当前请求的任务结构覆盖到所有相关运行中的任务(含跨执行者并行的),不得误停其他会话或其他用户请求派生的无关任务;取消(放弃某方向的级联停)MUST 自上而下传播,**是终态、不返工、不复活**已取消的下游;已产出保留。
- **FR-012**: 挂起 MUST 带"原因"(等回话 / 等系统恢复 / 用户停),并据原因决定唤醒方式:等系统恢复可自动续(billing/quota 类默认需用户显式继续或受预算/TTL 约束);用户停须用户显式继续;等回话由回话事件唤醒。

**协作范式(协调者临场切换)**

- **FR-013**: 派活方 MUST 能**点名委派**(把任务定向给某执行者)或把任务**放上看板**开放认领;两者统一为同一机制(任务带"给谁"——填了即定向,空着即开放)。
- **FR-014**: 看板认领 MUST 是**原子**的:同一开放任务不被并发双认领、不重复执行;认领后不干 MUST 能按租约超时释放;支持避开此前回绝者;完成幂等。
- **FR-015**: 无人认领时 MUST 有兜底:起临时执行者顶上;某类缺口反复出现时沉淀成固定专员。
- **FR-016**: 上级 MUST 能为两个执行者临时开一条**受监督直连通道**("拉个会"):两人直接交流、达成共识后回报;会议 MUST 有轮次/时长预算并产出结论;超限或互等时关闭通道并回父侧裁定;上级不必在场但**可随时查看**;通道**仅传消息**——MUST NOT 借对方工具、扩大被授权能力或绕过授权边界;通道内容遵循与正常路径相同的脱敏与归属校验。
- **FR-017**: 执行者 MUST 能在执行前/中**向派活方提问**对齐目标;提问 MUST 顺链逐层上冒,最终一跳到用户时复用既有面向用户的澄清机制;agent↔agent 的提问/路由可持久化,**面向用户的待答与答案不得持久化**(进程内、fail-closed)。若用户待答因超时、取消、停止或应用重启失效,原任务 MUST 挂起为"等回话";用户下次可交互时 MUST 重新发起澄清,不得猜答案、不得复用失效答案继续副作用。
- **FR-018**: 固定专员默认只用其预定义授权;**缺工具时 MUST 向上级请求**,由上级从其能力超集授予(限于其本任务授权子集)或拒绝(拒绝即一次"放弃"输入)。**MUST NOT** 通过会议或 spawn 隐式扩权。
- **FR-019**: 专员 MUST 能起**至多一个**临时子代理(仅为隔离上下文),该临时子代理**不得再向下派或找平级**;此能力为专员专用,普通被委派者不得获得(防深度封顶失效)。

**Todo 私人清单**

- **FR-020**: 执行者 MUST 能维护一份**私人 checklist**(Todo),把单个被派任务拆成自做的步骤;Todo **不委派、不裁定、不进任务结构**,纯自用追踪。
- **FR-021**: Todo MUST 持久化(会话级),不进大脑/记忆沉淀;其展示与任务实体**不共用状态命名与渲染**,以免混淆。

**横切**

- **FR-022**: 面向前端的任务/看板/通道事件 MUST 经既有公开事件契约注册、按 allowlist 投影并脱敏(任务描述等可能含敏感内容);前端缺口恢复 MUST 能拉取权威全图快照。
- **FR-023**: 防无限/循环委派 MUST 成立:非会议态下当前拓扑(枢纽单层 + 一级延伸)结构上不可能成调用环;会议直连引入的**等待环** MUST 通过轮次/时长预算、结论要求与超限回父侧裁定来防死锁。
- **FR-024**: 本特性的新配置项(会议预算、看板容量、招募阈值、全图预算[即 `assistant_tasks.graph.max_tasks`]等)MUST 统一走统一配置入口,不得散落。
- **FR-025**: UI MUST 使用面向用户的派生展示阶段(如执行中/等待检查/已暂停/需要确认/已完成),不得直接展示 `TaskAttempt`、`fenced`、`adjudication` 等内部术语;任务图、看板、会议和 Todo MUST 渐进展示,默认只突出当前请求的关键进度与可行动项。
- **FR-026**: 任务描述、会议消息、Todo 和裁定摘要 MUST 只通过脱敏投影进入 DTO/UI event;Todo 不得进入大脑/记忆沉淀,会议/任务内容不得绕过普通 assistant 消息引用路径直接注入长期记忆。

### Key Entities *(include if feature involves data)*

- **Task(任务)**:持久的工作项/编排节点。被委派、可有归属(owner/给谁)、处于六态之一、参与依赖结构、要被裁定。是"任务=子任务=委派"的统一一等公民。
- **TaskAttempt(运行时执行)**:一个 Task 的一次实际运行(运行中的执行循环/进程),带心跳/租约、检查点/幂等标记,用于崩溃恢复与迟到结果围栏。与 Task 是"持久工作项 vs 易朽执行"的关系;重启恢复不得盲目从头重跑,缺少可续检查点时交父侧裁定。
- **裁定项(父侧)**:派活方持有的"待我裁定"队列项;不是 Task 的状态值。承载认可/打回/放弃。
- **看板/认领**:就绪且未指派任务的开放队列;认领带归属/尝试/版本/租约语义。
- **调用链/任务图**:谁派了谁的有向结构 + 依赖边;带类型的边(依赖/委派/提问/会议通道/资源请求,各自取消传播与权限语义不同);带图级版本用于取消与重规划的竞态围栏。
- **Todo(私人清单)**:执行者自管的 checklist 条目;持久化、会话级、与 Task 完全分离。

### Constraints & Compatibility *(include when relevant)*

- **CC-001**: MUST 沿用现状拓扑(枢纽单层 + 一级延伸),不引入"无限递归/谁都能直连";唯一拓扑增量是专员起一个临时子代理。
- **CC-002**: MUST 保留并复用既有安全协议:高危确认 fail-closed、面向用户澄清仅进程内、子进程/越权 fail-closed、密钥不入日志/明文 DTO/前端持久化。
- **CC-003**: 现状"用户停=可恢复暂停"(既有可恢复语义)MUST 映射为本模型的"挂起";本模型新增的"取消(终态作废)"是**不同语义**,MUST 与之显式区分(不得复用同名概念造成"终态却能续"的矛盾)。
- **CC-004**: 任务级失败与现状"会话级终止失败持久化(单会话至多一个未解决失败)"MUST 对账分层:任务级失败在图内消化,只有冒到顶仍无法挽回才升级为 run 级。
- **CC-005**: 现状对"委派起点"的隐式状态(由委派流转事件 + 子会话状态现场重建,服务于子任务列表、记忆封存防误封、续跑归属校验、调试分类)MUST 在切换到显式任务实体时**整体迁移**;按"单用户未发布、不双写"一次性切换并补链路冒烟 + 门卫测试。
- **CC-006**: 跨执行者并行 MUST NOT 破坏既有并发安全约束:共享数据会话、可变激活缓存、计数写入、进程状态在证明并加固线程安全前不得并发共享。
- **CC-007**: 100% 调度边界 MUST 保留:任务必须派给子代理/专员,主助理只直接处理纯对话/澄清;面向用户的独占工具仍仅主助理可用。PM/Programmer/Trial 是工具集而非调度池成员,其工具失败走工具结果、不进任务状态机。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对一个需 ≥3 步、跨 ≥2 执行者的请求,用户在执行全程都能看到结构化的任务进度(节点 + 状态),无需等到结束。
- **SC-002**: 互不依赖的子任务并行执行,使该类多任务请求的总完成时间相对"逐个串行"**明显缩短**(可用一组基准请求量化对比)。
- **SC-003**: 对具备可用检查点/幂等标记的暂停/崩溃恢复任务,**100%** 从断点继续、无重复副作用、无丢步;对无法证明安全重试的任务,**100%** 进入父侧裁定并给出安全说明,不得自动重放;在注入式崩溃/重启测试中,**0** 个任务停留在"永久运行中"。
- **SC-004**: 用户点"停止"后,当前用户请求派生的整个任务图在"当前这轮结束"内进入暂停且产出保留,不影响其他会话或其他用户请求;随后"继续"可恢复——在测试场景中成功率 100%。
- **SC-005**: 同一开放看板任务在并发认领压力下**0 次**双认领/重复执行。
- **SC-006**: run 级失败对用户仅呈现安全说明;在审计中**0 次**原始 provider 错误/密钥/堆栈泄露。
- **SC-007**: 任务(Task/TaskAttempt)、裁定项、Todo 三者在 UI 与数据上**始终可区分**(独立状态词/渲染/表),评审与门卫测试确认无混用。
- **SC-008**: 既有安全与边界回归全绿:高危确认 fail-closed、面向用户澄清不落库、100% 调度、并发安全门卫、深度取消(改为顺图传后)契约测试通过。
- **SC-009**: 受控发布期间必须能观测并审计 TaskAttempt 围栏、迟到结果拒绝、看板认领冲突、任务图 resync、用户停止、根图失败升级等计数;若根图失败率或恢复失败率相对基线显著上升,必须能通过本地回滚/关闭新路径恢复旧会话安全显示。

## Assumptions

- 单用户、未发布、无外部消费者:数据层切换可"一次性、不双写",不预留 deprecation/双发兼容。
- 现有 Agent 会话生命周期、blinker 事件中心、公开 UI 事件契约、统一配置、高危确认与面向用户澄清机制保持可用并被复用。
- "整个统一任务模型一个大 spec"(用户拍板):范式三招、看板、会议、Todo 全部纳入本特性;实现可按用户故事优先级(P1→P4)分阶段交付,P1(显式任务 + 异步执行地基)为其余一切的前置。
- 范式不做"选择器"字段,但协作边/通道/运行时的**类型**仍持久化(typed edge/channel/attempt),因其取消传播、死锁判定、权限边界各不相同。
- 容量=1(单专员串行,真并行只在专员之间)为既定前提;主助理同时派几个专员是可调配置数字,不影响架构。
