## Phase 0: Research

No NEEDS CLARIFICATION items. Key technical decisions:

### Decision 1: 边界检测算法

**Decision**: 从保留区开头向后扫描收集 tool_call_id，再从压缩区末尾向前找对应的 assistant(tool_calls) 消息，将其连同压缩区内剩余的 tool results 一起移入保留区。

**Rationale**: 保留区的 tool result 是孤立问题的根源，以它们为锚点反向查找最精确。

**Algorithm**:
```
1. 收集 keep_msgs 中所有 tool role 消息的 tool_call_id → keep_tc_ids
2. 如果 keep_tc_ids 为空，无需调整
3. 从 compress_msgs 末尾向前遍历 assistant(tool_calls) 消息：
   a. 解析该 assistant 消息中的所有 tool_call id
   b. 如果任一 id 在 keep_tc_ids 中 → 记录该 assistant 消息索引为 boundary_idx
   c. 立即停止扫描；该 assistant 之后的整个后缀就是要保留的边界 tool 组
4. 如果未找到 boundary_idx，返回原始 compress_msgs / keep_msgs
5. 将 compress_msgs[boundary_idx:] 整体移入 keep_msgs 前部
6. compress_msgs = compress_msgs[:boundary_idx]
```

### Decision 2: 孤立 tool result 检测位置

**Decision**: 在 `assemble_context` 中 reference_handler 替换之前（压缩后、引用替换前）执行校验。

**Rationale**: 压缩是孤立产生的唯一来源。压缩后立即检查是最早的检测点。放在引用替换前是因为引用替换会改变消息内容结构，增加检测复杂度；同时该清理只移除孤立 tool result，不修改 assistant(tool_calls)，因此不改变 `get_pending_tool_calls` 的语义。

## Phase 1: Design

### Data Model

无新增实体。使用现有 Message 模型的 `role`、`tool_calls`、`tool_call_id` 字段。

### Interface Changes

**`_split_messages` 签名不变**，内部逻辑增加边界调整步骤：
- 返回值仍为 `(system_msg, compress_msgs, keep_msgs)`
- `compress_msgs` 可能比原来少几条（被移入 `keep_msgs` 的边界 tool 组）

**`assemble_context` 签名不变**，在压缩后增加校验步骤：
- 加载消息后、引用替换前，扫描并剔除孤立 tool result
- 记录 warning 日志
- reference_handler 仍基于清理后的原始 Message 列表执行替换；`get_pending_tool_calls` 语义保持不变
