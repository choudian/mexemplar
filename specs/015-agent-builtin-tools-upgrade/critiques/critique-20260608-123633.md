## Executive Summary

The feature solves a real and recurring Agent reliability problem: foundational tools currently have inconsistent output contracts, weak pagination, incomplete safety boundaries, and limited recovery for long-running workflows. The spec is directionally strong, and the plan correctly keeps the work inside the Agent/business/execution/data layers rather than leaking tool execution state into UI or desktop API.

However, the plan is not ready for `/speckit-tasks` without updates. Three issues should be resolved first:

1. New configuration is promised but not enumerated with keys, defaults, docs/templates, or fixed-constant exceptions, which conflicts with the constitution's unified configuration rule.
2. Persistent raw-output references may store sensitive raw output across restarts, but the plan does not yet define a concrete threat model, retention/cleanup implementation, storage boundary, or authorization model.
3. The file baseline contract is internally ambiguous: the user story says existing-file writes/edits succeed only after a matching baseline, while requirements and contracts make baselines optional.

**Verdict**: ⚠️ **PROCEED WITH UPDATES**. Resolve the must-address items, then generate tasks.

## Product Lens Findings

### 3a. Problem Validation

**P1 - 💡 Evidence should be made explicit**

The pain point is plausible and well described for engineering Agent workflows, but the spec does not cite concrete evidence: failed sessions, oversized tool results, stale edits, or high-risk confirmation incidents. Without evidence, the MVP order may be driven by architectural preference rather than observed user pain.

Suggestion: Add a short "Evidence / observed failures" section to `spec.md` with 3-5 concrete failure modes, such as stale overwrite, unreadable large files, unpaired tool result after compression fallback, or long-running test process duplication.

### 3b. User Value Assessment

**P2 - 💡 MVP boundaries need to be explicit**

The feature spans safe reads, mutations, search, patching, terminal execution, process lifecycle, persistent artifacts, and compaction. The spec priorities imply ordering, and the plan lists an implementation strategy, but there is no explicit minimum shippable slice with acceptance gates.

Suggestion: Add an MVP section: "Slice 1 = envelope + workspace policy + paginated/redacted read + baseline-required existing-file mutation + AgentLoop pairing tests." Treat search, process lifecycle, and persistent output references as later slices unless they are required to pass the first slice.

**P3 - 💡 Agent onboarding is underspecified**

The spec says tool descriptions must explain bounded reads, baselines, processes, and output references, but there is no acceptance criterion proving Agents can actually continue correctly from `nextPageToken`, stale-baseline errors, or `load_tool_output` references.

Suggestion: Add acceptance tests where an Agent receives a stale-baseline result and rereads before retrying, receives a truncated file window and requests the next window, and receives an output reference then loads the bounded raw window.

### 3c. Alternative Approaches

**P4 - 💡 Search implementation should state when custom traversal is enough**

Research rejects ad hoc shell parsing and leaves future `rg --json` as possible, but large repositories can make pure Python traversal slow. Product value is "find relevant files quickly"; users do not care whether the implementation is native or `rg`-backed.

Suggestion: Add a plan note that the contract is stable but implementation may use native traversal or `rg --json` behind the adapter, with a benchmark threshold for switching.

### 3d. Edge Cases & User Experience

**P5 - 🤔 Outside-workspace read confirmation UX needs a product decision**

The spec allows outside-workspace reads after high-risk confirmation and says UI changes are out of scope. Existing confirmation UI may technically display a generic summary, but the product decision is still important: should Agents be encouraged to inspect files outside the workspace, or should this be an exceptional escape hatch with stronger wording?

Suggestion: Decide whether outside-workspace reads are "allowed after confirmation" or "discouraged exceptional access." Encode the wording in the confirmation summary and tool description.

### 3e. Success Measurement

**P6 - 💡 Success criteria are test-measurable but not launch-measurable**

SC-001 through SC-009 are good deterministic acceptance criteria, but they do not define post-launch health: reduction in stale write rejections, tool result size distribution, artifact cleanup success, process leaks, or confirmation denial rates.

Suggestion: Add runtime health metrics to the plan: count of compacted outputs, raw reference creation/load failures, stale mutation rejections, process records left open at shutdown, confirmation fail-closed count, and cleanup failures.

## Engineering Lens Findings

### 4a. Architecture Soundness

**E1 - 🎯 Config surface is not specified enough to satisfy the constitution**

The constitution requires all runtime configuration through `get_unified_config()` / `UnifiedConfigManager`, and new config must sync defaults, templates, UI exposure decisions, and docs. The plan says new thresholds, retention limits, workspace policy, and output caps will use unified config, but it does not list exact config keys, defaults, fixed constants, or required `config.example.json` / docs updates.

Suggestion: Add a `Configuration Contract` table to `plan.md` with each key, default, validation, owner, whether Settings UI exposes it, and docs/template update target. For any non-configurable fixed constant, explicitly mark it as fixed and explain why.

**E2 - 💡 AgentLoop save boundary needs concrete coverage points**

The plan correctly chooses a save-time governance boundary instead of post-hooks, but current `AgentLoop` has multiple save paths: normal batch result, `_save_error`, solo interrupt, invalid mixed batches, unknown tools, skipped tools, and handler exceptions. If governance is inserted in only one path, FR-022 can regress.

Suggestion: Add a small design note naming the exact wrapper, for example `ctx.save_tool_result_governed(...)` or `AgentLoop._persist_tool_result(...)`, and list every existing save site that must route through it or be explicitly exempt.

### 4b. Failure Mode Analysis

**E3 - 💡 Process lifecycle failure modes are underdesigned**

The spec covers process states, but the plan does not yet define how stdout/stderr are pumped without deadlock, how log ring buffers are bounded, how Windows process trees are terminated, how stdin is enabled/disabled, how duplicate starts are detected, or how records are cleaned on sidecar shutdown.

Suggestion: Add a `ProcessManager Failure Modes` section to `plan.md` covering stream pumps, bounded buffers, process-tree termination, duplicate key strategy, timeout behavior, shutdown cleanup, and tests for each state transition.

**E4 - 💡 Artifact write failure fallback is stated but not operationalized**

The spec says artifact writes or compression failures must still produce one paired result, but the plan does not define the fallback order. For example, if raw blob write succeeds but SQLite metadata insert fails, or metadata insert succeeds but blob write fails, cleanup and result semantics are unclear.

Suggestion: Define artifact creation as an atomic-ish two-phase operation with cleanup: write temp blob, fsync/close, insert metadata, rename/finalize, and on any failure return compact visible fallback with `compaction_failed_fallback` warning and no dangling active reference.

### 4c. Security & Privacy Review

**E5 - 🎯 Persistent raw-output threat model is missing**

This feature intentionally persists raw command output, media metadata, and potentially sensitive local content across sidecar restarts. The spec prevents raw output from entering ordinary Agent-visible text, but the plan does not define storage directory, file permissions, retention defaults, cleanup trigger, authorization rules for `load_tool_output`, whether raw artifacts are encrypted, or how local paths/secrets are prevented from leaking in metadata.

Suggestion: Add a `Raw Output Artifact Security Model` to `plan.md` and `data-model.md`: storage root under app data, private permissions best effort, metadata fields safe for ordinary text, retention defaults and cleanup schedule, authorized loaders, expired/deleted behavior, and tests proving no storage path or raw secret appears in envelopes/logs.

**E6 - 💡 The JSON schema cannot enforce the no-raw-output rule**

`tool-result-envelope.schema.json` intentionally leaves `payload` as an arbitrary object. That makes it useful as a top-level envelope schema, but insufficient as a safety contract for each tool's payload.

Suggestion: Keep the common schema, but add per-tool payload validators or schema fragments for `read_file`, `exec`, `process_logs`, and `load_tool_output`, plus tests that attempt to place base64/media/raw large output into visible payloads.

### 4d. Performance & Scalability

**E7 - 💡 Search and file reads need hard traversal and memory caps**

The plan says bounded pages should avoid unbounded content, but it does not specify max files scanned, max bytes decoded per file, max total search time, cancellation points, or behavior when a repository is huge.

Suggestion: Add config or fixed constants for max search files, max scanned bytes per file, max total matches per page, max elapsed time, and skipped-file metadata. Include tests with large fixture trees.

### 4e. Testing Strategy

**E8 - 💡 Test matrix should include schema and prompt migration failures**

The test plan covers many deterministic behaviors, but it does not explicitly test that new tool schemas/descriptions are the only mounted versions for migrated tools, or that the prompt/tool descriptions teach continuation correctly.

Suggestion: Add guard tests for `BUILTIN_GENERAL_TOOLS` schemas matching the contract and integration tests where an Agent follows `nextPageToken`, `baseline_stale.nextAction`, and `load_tool_output`.

### 4f. Operational Readiness

**E9 - 💡 Migration, cleanup, and rollback readiness are incomplete**

The plan says "next SQLite schema migration" but not the schema version, indexes, cleanup job, idempotency, or rollback behavior. Since artifacts are file-backed, database cleanup must also handle missing blobs and orphaned blobs.

Suggestion: Add migration details: new table/indexes, schema version, repository cleanup APIs, orphan cleanup behavior, and a rollback note. If reversible migrations are not supported by the project, state the forward-only recovery procedure.

### 4g. Dependencies & Integration Risks

**E10 - 🤔 Authorized workspace source is not pinned to a concrete runtime interface**

The data model includes `workspace_root`, but existing `ToolCallContext` only carries tool name, args, session id, agent type, and iteration. The plan assumes the authorized workspace defaults to current Agent workspace root, but does not specify where that root is stored, how subagents/specialists inherit it, or how tests override it.

Suggestion: Decide and document the workspace source: AgentConfig field, run context, unified config, or explicit tool runtime context. Then add tests for assistant, ephemeral subagent, and specialist calls.

## Cross-Lens Insights

**X1 - 🎯 Baseline policy conflict undermines the core safety promise**

Product story 2 says existing-file writes/edits succeed only after a matching baseline, while FR-008 says baseline validation is optional and the `write_file` contract makes `expectedBaselineId` optional. This ambiguity can lead to a shipped implementation that still overwrites files without the Agent having inspected them.

Suggestion: Define baseline policy precisely:
- Creating a new file may omit baseline.
- Replacing an existing file, editing a file, deleting a file, and updating/deleting through patch require a current baseline by default.
- Any force mode, if allowed, must be explicit, high-risk confirmed, and tested.

**X2 - 💡 A smaller MVP reduces both product and engineering risk**

The highest user value and lowest architectural uncertainty are in envelope + permission + safe read + stale mutation protection. Process lifecycle and persistent raw artifacts add substantial security and operational surface.

Suggestion: Add phase gates. Do not let `/speckit-tasks` produce one undifferentiated task list for all tool families; tasks should be grouped by independently shippable slices with contract and guard tests per slice.

**X3 - 💡 Confirmation wording is both UX and security-critical**

Outside-workspace reads, elevated commands, and force mutations all rely on confirmation summaries. If summaries are too vague, users cannot make informed decisions; if too detailed, they leak sensitive content.

Suggestion: Add confirmation summary examples and tests for write, edit, exec, outside-workspace read, and any force mutation mode.
