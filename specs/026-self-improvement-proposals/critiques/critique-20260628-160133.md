# Critique Report: 自我改进提案（B 阶段）

**Date**: 2026-06-28 16:01
**Artifacts**: spec.md · plan.md · research.md · data-model.md · contracts/
**Lenses**: Product（产品负责人）+ Engineering（Staff 工程师）

## Executive Summary

这是一个**方向清晰、安全意识到位**的设计：A 只读不动、停在 B、git 为安全网、source-only 爆炸半径、合并手动——这些都对。脑暴阶段已把最大的风险（命门）核实掉，并把 MVP 收口到"手动合并"，这是成熟的范围判断。

但它本质是「**让系统改自己的代码**」，属于全行业都谨慎的地带。本次 critique 找到 **2 个 Must-Address**（都在工程侧、都可在不重写 spec 的前提下解决）和若干 Recommendation。核心担忧集中在三处：①隔离的地基（执行体 workspace 重定向）尚未验证就被整个安全模型依赖；②"只改源码"的爆炸半径定义漏了 `exec` 这条更宽的能力、且没防"改造自我改进系统自身"的递归砖化；③提案噪声跨复盘累积会导致审批疲劳。

**Verdict: ⚠️ PROCEED WITH UPDATES** —— 解决 2 个 Must-Address（建议落成 plan 调整 + tasks 排序），即可进 `/speckit-tasks`。

## Product Lens Findings

### 3a. Problem Validation
- 问题与需求由用户本人驱动，证据充分（roadmap + 本轮对话）。A 已提供"可见性"，B 的增量价值是"自动实施"。**但**：当前单用户、低任务量，`worth_changing` 提案可能很稀疏——为可能罕见的事件建"worktree + 任务图 + programmer"这套重机器，ROI 存疑（**Q3**）。

### 3b. User Value / MVP
- 计划已把 US1（提案+审批）设 P1、US2（自动实施桥接）设 P2，支持分期。**强烈建议真的分期发**：先发 US1，用真实数据验证"提案质量值不值得自动改"，再建 US2 桥接（**X2**）。在噪声未验证前就把自动改代码搭上去，是在不确定的地基上盖重楼。

### 3c. Alternative Approaches
- 更轻的替代：US1 之后，用户可把批准的提案直接丢给现有助理对话去改（人肉触发），不建专用桥接。自动桥接的价值在"省那一步"，但要确认这一步的体力值得这套机器（与 Q3 同源）。可接受，但应有意识地权衡。

### 3d. Edge Cases & UX
- **提案噪声（X1，💡）**：唯一性只按 `(source_review_id, finding_index)`，**跨复盘的同类发现会重复堆积**——"助理重复抓取"这种系统性低效几乎每个任务都会被审查员再报一次，BrainScreen 会被近重复提案淹没 → 审批疲劳 → 功能被无视。需要跨复盘的去重/合并或冷却。
- **可发现性（P1，💡）**：提案落在 BrainScreen（管理屏，用户未必常开），无通知机制。用户怎么知道有提案待审？建议复用既有 toast/badge 在有 `pending_review` 时提示。
- **资源争用（X3 相关，💡）**：后台自我改造任务图与用户真实任务**共用同一个 dispatcher 线程池（有界 worker）**。自我改造跑起来可能挤占用户任务的执行容量、拖慢真实对话。

### 3e. Success Measurement
- SC-001..006 可度量、技术无关，质量好。缺一个"功能值不值得留"的产品指标（如 approved/rejected/merged 比例），建议轻量记录（💡，非阻塞）。

## Engineering Lens Findings

### 4a. Architecture Soundness
- **执行体 workspace → worktree 重定向（E1，🎯）**：research D4 已诚实标 ⚠️——但这是**整个隔离与安全模型的地基**。若执行体无法被干净地指向特定 worktree（当前 workspace ≈ 项目根），programmer 就会改到正在运行的主工作树，worktree 隔离、source-only、git 回滚全部落空。**这是"假设错了就推翻安全模型"的承重假设，不能等到实现中途才发现。**

### 4b. Failure Mode Analysis
- **递归自我改造砖化（E2 的一半，🎯）**：没有任何东西阻止一条提案去**改自我改进系统自身**（proposal_service / bridge / 审查员 / 调度器）或核心启动路径。一次坏的自我改造可能：砖掉启动、砖掉"改自己的能力"、或产生更多坏提案的反馈环。blast-radius 必须把"自我改进子系统 + 启动核心路径"列为禁改区或至少显式标红。
- **"测试通过"的可信度（E3，💡）**：合并手动是好护栏，但用户容易信任绿灯就合并；而坏改动可能跑过了被改路径的测试、却砖了未覆盖路径。需明确自我改造跑哪些测试、绿灯的语义边界。

### 4c. Security & Privacy
- **`exec` 不在 source-only 的覆盖里（E2 的另一半，🎯/💡）**："只改源码文件"说的是写文件；但"跑测试"需要 `exec`，而 `exec` 是比文件写**宽得多**的能力（可跑任意命令、联网、破坏）。爆炸半径的定义必须显式涵盖 `exec`：允许 worktree 内测试型 exec，但要挡住网络/破坏型 exec，否则"只改源码"是个漏的承诺。
- **finding 快照的敏感内容（Q2，🤔）**：`what/evidence` 快照自执行 trace 并持久化+展示。A 已治理 skeleton，但提案表是新持久化+新展示面，需确认不比 A 多泄漏 trace 敏感内容。

### 4d. Performance & Scalability
- 单用户低量，无吞吐瓶颈。轮询 job 仅扫 `in_progress`，开销可忽略。✅

### 4e. Testing Strategy
- 覆盖面规划完整。**但闭环集成测试（命门回归）若拉真 LLM/executor 会又慢又 flaky**（项目已知多文件同进程 teardown flaky）。建议闭环测试 **mock executor/LLM**，确定性断言"建图→踢图→状态机→回报"的接线，不去测改码质量（E6，💡）。

### 4f. Operational Readiness
- **worktree 堆积（E5，💡）**：失败/完成的 worktree 按 D8 保留到 reject，长期会在 `.worktrees/improvement/` 堆积占盘。需清理机制/保留上限（可复用 `speckit-worktree-clean` 思路）。
- 迁移 `v21` 仅加表、向后兼容、forward-only（与项目一致）。✅

### 4g. Dependencies & Integration
- **base = HEAD commit，非工作树（Q1，🤔）**：worktree 从 HEAD 建，用户主工作树的未提交改动不进自我改造的基线。可能让用户困惑（"我刚改的它没看到"）。需在文档/UI 说明。
- **跨提案陈旧基线 + 合并冲突（E4，💡）**：多条提案各从各自批准时的 HEAD 建分支；合并了 A 之后，B 的分支基线变旧，可能冲突或回带已修问题。建议串行化自我改造（一次一条）或合并前提示 rebase/重建。

## 建议的 spec/plan 改动（提议，未应用）

1. **plan.md / tasks 排序（E1, X2）**：把"执行体 workspace→worktree 重定向 spike + 冒烟"列为 **tasks 的第一项前置门**；US2 桥接的其余任务依赖它通过。US1（提案+审批+UI）与桥接解耦，可先独立完成。
2. **spec FR-014 收紧（E2）**：把"只改源码"明确为——(a) 文件改动限 worktree 内 git 源码；(b) `exec` 仅允许 worktree 内测试型、禁网络/破坏型；(c) **禁改自我改进子系统自身文件与启动核心路径**；三者各补门卫测试。
3. **spec/data-model 去重（X1）**：提案唯一性增加"跨复盘同类合并/冷却"语义（如按 `finding_type + 归一化 what` 去重或冷却窗口）。
4. **spec 补充（E4/E5/P1/Q1）**：串行化自我改造或合并前 rebase 提示；worktree 保留上限；pending 通知；基线=HEAD 语义说明。
