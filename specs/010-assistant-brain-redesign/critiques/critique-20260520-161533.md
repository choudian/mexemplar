## Product Lens Findings

### 3e. Success Measurement

**[P7] 💡 SC-002 的"100%"是落在 LLM 判断行为上的硬指标,缺测量方法,且与 SC-001 取法不一致**

SC-002 写道:"**100%** of user task requests ... result in delegation; the assistant performs zero direct task execution."

但任务/对话的区分由 LLM 逐条判断——FR-001:"The assistant uses this distinction to decide **per message** whether dispatch is required"。对比 SC-001 明智地用试验比例度量同样是 LLM 驱动的行为:"in **at least 9 of 10 trials**"。

值得肯定的是:助理工具集(`reply_to_user` / `delegate_to_subagent` / `delegate_to_specialist` / `create_specialist` / `retrieve_*` / `invalidate_memory_entry`)**没有任何内联执行任务的工具**——"派发"在结构上基本被工具集强制,这是规格的优点。因此 SC-002 真正的残余失败模式不是"漏派发",而是"助理用 `reply_to_user` 直接对话式地假装完成、或口头作答一个本应派发的任务",这仍是 LLM 判断依赖项,无法作为硬性 100% 保证。SC-004("100% 自动产物有 reason")可由 DB `reason NOT NULL` 结构性保证、SC-010 可由"不建确认弹窗"保证——它们的 100% 成立;SC-002 是唯一一条 100% 落在 LLM 行为上、却既无测量方法(几次样本?谁判定某条算不算"task"?)也不可证伪的。

**Suggestion**: 把 SC-002 改为与 SC-001 同构的可度量形式(如"在 N 次任务型请求样本中,至少 X/N 被正确派发且零内联执行"),或补一句测量口径说明。"100% 调度"的设计姿态保留不变,只让成功标准可证伪。

## Engineering Lens Findings

### 4a. Architecture Soundness —— 跨阶段一致性

**[E11] 🎯 持久区的 P1/P2 阶段归属在四份文档间自相矛盾;FR-028 破冰答案写入机制未定义**

这是本轮的核心发现,与上一轮已修复的 E3 是同一类缺陷(跨阶段范围错配),证据链如下:

*要求持久区在 P1 即生效的证据:*
- `spec.md` **FR-028**(属 US1 = **P1**):"System MUST write the user's icebreaker answers **directly into initial persistent-zone entries**, each with a reason." → 破冰是 P1,破冰答案必须落在持久区。
- `spec.md` Architecture Impact(line 271):"the persistent zone MUST be **injected in full** (all active entries)" 且 "the ranking is therefore observable and verifiable **from Phase P1 onward**"。对应 Clarification(line 136)同义。
- `data-model.md`(概览 + `migrate_to_v11` 伪代码 step 2):v11 migration 含"数据回填:SELECT from `assistant_profile` → INSERT `brain_memory_entries` (zone='persistent', origin='system_migration')"。
- `research.md` Decision 7:Profile 数据通过 v11 migration 的一次性回填迁入持久区。
- v11 migration 属 **P1**(`plan.md` P1 范围"v11 migration(全部表)";CC-009 "P1 一次性建全所有 schema,后续 phase 不新增 migration")。`migrate_to_v11` 是一个原子迁移函数,其 step 2 回填会随 P1 的建表一并执行——**无法把回填拆到 P2**,否则就要拆迁移,违反 CC-009。

*与上述冲突的 plan 表述:*
- `plan.md` **P1 范围**(line 144):"单次 LLM 沉淀(**只激活热区写入**)、BrainContextBuilder(**热区注入**)、更新 assistant_prompt(热区 + **持久区框架**)"。
- `plan.md` **P2 范围**(line 152):"沉淀**激活持久区** + 归档区写入;…;**Profile 数据一次性迁入持久区**"。

**四处矛盾:**
1. **Profile 迁移阶段双重排期**:data-model + research 说它发生在 v11 migration(P1);plan P2 又把它列为 P2 范围。同一动作被放进两个阶段。
2. **持久区注入**:spec 要求"P1 起全量注入持久区";plan P1 只做"持久区框架"(框架 ≠ 全量注入)。
3. **破冰答案落地**:FR-028 要求 P1 把破冰答案写入持久区;plan P1 沉淀"只激活热区写入" → 破冰答案会落进热区(随后衰减),而非持久区 → 直接违反 FR-028。
4. **FR-028 的写入机制本身未定义**:助理工具集没有任何"写记忆条目"的工具;"directly write into persistent-zone entries" 究竟是沉淀路由、迁移回填、还是某条未列出的路径,无任何文档说明。

**为什么是 🎯**:plan 的"分阶段交付计划"是 `/speckit-tasks` 给任务分配阶段的权威依据。按当前 plan,tasks 生成器会把持久区注入与写入全部排进 P2,P1 的 `tasks.md` 将**缺失**(a)持久区全量注入任务、(b)破冰答案→持久区写入任务,直接违反 spec 的 P1/US1 要求(FR-028、注入 Clarification、SC-005 破冰链路);同时 Profile 迁移会在 P1(migration)与 P2(plan 范围)被双重排期。这与上一轮判 🎯 并已由用户修复的 E3 结构完全一致,应同等对待。

**产品后果**(为何不只是文字洁癖):若 P1 真按现 plan 落地,破冰流程(FR-028 / SC-005,P1 的用户可见流程)收集到用户的核心身份事实后**不会被作为持久事实留存**——它们落进会衰减的热区 → 几周后衰减 → 下次会话助理不再具备稳定身份认知 → P1 自身的核心承诺("从每次重新认识你变成记得你")在 P1 即被打折。

**Suggestion**(多文档,一根因):
- 修订 `plan.md`:明确持久区是 **P1** 的一等组成。P1 沉淀写入 **hot + persistent** 两个分区(沉淀 schema 本就同时产出二者,见 E12);P1 的 BrainContextBuilder 注入热区 top-N + **持久区全量**;P1 的 assistant_prompt 含真实持久区注入,而非仅"框架"。
- 从 `plan.md` P2 范围**移除**"Profile 数据一次性迁入持久区"(它发生在 P1 的 v11 migration)。P2 改述为"激活**归档区**写入 + 归档分层 + `retrieve_archive`";若 P2 仍需体现持久区,应明确 P2 只新增"沉淀驱动的持久区增量",而 migration 回填 + 破冰写入归 P1。
- 在 `spec.md` FR-028 明确破冰答案进入持久区的**机制**(推荐:破冰 Segment 的沉淀把破冰答案路由为 `zone='persistent'` 的条目;若产品要求"破冰当轮即时可见",须说明这与"全脑封存后沉淀生效"的语义如何协调)。
- 修订后建议复跑 `/speckit-critique-run` 复核此项闭合。

**[E12] 💡 `distillation_output` 工具 schema 固定 5 分区,但分阶段只增量激活分区,二者关系无文档**

`quickstart.md` 的 `DISTILLATION_TOOL_SCHEMA` 把 `hot_zone / persistent_zone / subconscious_zone / failure_zone / prediction_zone` **全部列为 required**;FR-021 也定义沉淀为"a single structured LLM call whose response is a multi-zone JSON object",validity = "match the expected multi-zone schema with **all required zone fields present**"——schema 是固定多分区。沉淀工具在 **P1** 交付(quickstart 实现顺序第 5 项)。

但 plan 分阶段只增量激活分区:P1 热区(E11 修订后含持久区)、P2 归档、P4 潜意识 + 失败 + 猜测。于是 P1 的沉淀 LLM 调用若用固定 5 分区 schema,LLM 会产出全部分区的条目,而 P1 的 `DistillationService` 只持久化已激活分区 → 其余分区的提取结果被直接丢弃。后果:(a)P1–P3 阶段为**永远被丢弃的分区**持续付 LLM token(放大下方沿用项 E6 的成本问题);(b)"P1 只激活某些分区"与"schema 固定 5 分区"之间没有任何文档说明 P1 是用完整 schema 丢弃未激活分区、还是用裁剪 schema(若裁剪,则 schema 随 phase 演化,与 data-model/quickstart"固定 schema"表述矛盾)。

**Suggestion**: 在 `research.md` 增补一条 Decision,或在 `quickstart.md`/`data-model.md` 明确:沉淀 schema 始终全量请求,各 phase 的 `DistillationService` 显式只持久化已激活分区、丢弃其余(并承认这部分提取 token 成本,关联 E6);**或**明确各 phase 用裁剪 schema 并接受 schema 按 phase 演化。二选一并写下来,避免 `/speckit-tasks` 在 P1 沉淀任务上做无依据的实现假设。

### 4a. Architecture Soundness —— 规格内部矛盾

**[E13] 💡 猜测(预测)条目的"生成"机制在 spec 与 quickstart/plan 间矛盾**

- `spec.md` **FR-025**:周期性后台工作明列 "**prediction generation** and verification" → 生成是周期 job。
- `spec.md` US4 Acceptance Scenario 4:"**When 猜测生成工作运行**" → 称之为独立"工作/job"。
- **但** `quickstart.md` 的 `DISTILLATION_TOOL_SCHEMA` 把 `prediction_zone`(含 `verification_checkpoint`)列为单次 **Segment 沉淀工具**的必填输出。
- `plan.md` P4:"沉淀**激活…猜测区写入**" → 把猜测写入归为沉淀产物。
- `research.md` 无任何 Decision 澄清。

矛盾:猜测到底是(a)每个 Segment 沉淀时由 distillation LLM 产出,还是(b)由独立周期 worker job 生成?FR-025 + US4 AS4 指向(b);quickstart schema + plan P4 指向(a)。若(b)成立,P1 交付的 distillation schema 里 `prediction_zone` 字段是多余的;若(a)成立,FR-025 的"prediction generation"周期项措辞是错的。

**Suggestion**: 在 `research.md` 增补一条 Decision 明确猜测生成机制,并同步 `quickstart.md` schema、`plan.md` P4、`spec.md` FR-025 三处。倾向(b)独立周期 job——"对未来的预测"需要跨 Segment 的累积视角,塞进单 Segment 沉淀语义不顺;若定(b),应从 `distillation_output` schema 移除 `prediction_zone`。该项被 P4 gated、不阻塞当前 tasks,但 `distillation_output` schema 是 **P1 工件**,应在 P1 之前定。

**[X3] 💡 新"技能池 / 技能池管理面板 / 专员"概念与现有"技能列表 / 技能组合"屏幕重叠,plan.md 完全未提及现有屏幕(产品 UI 一致性 × 工程集成)**

- **断点**:`plan.md` 的 Project Structure 只列新增的 `BrainScreen` / `SpecialistScreen` / `brainStore` / `specialistStore`,**对现有 `screens/skills/` 与 `screens/compositions/` 只字未提**。`spec.md` Assumptions 仅声明 "Skills and specialists coexist in the short term; consolidation deferred"——它覆盖了 skills-vs-specialists 的概念共存,**未覆盖**"新技能池管理面板 vs 现有技能列表屏幕"、"专员 vs 技能组合(Composition + `MemberSelector`,把成员组合成一个单位)"的 UI/实现重叠。

- **产品视角**:交付后导航栏会同时出现「技能教学 / 技能列表 / 技能组合 / `/brain`(内含技能池面板) / `/brain/specialists`」五个与"能力"相关的入口。用户难以分辨"技能列表"与"`/brain` 技能池"、"技能组合"与"专员"的差别。

- **收敛**:两个视角都指向同一动作——必须在 plan 显式写出新旧能力管理面之间的关系。

**Suggestion**: 在 `plan.md` 增补一段,明确本功能与现有 `skills` / `compositions` 屏幕的关系:技能池管理面板是**复用 / 取代 / 并存**于现有技能列表?专员与"技能组合"是两套独立机制,还是应收敛?即使结论是"短期并存"(与 Assumptions 一致),也应在 plan 显式写出。该项不阻塞 P1(技能池面板在 P5、专员在 P3),但应在 P3/P5 规划前解决。
