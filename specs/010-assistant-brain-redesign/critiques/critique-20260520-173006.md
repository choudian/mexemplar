## Executive Summary

本轮审查重点复核用户刚刚要求“全部修复”的上一轮发现：E11、E12、E13、P7、X3，以及沿用的 E10。结论是：**上一轮新增的 Must-Address E11 已闭合**，并且相关同根项 E12/E13/P7/X3/E10 也已同步吸收，没有观察到新的阻塞级矛盾。

最关键的修复已经连成一条一致的实现线：

- P1 现在明确包含 `assistant_profile` 迁移回填、热区 + 持久区沉淀、持久区全量注入，以及破冰答案通过 P1 Segment 沉淀写入持久区。
- P2 不再重复排期 Profile 迁移，只扩展长期经验沉淀、归档写入、归档分层和 `retrieve_archive`。
- `distillation_output` schema 改为按 phase 裁剪，P1 只请求 `hot_zone` + `persistent_zone`，不再为未激活分区付 LLM 成本。
- 猜测区生成改为周期性 prediction generation worker，`prediction_zone` 不再属于 Segment 沉淀 schema。
- SC-002 从不可证伪的 “100% of user task requests” 改为带人工标注样本的 `至少 9/10 + 零直接执行`。
- plan/research/spec 已明确新 `/brain` 技能池面板与现有技能列表、技能组合屏幕短期并存且职责不同。

本轮只新增 **2 条非阻塞 Recommendation**：用户编辑/手动创建的 `reason` 默认填充规则需要在契约里写得更明确；`data-model.md` 的 `loaded_count=0` 效果比说明最好补一句“不代表新条目排序应被压低”。这两项不会污染 `/speckit.tasks` 的 P1/P2 阶段拆分，可在任务生成前或实现时顺手补。

## Product Lens Findings

### 3a. Problem Validation

**Status**: 无新增阻塞项。

首轮沿用项 P1（需求证据主要来自设计稿）仍是产品侧背景风险，但用户此前选择不处理，本轮没有新增证据缺口。当前 spec 依然有清晰的用户痛点叙述：助理从“每次重新认识你”转为“记得你并能调度执行体”。

### 3b. User Value Assessment

**Status**: E11 修复后 P1 用户价值恢复闭环。

上一轮最核心的产品后果是：破冰答案如果只进入热区，会让 P1 的“记得你”承诺打折。现在 `spec.md` FR-028 明确破冰答案通过 P1 Segment 沉淀写入 `persistent`，`plan.md` P1 也包含持久区全量注入，因此 P1 用户故事恢复为可独立交付的 MVP。

### 3c. Alternative Approaches

**Status**: 无新增阻塞项。

E12 的取舍已定为 phase-specific schema，而不是全量 schema 后丢弃。这是更保守的成本路径，也避免把未激活分区误导进 P1 tasks。

### 3d. Edge Cases & User Experience

**[P8] 💡 用户手动编辑/创建产物的 reason 填充规则在 API 契约中仍偏隐含**

`data-model.md` 要求 `reason NOT NULL`，且说明 `origin='user_edit'` 或 `manual` 也必须非空；`spec.md` FR-032/FR-038/FR-042 强调自动产物和演化链的 reason。但 `contracts/rest-api.md` 的 `PUT /api/brain/entries/{entry_id}`、`POST /api/brain/specialists` 请求体没有 `reason` 字段，也没有说明后端如何填充用户编辑/手动创建的 reason。

这不阻塞实现，因为后端完全可以统一生成默认 reason，例如“用户在管理界面编辑”或“用户手动创建专员”。但如果 tasks 只看 REST contract，可能会误以为 `reason` 可空，或在实现时撞上 NOT NULL。

**Suggestion**: 在 `contracts/rest-api.md` 对编辑/创建接口补一句：当请求体未提供 reason 时，后端必须写入系统默认 reason；用户编辑产生的 `feedback_signals.context_summary` 仍记录被修改内容摘要。

### 3e. Success Measurement

**Status**: P7 已闭合。

SC-002 现在写为“至少 10 条人工标注任务样本中，至少 9/10 正确派发，且 0 accepted runs 出现助理直接执行”。这已经与 SC-001 的试验比例口径同构，并保留“零直接执行”的硬门槛。无新增阻塞项。

- `data-model.md` 与 `research.md` 的 v11 migration 回填描述仍与 P1 一次建表策略一致。

**E13 Re-Verification**: ✅ 闭合。

E1/E2 继续闭合：Segment 沉淀写入与状态转换仍要求单事务；`open` 态崩溃恢复仍由未覆盖消息隐式推导。上一轮沿用的 E7（单 worker 承载多类周期任务的饥饿风险）仍是非阻塞建议，未因本次修复恶化。

### 4c. Security & Privacy Review

**Status**: 无新增阻塞项。

本轮改动没有扩大敏感面。大脑数据安全边界仍与 SQLite/OS 文件系统一致；sidecar token 与分层边界没有被新文档绕开。

### 4d. Performance & Scalability

**Status**: E12 的成本风险已降低。

phase-specific schema 消除了 P1/P2 为未激活分区付费的主要浪费。上一轮沿用的 E6（缺少 LLM 成本/用量观测与上限）仍然存在，但已不再被固定全量 schema 放大。

### 4e. Testing Strategy

**Status**: 无新增阻塞项。

`plan.md` 仍规划 Segment 状态机、Repository、沉淀链路、上下文注入、专员招募、guardrail 等测试。建议 tasks 生成时确保新增 P1 持久区行为有测试：Profile 回填、破冰答案入持久区、持久区全量注入。

### 4f. Operational Readiness

**Status**: 首轮沿用项 E8 仍是非阻塞风险。

v11 仍是单向迁移，无回滚/feature flag 方案。这是既有 Recommendation，用户此前选择不处理；本轮没有新阻塞。

### 4g. Dependencies & Integration Risks

**[E14] 💡 `loaded_count=0` 在 data-model 中被定义为效果比 0.0，但文档可再防止实现误读**

`data-model.md` 仍写 `effectiveness = referenced_count / loaded_count`，`loaded_count=0` 时视为 0.0。`spec.md`、`research.md` 已明确复合评分和探索配额，因此不是实质矛盾。但 tasks 或实现若只看 data-model 的公式，可能把新条目按 0.0 效果比压到末尾。

**Suggestion**: 在 `data-model.md` 效果比公式旁补一句：`loaded_count=0` 的 0.0 仅用于避免除零，排名时必须结合 `plan/research` 的探索配额，不得作为排除或永久降权依据。
