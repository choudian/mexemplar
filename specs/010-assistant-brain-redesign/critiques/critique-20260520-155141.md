# Critique Report: Assistant Brain Redesign

**Feature**: `010-assistant-brain-redesign`
**Critique Date**: 2026-05-20
**Artifacts Reviewed**: spec.md、plan.md、research.md、data-model.md、contracts/rest-api.md、contracts/events.md、quickstart.md、checklists/requirements.md、constitution.md
**Verdict**: ⚠️ **PROCEED WITH UPDATES** —— 发现 3 个 Must-Address 项,均为工程可解项,无需推翻规格。

---

## Executive Summary

这份规格的质量明显高于平均水平:30+ 条 Clarifications、15 个 Edge Case、45 条 FR、12 条 SC、11 条 CC,枚举值(Segment 状态、Memory Entry 状态、zone 集合)在 spec / data-model / contracts 三处保持内部一致,Constitution Check 逐条给出诚实证据。设计稿驱动的"6 分区大脑 + 100% 调度"模型概念清晰,5 阶段增量交付路径合理。

但本次评审从工程视角发现 **3 个会污染 `tasks.md` 的 Must-Address 缺陷**,全部集中在 **Segment 生命周期的健壮性** 与 **跨阶段数据依赖**:

1. **沉淀写入的原子性未声明** —— FR-021 只保证"恰好一次触发",不保证"恰好一次写入";崩溃可产生重复记忆条目。
2. **`open` 态 Segment 的表示与崩溃恢复未定义** —— 崩溃恢复只覆盖 `distilling` 态,进程被杀时进行中的会话增量去向不明。
3. **效果比注入排序在 P1/P2 没有数据来源** —— `referenced_count` 要到 P3 才可计量,导致 P1/P2 的 top-N 排序退化为空操作,违反 CC-009 的阶段独立可验证性;且该排序对新条目存在冷启动饿死问题。

这三项都能用规格 / 计划层面的文字补充解决,不触及核心架构。除此之外有 13 条 Recommendation(主要是成本可观测性、回滚策略、检索机制、UX 死等)和 1 条 Question(心理画像的隐私观感)。建议先吸收 Must-Address 修订,再运行 `/speckit.tasks`。

整体判断:**规格地基稳固,P1-P3 价值清晰可交付;P4(尤其猜测区)价值最弱、成本最高,建议在 tasks 前重新审视其去留。**

## Product Lens Findings

### 3a. Problem Validation

**[P1] 💡 需求证据完全来自设计稿,无用户侧证据**
规格 Input 明确写明本功能从两份设计稿(`assistant_agent_redesign_draft.md` / `assistant_brain_implementation_design.md`)反推而来。spec / research 全程未引用任何用户研究、支持工单或使用数据。这是一次典型的"愿景驱动"重构:把助理从"记事本"升级为"有大脑的人"是一个有吸引力的叙事,但没有任何地方证明用户**正在因为"助理记不住"而受挫**。
考虑到功能体量(6 分区 / 6 张新表 / 7+ 新工具 / 2 个新 UI 模块 / 1 个跑 7 类周期任务的后台 worker),这是一笔很大的赌注。
**Suggestion**: 不要求补做用户调研,但应在 spec 的 Assumptions 中**显式承认这是一次愿景性投资**,并给出一个可证伪的早期信号(例如"P1 上线后,用户在新对话中复述背景的频次下降"),让团队在 P1 后能判断是否值得继续 P4/P5。

### 3b. User Value Assessment

**[P2] 💡 现有 `assistant_summaries` 记忆内容在迁移中被悬空丢弃**
data-model 说明 `assistant_summaries` 表"保留(过渡期 backward compat)",但只有 `assistant_profile`(称呼 / 风格 / 备注)被 FR-011 迁入持久区。当前助理的**单段记忆摘要内容**没有任何 FR / 迁移步骤接收它。结果:一个有存量记忆的老用户,在大脑系统启用后,助理会**忘掉它此前积累的全部记忆摘要**,直到新 Segment 重新沉淀。这与本功能"从每次重新认识你变成记得你"的核心承诺直接矛盾——恰恰是老用户体验到一次记忆倒退。
**Suggestion**: 二选一并写入 spec —— (a) v11 migration 把现有摘要作为一条 `origin=system_migration` 的持久区(或热区)条目回填;或 (b) 在 Assumptions 显式声明"旧摘要内容被有意丢弃",并说明理由(例如旧摘要结构无法可靠拆分到 6 分区)。当前是"既没迁移也没说明"的隐性丢失。

### 3d. Edge Cases & User Experience

**[P3] 💡 "不显示阻塞加载屏" + "上下文就绪前不回复" 会产生死等 UX**
Clarification 决定:会话页面立即开放输入、上下文后台构建、助理首轮回复必须等 `brain_context_ready`、且"用户不被展示阻塞加载屏"。这三条叠加的结果是:用户打开对话、立刻打字、回车,然后**面对一片静默**——既没有加载屏,助理也不回应。这比一个明确的加载指示更糟,因为用户无法区分"在想"和"卡住了"。
**Suggestion**: 区分"阻塞模态加载屏"(规格正确地禁止)与"轻量进行中反馈"(规格应当要求)。补一条 FR:首轮回复在等待上下文期间,UI MUST 显示一个非阻塞的"思考中 / typing"指示,直到 `brain_context_ready` 后开始流式回复。

### 3e. Success Measurement

**[P4] 💡 没有记忆质量 / 对话回归指标,也没有回滚触发条件**
12 条 SC 全部度量**功能是否存在**(条目有 reason、调度发生、猜测拿到状态…),没有一条度量**大脑是否让助理变得更好**。沉淀是 LLM 驱动的,完全可能产出低质量甚至错误的记忆条目,这些条目被注入上下文后会污染助理回复。当前规格下,本功能可以"12 条 SC 全绿"地上线,同时让助理变得更难用,而没有任何指标能发现这一点。也没有任何地方定义"什么信号触发回滚"。
**Suggestion**: 补一条聚焦质量的 SC(例如"P1 上线后,助理引用的记忆条目中被用户当轮纠正 / 失效的比例低于阈值",可借用已规划的 `invalidated` 信号和效果比来度量),并在 spec 写明一个回滚触发条件。

**[P5] 💡 全程没有延迟 / 响应性的成功标准**
本功能同时引入两个增加延迟的机制:会话启动的异步上下文构建、以及 100% 调度的派发间接层(见 X1)。SC-001..SC-012 没有一条约束响应性。一个"功能正确但明显变慢"的助理会被所有 SC 判定为成功。
**Suggestion**: 补一条延迟门卫 SC(例如"纯对话性回复的首字节延迟、以及简单任务的端到端延迟,相对重构前不出现可感知回归")。

### 3c. Alternative Approaches & Privacy

**[P6] 🤔 潜意识区 + 猜测区构成一份心理画像,在管理 UI 中展示的观感未被评估**
潜意识区存储"用户难以直说的偏好 / 价值观 / 风格 / 反感",猜测区存储"对用户下一步行为的预测"。大脑管理模块会把这些**默认展开、不折叠**地呈现给用户(FR-042)。这在技术上没问题,但产品上有真实风险:用户打开 `/brain` 看到系统对自己"价值观"和"反感"的推断、以及"系统预测你接下来会做 X"——这可能让人不安,而非感到被理解。规格把数据安全决策(CC-011)聚焦在"是否加密",却没有评估**把推断结果摊给用户看**这件事本身的信任成本。
**Suggestion**: 这是一个需要 stakeholder 拍板的产品判断,不是开发团队能独立决定的。明确一点:潜意识 / 猜测条目的呈现措辞应保持"参考性、可能不准"的语气(FR-013 已要求标注为参考性,可延伸到 UI 文案);并确认产品方接受"向用户展示其心理画像"这一姿态。

## Engineering Lens Findings

### 4b. Failure Mode Analysis

**[E1] 🎯 沉淀写入未声明与状态转换的原子性,崩溃会产生重复记忆条目**
FR-021 把 exactly-once 精确地定义为**触发**层面的保证:`pending → distilling` 用 CAS / 行锁完成。但"恰好一次写入"没有被任何地方保证。崩溃场景:
1. Worker 抢占 Segment(`pending → distilling`),LLM 调用成功,把 10 个条目写入 `brain_memory_entries` 并 commit;
2. 在把 Segment 置为 `completed` 之前,应用崩溃;
3. 重启时崩溃恢复逻辑(Clarification:"扫描并重置所有 `distilling` Segment 回 `pending`")把它打回 `pending`;
4. Worker 重新沉淀,**再写一遍 10 个条目** —— 第一批已 commit 的条目还在,产生重复。

data-model 把 `completed_at` 只当作一个普通列,没有任何地方说明"条目 INSERT + Segment 置 `completed`"必须在**同一个事务**内提交。
**Suggestion**: 在 spec FR-021 / data-model 明确:沉淀的全部条目 INSERT 与 Segment `distilling → completed` 状态转换 MUST 在单个数据库事务内原子提交。崩溃发生在 commit 前 → 整体回滚 → Segment 自然停留在 `distilling`,由崩溃恢复正常重置重试,不留半成品。这同时是 P1 `DistillationService` 任务的关键约束。

**[E2] 🎯 `open` 态 Segment 的表示形式与"进程被杀"的恢复行为未定义**
data-model 的状态机图写的是 `[open] → pending (sealed)`,但 `open` **不在** `brain_segments.status` 的枚举里(枚举只有 `pending/distilling/completed/failed`);且 `message_id_start/end` 标注为"已封存时填充"。这意味着一个进行中的 Segment 要么根本不是数据库行(隐式,由"尚未被已封存 Segment 覆盖的消息"推导),要么是某种未文档化的内存状态。两种解释导致完全不同的崩溃行为:
- 若是隐式的:进程被杀 → 下次 `new_session` 边界能正常封存遗留增量 → 无损失。**但这个推导规则没有写下来。**
- 若是内存行:进程被杀 → 该 Segment 连同整段会话增量永久丢失,永不沉淀。

Clarification 极其细致地处理了 `distilling` 态的崩溃恢复,却完全没有覆盖"崩溃 / 被杀时 Segment 还处于 `open`"。而 `brain_segments` 的 schema 是 P1 一次性建全的(CC-009),这个表示决策必须在建表前定。
**Suggestion**: 在 data-model 明确 `open` Segment 的表示(推荐"隐式":不建行,由消息表与最后一个已封存 Segment 的 `message_id_end` 推导待封存范围),并补一条 Edge Case 说明非优雅退出后,遗留的进行中增量如何在下次启动 / 下次会话时被封存与沉淀。

### 4a. Architecture Soundness — 跨阶段数据依赖

**[E3] 🎯 效果比注入排序在 P1/P2 没有数据来源,违反 CC-009 阶段独立性,且对新条目存在冷启动饿死**
spec 的 Architecture Impact 与 Clarification 规定注入策略为分层:持久区全量、热区 / 潜意识区各取 top-N,**按效果比 `referenced_count / loaded_count` 排序**。但这条排序链有两个断裂:

1. **跨阶段断裂**:`referenced_count` 只能通过 `reply_to_user` 工具携带的 `memory_entries_referenced` 字段计量,而 `reply_to_user` 工具与该计量都排在 **P3**(plan P3 范围明列)。热区注入却在 **P1** 就交付(plan P1 范围:"BrainContextBuilder(热区注入)"),P2 范围更直接写明交付"效果比排序"。于是 P1 和 P2 期间,所有条目 `referenced_count` 恒为 0,效果比恒为 0.0,top-N 排序退化为"按 DB 顺序取前 N"。CC-009 要求"每个 phase 独立可观察、可验证"——P2 无法验证它声称交付的效果比排序。

2. **冷启动饿死(即使 P3 之后也存在)**:一条新沉淀出的高价值条目 `loaded_count=0` → 效果比 0.0 → 排在最后 → 永远进不了 top-N → 永远拿不到 `loaded_count` → 永久饿死。纯效果比排序在数学上会把新条目锁死在底部。

**Suggestion**: 在 spec / research 明确一个**兜底 / 混合排序**:热区按 `relevance_score` 降序 + 新近度兜底,潜意识区按新近度兜底;效果比作为一个**加权项**叠加,而非唯一排序键;并为低 `loaded_count` 的新条目保留一个探索性配额。这样 P1/P2 的排序立即可验证,P3 引入计量后只是让权重生效,且彻底消除冷启动饿死。这是运行 `/speckit.tasks` 前必须定的事,因为它直接决定 P1 `BrainContextBuilder` 任务的实现。

### 4d. Performance & Scalability

**[E4] 💡 `retrieve_archive` 的检索机制完全未指定,且向量库被 CC-003 禁止**
research.md 给出 10 条决策,**没有一条**涉及归档区检索。归档区是"对话历史的分层索引",对长期用户会增长到数千条。FR-035 提供 `retrieve_archive(query)` 工具(P2 交付),但 query 如何匹配到条目?CC-003 明确禁止引入向量数据库。在没有向量检索的前提下,对一个持续增长的归档做语义检索是一个真问题——SQL `LIKE` / 关键词匹配的召回质量很可能不够。
**Suggestion**: 在 research.md 补一条 Decision(例如"Decision 11: 归档检索机制"),明确在 CC-003 约束下的方案——可能是依赖分层摘要(日/周/月/年)缩小检索面 + 关键词,或 SQLite FTS5 全文索引(不算"新中间件")。这不阻塞 P1,但应在 P2 tasks 之前定。

**[E5] 💡 `brain_zone_changed` → 上下文重建没有去抖 / 合并**
events.md 说 `BrainContextBuilder` 消费 `brain_zone_changed` 来"判断是否重建"。一次沉淀会向多个分区写入多条条目,每次写入都触发一次 `brain_zone_changed`。没有去抖的话,单次沉淀(假设写 15 条)会触发 15 次上下文重建。
**Suggestion**: 在 events.md / plan 明确重建是去抖 / 合并的(例如沉淀完成后发一个汇总事件,或 builder 端做短窗口合并)。

**[E7] 💡 单后台线程承载 7 类周期任务,长沉淀积压会饿死时间敏感任务**
research Decision 2 选择单一 daemon 线程跑全部大脑周期任务(沉淀、热区衰减扫描、归档分层、潜意识深度沉淀、猜测生成、猜测验证、招募扫描),并显式否决了多线程("超过当前需求规模")。对单用户应用,负载低,这个取舍基本合理。但后果应被记录:一旦沉淀积压(LLM 调用慢 + 重试),**所有**其他任务——包括到点的猜测验证、热区衰减——都被阻塞。
**Suggestion**: 保留单线程决策,但在 research Decision 2 补一句已知后果,并说明缓解方式(例如 worker 每个 tick 给不同任务类型留时间片,而非"沉淀积压时一直跑沉淀")。

### 4f. Operational Readiness

**[E6] 💡 没有 LLM 成本 / 用量的可观测性,也没有任何上限**
这是本功能最被低估的工程风险。当前助理:每轮 1 次 LLM 调用 + 1 次摘要。重构后新增的 LLM 调用:每个 Segment 1 次沉淀(+重试)、周期性猜测生成、每条猜测到点 1 次验证(+重试)、周期性潜意识深度沉淀、周期性招募扫描。对一个活跃用户,token 开销可能是当前的数倍。而这是一个**用户自带 API Key 付费**的桌面应用——成本意外暴涨是直接的产品 + 工程问题。规格 / 计划没有任何成本估算、用量可观测性,也没有"关闭昂贵周期任务"的开关。CC-008 让周期可配(好,能调频率),但没有任何地方把 LLM 成本当作一等关注点。
**Suggestion**: 补一条 FR 要求大脑的 LLM 调用具备基本可观测性(调用次数 / token 量按任务类型计数,可在管理 UI 或日志查看);并确认每类周期任务都能通过 `brain.*` 配置独立关闭(降级到纯被动记忆)。

**[E8] 💡 没有回滚策略 / 特性开关;v11 迁移单向;门卫测试移除旧路径**
这是一次"重建助理大脑"级别的根本性重构,但规格 / 计划没有任何 kill switch。v11 migration 的伪代码没有 down-migration。Constitution IV 要求门卫测试证明"旧路径已移除"——也就是说旧的 `assistant_memory` 路径会被**删除**,而非开关切换。保留 `assistant_summaries` / `assistant_profile` 表对回滚有帮助,但没有"新旧助理并行、可切换"的机制。一旦上线后发现大脑让助理变差(见 P4),唯一的回退路径是回滚整个发布。
**Suggestion**: 至少做一个有意识的决策并写入 plan:要么接受"回滚 = 回滚发布"(对桌面应用可能可接受,但应明示),要么在 P1 引入一个 `brain.enabled` 配置开关,让大脑可被整体旁路、回退到旧记忆路径。考虑到这是分阶段交付,一个早期的总开关风险很低、价值很高。

### 4g. Dependencies & Integration Risks

**[E9] 💡 `reply_to_user` 在 P3 中途替换核心回复机制,有流式 / 聊天 UI 回归风险**
research Decision 4 决定把助理**所有**面向用户的回复,从现有的 `text_as_user_input=True` 隐式文本输出,迁移到显式的 `reply_to_user(...)` 中断型工具调用。已核实:`text_as_user_input` / `is_interrupting` 机制确实存在于 `agent_loop.py` / `config.py`,`reply_to_user` 工具尚不存在——即现状描述准确。三个风险:
1. 这是对核心助理 loop 回复路径的重大行为改动,而 006-chat-ui-polish 的流式渲染、SafeMarkdown、004-auth-toast 的非模态确认流都建立在当前输出机制上。把回复改成工具调用结果,可能回归 token 级流式输出——research Decision 4 在否决某个备选方案时自己也提到流式问题,但没有论证**所选方案**如何保证流式不退化。
2. 它排在 P3,但 P1 / P2 的助理同样需要回复——意味着 P1/P2 用旧机制、P3 中途换机制,是一次功能进行中的核心机制切换。
3. `referenced_count` 计量搭在 `reply_to_user` 上,把 P1/P2 的注入排序与 P3 强耦合(见 E3)。
**Suggestion**: 在 research Decision 4 补一段,明确 `reply_to_user` 方案下首字节流式输出如何保留;并在 plan 评估:是否值得把 `reply_to_user` 提前到 P1(统一回复机制 + 让 E3 的计量从一开始就到位),用一次切换换掉"P1/P2/P3 三段式机制漂移"。

## Cross-Lens Insights

> 两个视角收敛之处,优先级最高。

**[X1] 💡 100% 调度对简单任务收取真实的延迟 + 成本税(产品 × 工程收敛)**
- **工程视角**:FR-001 要求每个任务(含简单任务)派给执行体。一个原本 1 次 LLM 往返的简单任务,现在变成:助理判断 → 派发 → 临时 subagent 启动 → subagent LLM 调用 → 返回 → 助理汇总(再 1 次 LLM 调用)→ 回复,**最少 3 次 LLM 往返**。延迟与 token 对每个任务都翻倍以上。
- **产品视角**:从用户角度,一个简单任务慢 3 倍、贵 3 倍是一次体验回归。规格已经为"纯对话性交流"开了豁免口子(FR-001 Clarification),但"需要一次工具调用的简单任务"仍走完整派发,这是明确的设计意图("including simple tasks")。
- **收敛**:两个视角都指向同一个动作——要么为"单次工具调用的平凡任务"留一条快速路径,要么**显式接受这个税并用 SC 度量它**(见 P5,目前完全没有延迟 SC)。当前规格把"调度模型的纯粹性"置于"用户感知的响应性"之上,却没有让这个取舍可见、可度量。
**Suggestion**: 不一定要改 FR-001 的设计姿态,但必须让代价可见:补延迟 SC(P5),并在 spec 明确记录"100% 调度的纯粹性是经过权衡的选择,代价是简单任务的延迟 / 成本"。若产品方不接受该代价,则需要一条平凡任务快速路径。

**[X2] 💡 猜测区:用户价值不明 + 经常性 LLM 成本最高,两个视角都指向"P4 前重新审视去留"**
- **产品视角**:猜测区对助理**不可见**(FR-017),所以它不会改善任何一次对话。它的状态(hit/miss/partial/expired)+ 理由只在管理 UI 给用户看。没有任何 FR 描述验证结果被**谁消费**——FR-016/FR-025 说"用于系统自我校准",但规格里没有任何机制真的拿验证结论去校准什么。这是一个**开环**:生成(LLM 成本)→ 验证(LLM 成本)→ 展示。用户是唯一消费者,而"用户翻开 `/brain` 读一份系统对自己的预测对账单"的价值非常可疑,甚至偏向 P6 的观感风险。
- **工程视角**:猜测区是经常性 LLM 成本的大头(周期生成 + 每条到点验证 + 双重重试逻辑),却没有任何下游消费它的产出(见 E6)。
- **收敛**:两个视角都说同一件事——猜测区是整个功能里**投入产出比最差**的部分。
**Suggestion**: 它排在 P4(被 P1-P3 三个阶段 gated),所以不阻塞当前 tasks 生成。但强烈建议在进入 P4 规划前做一个明确决策:要么**为"自我校准"定义一个真实的消费者**(例如验证 miss 率高时,降低同类沉淀条目的注入权重,形成闭环),要么把猜测区**从 P4 切掉 / 降级为后续独立实验**。带着一个开环、高成本、不可见的分区进入实现,是在为不确定的价值付确定的成本。
