# Research: 010-assistant-brain-redesign

Generated by `/speckit-plan` — Phase 0 output. All NEEDS CLARIFICATION items from Technical Context are resolved here.

---

## Decision 1: 沉淀 LLM 调用架构

**Decision**: 单次结构化工具调用（LangChain `bind_tools`）。定义一个 `distillation_output` 工具，沉淀 LLM 被强制调用该工具一次，输出当前 phase 已激活写入分区的多分区 JSON。Schema 按 phase 裁剪：P1 只要求 `hot_zone` + `persistent_zone`；P2 在此基础上激活归档区写入；P4 追加 `subconscious_zone` + `failure_zone`。未激活分区不出现在 schema 中，也不做"先请求再丢弃"。

**Rationale**: 现有 `LangChainLLMClient.chat_with_tools()` 已支持工具绑定和结构化参数提取；用工具调用比 `response_format` JSON schema 更稳健（Anthropic / OpenAI 均支持），无需引入新基础设施。规格 FR-021 明确要求单次 LLM 调用；phase-specific schema 保留"单次共享理解"的原子性，同时避免 P1/P2 为尚未激活、会被丢弃的分区持续支付 LLM token 成本。

**Alternatives considered**:
- 分区顺序调用（6 次）：违反 FR-021、成本高、分区不一致。
- 全量 schema + 丢弃未激活分区：实现简单，但 P1/P2 会持续为无效输出付费，且容易让任务生成器误以为所有分区已在 P1 交付。
- `response_format` JSON schema：LangChain 封装层支持不统一，与现有 `bind_tools` 路径不兼容。

## Decision 2: 大脑后台 Worker 架构

**Decision**: 新建 `BrainBackgroundWorker`，复用现有 `AssistantTaskWorker` 的 daemon thread + `threading.Event` 模式。单一后台线程处理所有大脑周期任务（沉淀、热区衰减扫描、归档分层、潜意识深度沉淀、猜测生成/验证、专员招募）。

**Rationale**: 现有 `AssistantTaskWorker` 已验证了 daemon thread + event signal + `PendingTaskRepository` 的可靠性（CC-001 重用现有 kernel）；引入消息队列或 celery 等中间件违反 CC-003。

**Alternatives considered**:
- APScheduler / 独立定时线程：引入额外依赖，违反 CC-003。
- 多线程（每类任务一个 worker）：增加线程竞争和协调复杂度，超过当前需求规模。

## Decision 3: Segment 原子状态转换（exactly-once 沉淀）

**Decision**: SQLite 行级原子更新，使用 `UPDATE brain_segments SET status='distilling' WHERE segment_id=? AND status='pending'`；检查 `rowcount == 1` 来确认是否成功抢占。成功才启动沉淀；rowcount == 0 说明已被抢占，静默丢弃。

**Rationale**: SQLite 在写操作时使用数据库级写锁，单进程内 SQLAlchemy + `text()` 的 UPDATE WHERE 天然是原子的。等价于 compare-and-swap 语义，无需额外应用层去重。与规格 FR-021 完全吻合。

**Alternatives considered**:
- `SELECT FOR UPDATE`：SQLite 不支持行级 FOR UPDATE。
- 应用层锁（`threading.Lock`）：在单进程内有效，但如未来多进程扩展则失效；DB 级保证更健壮。

## Decision 4: 助理结构化回复与 `memory_entries_referenced`

**Decision**: 将 assistant 的所有面向用户的回复（含纯对话性回复）从 `text_as_user_input=True` 的隐式文本输出，迁移到显式 `reply_to_user(text, memory_entries_referenced=[])` 工具调用。该工具是中断型工具（`is_interrupting=True`），loop 收到后把 `text` 作为 assistant 回复展示给用户，同时批量更新 `referenced_count`。

**Rationale**: 结构化字段无法嵌入纯文本流；工具调用是提取结构化元数据的唯一可靠机制。将回复统一为工具调用同时让 100% 调度语义更清晰——助理的所有输出（包括对话性回复）都通过工具。

**Alternatives considered**:
- 在文本尾部追加 `<!--BRAIN:[ids]-->` 注释：需 backend strip 解析，脆弱，依赖 LLM 格式纪律。
- 独立 `note_memory_references(ids)` 非中断工具：LLM 可能漏掉调用，不可靠。
- `text_as_user_input=True` + 后处理 JSON 提取：破坏流式输出并引入解析复杂度。

## Decision 5: 前端路由集成

**Decision**: 新增 `brain` 和 `brain/specialists` 两个路由 ID 到现有 Zustand `shellStore` 路由数组（RouteDefinition 模式）。`/brain` 内部的分区切换用局部 state 处理；`/brain/specialists` 作为独立顶层路由。新增 `brainStore`（分区条目、pagination）和 `specialistStore`（专员列表/编辑）两个 Zustand store。

**Rationale**: 现有路由是 client-side state（不是 React Router），新路由只需在 `routes.tsx` 注册新的 `RouteDefinition`，成本低。保持与现有 5 条路由完全一致的模式（CC-005）。

**Alternatives considered**:
- 引入 React Router：需要重构全部路由，超出本 feature 范围。
- 将大脑管理嵌入 assistant 会话侧边栏：违反规格（必须是并列而非嵌套）。

## Decision 6: 上下文异步加载

**Decision**: 会话启动时后台构建大脑上下文（goroutine 等价的 `asyncio.create_task` 或线程），`brain_context_ready` blinker 事件触发后 assistant 开始首轮回复。前端 UI 在等待期间保持输入框可用，但第一轮 LLM 调用阻塞直到上下文就绪（后端阻塞，不阻塞 UI）。

**Rationale**: 规格明确要求异步非阻塞（CC-008 compatible），与 FR-020 `segment_idle_trigger` 的前端检测、后端响应模式对称。

**Alternatives considered**:
- 同步阻塞加载：用户感知延迟，违反规格。
- 不等待上下文就绪直接回复：首轮回复在无大脑上下文时发出，违反规格。

---

## Decision 7: 数据库迁移策略

**Decision**: 单次 v11 migration（`migrate_to_v11`）创建全部 6 个分区表 + 所有支撑表（共 6 张新表），现有 `assistant_summaries` / `assistant_profile` 表保留不删除（backward compat 过渡期），Profile 数据通过一次性数据回填迁移到 `brain_memory_entries` 持久区。

**Rationale**: 规格 CC-009（增量可交付）要求 P1 一次建全 schema；后续 phase 只激活业务逻辑，不再新增 migration（与 Clarifications 确认一致）。现有迁移至 v10，本次 v11。

**Alternatives considered**:
- 分 Phase 建表：增加迁移数量，后续 phase 依赖前序 phase 的 schema，破坏独立可交付性。
- 删除 assistant_summaries：破坏向后兼容性，在过渡期内可能影响现有用户。

## Decision 8: 助理工作方式——100% 调度边界

**Decision**: "任务型请求"（需要工具调用、外部操作、多步执行）→ 派给临时 subagent 或固定专员；"纯对话性交流"（问候、记忆查询直接从注入上下文回答、简短澄清）→ 助理直接通过 `reply_to_user` 工具回复，不经过派发。助理的系统 prompt 包含明确的分类判断规则。

**Rationale**: 与规格 FR-001 的"任务"定义完全对齐；Clarifications 明确了此边界。

**Alternatives considered**:
- 所有输出（含对话性）都派发：过度设计，增加延迟，闲聊也引发 subagent 创建。
- 完全没有调度边界：违反规格核心设计目标。

## Decision 9: 热区条目衰减路由

**Decision**: `entry_type` 字段（枚举 `event` | `insight`）由沉淀 LLM 在创建热区条目时赋值；衰减路由器在 `fading` → 退出时：`event` 类型 → 移入归档区，`insight` 类型 → 移入持久区或退役（relevance_score 极低时直接 soft-delete）。

**Rationale**: 与规格 FR-009 完全一致；`entry_type` 是沉淀 `distillation_output` 工具的必填字段，不允许空值。

---

## Decision 10: 反馈信号消费机制

**Decision**: 用户在管理界面执行编辑/删除时，写入 `feedback_signals` 表（含 zone、operation、target_id、context_summary）。未来的沉淀 LLM 调用和专员招募扫描在构建 prompt 时，从 `feedback_signals` 表加载近期相关信号追加为提示词上下文。信号是注入型（主动提示词注入），不是单纯分析型日志。

**Rationale**: 与规格 FR-044 完全一致；使用 `feedback_signals` 表而非 blinker 事件，因为信号需要在未来的独立 LLM 调用中被读取（blinker 是进程内瞬态）。

---

## Decision 11: 大脑上下文注入排序策略

**Decision**: 热区 / 潜意识区的 top-N 注入采用**复合评分**，而非单一效果比排序。热区主排序键为 `relevance_score`（新近度兜底），潜意识区主排序键为新近度；效果比（`referenced_count / loaded_count`）作为附加加权项叠加，不作为独立排序键。`loaded_count` 较低的新条目获得一个探索配额，保证从未被注入的条目不会被永久饿死。

**Rationale**: 纯效果比排序有两个断裂——(1) `referenced_count` 依赖 `reply_to_user` 工具的 `memory_entries_referenced` 字段，而该工具排在 P3；P1/P2 期间所有条目效果比恒为 0.0，排序退化为空操作，违反 CC-009“每个 phase 独立可验证”。(2) 即使 P3 之后，新沉淀条目 `loaded_count=0` → 效果比 0.0 → 永远排在末尾 → 永远拿不到注入机会 → 永久饿死。复合评分让排序自 P1 起即有意义（效果比项为零时自然退化为 relevance / 新近度），并用探索配额消除冷启动饿死。

**Alternatives considered**:
- 纯效果比排序：P1/P2 无数据来源，且冷启动饿死新条目（见上）。
- 把 `reply_to_user` + `referenced_count` 计量提前到 P1：可让效果比从一开始可用，但仍不解决新条目饿死，且把核心回复机制切换提前会放大 P1 风险。复合评分 + 探索配额是更小、更稳的改动，一次性解决两个问题。

## Decision 12: 猜测生成机制

**Decision**: 猜测区条目由 `BrainBackgroundWorker` 的周期性 prediction generation job 生成，不由单个 Segment 的 `distillation_output` 工具生成。该 job 读取跨 Segment 的近期热区、持久区、归档摘要和已验证猜测反馈，调用后台 LLM 产出带 `verification_checkpoint` 与 `reason` 的 prediction-zone Memory Entries。验证仍由独立 prediction verification job 在 checkpoint 到达后执行。

**Rationale**: 猜测是对用户接下来可能行动的跨时段判断，需要多段记忆和历史校准信号；塞进单 Segment 沉淀会把预测变成局部片段副产物，语义不稳，也与 FR-025 的周期性工作定义冲突。把生成和验证都放进后台 worker 后，P4 的猜测区具有清晰的触发点、输入集合和可观测周期。

**Alternatives considered**:
- Segment 沉淀直接输出 `prediction_zone`：实现路径短，但会让每段对话都尝试预测，成本高且缺少跨 Segment 视角。
- 用户请求时临时生成猜测：让预测变成对话功能，不再是系统自我校准机制。

---

## Decision 13: 技能池、技能列表、技能组合与专员的 UI 边界

**Decision**: 短期保留现有 Skills 与 Compositions 屏幕，不在 `/brain` 中重复实现。现有技能列表继续管理用户教学得到的技能资产；现有技能组合继续管理用户手动组合出的能力集合；`/brain` 技能池面板只管理主助理可授予专员的能力白名单；`/brain/specialists` 只管理固定专员（命名执行体、角色定义、工具白名单、版本历史）。

**Rationale**: 现有前端已经有技能教学、技能列表和技能组合入口。新大脑管理模块需要的是"专员可使用哪些能力"的权限面，而不是另一个技能资产管理面。明确边界可以避免 P5 生成重复屏幕，也降低用户面对多个能力入口时的概念混乱。

**Alternatives considered**:
- 用 `/brain` 技能池面板取代现有技能列表：风险高，需要迁移已有用户路径，超出本 feature。
- 把专员等同于技能组合：两者语义不同；专员是可调度的执行体，技能组合是能力集合。
