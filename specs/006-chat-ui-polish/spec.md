# Feature Specification: 聊天界面体验完善（Chat UI Polish）

**Feature Branch**: `006-chat-ui-polish`
**Created**: 2026-04-28
**Status**: Completed
**Input**: User description: "docs/local/todo 三项聊天 UI 完善：新对话/欢迎界面隐藏免确认 Toggle、压缩后的旧聊天记录可回看、AI 回复 Markdown 渲染"

## Clarifications

### Session 2026-04-28

- Q: 压缩后旧消息是否作为独立归档区展示？ → A: 不做用户可见分区；按原时间线透明并入聊天记录，不显示"已归档"/"已压缩"提示或分隔
- Q: 压缩前旧消息中工具调用与工具结果的展示策略？ → A: 用户视角只回看用户消息与助手对话回复；工具调用与工具结果不作为普通聊天记录展示（未压缩消息的现有工具行为不变）
- Q: 是否需要为 Markdown 渲染或完整历史回看新增可关闭的配置开关？ → A: 默认始终启用 Markdown 渲染与完整历史回看，不新增 `unified_config` 配置
- Q: 压缩前旧消息默认完整展示还是折叠/展开？ → A: 默认完整展示用户消息与助手回复原文，不因内部归档状态做每条消息折叠
- Q: Markdown 链接是否可点击并打开外部目标？ → A: 所有 Markdown 链接只渲染为带样式文本，不提供点击打开
- Q: Markdown 渲染是否仅限 Assistant 还是覆盖共用聊天气泡的 AI 回复？ → A: 只要使用同一聊天气泡组件展示的 AI 回复都渲染，具体 Agent 类型不单独分支
- Q: 完整历史消息读取是否允许新增业务层/Service 接口？ → A: 允许新增最小只读接口暴露压缩前旧消息；不改存储 schema、不改压缩契约
- Q: "免确认" Toggle 在 Agent 启动后是否只在执行中显示？ → A: 对话启动过 Agent 后持续显示；新对话、欢迎页、清空后隐藏
- Q: 极长历史回看的性能验收与加载策略？ → A: ≥1000 条旧消息时首屏加载 ≤2s、滚动/输入单次 UI 阻塞 ≤100ms；初始展示最新 10 条，向上滚动分页加载更早历史
- Q: Markdown 图片语法如何处理？ → A: 允许远程图片渲染，但图片不可点击或触发导航；本地文件、脚本等非远程图片目标安全降级
- Q: Markdown 表格语法是否作为基础支持？ → A: 支持 GitHub 风格 pipe table，并渲染为只读表格

## User Scenarios & Testing *(mandatory)*

### User Story 1 - AI 回复消息以富文本展示 Markdown (Priority: P1)

用户与 Agent 对话时，AI 回复经常包含标题、列表、代码块、加粗、链接、图片、表格等 Markdown 元素。当前聊天气泡按纯文本展示，导致 `**bold**`、`# 标题`、` ```代码``` ` 等记号原样可见，可读性差，长答复尤其难以扫读。本故事要求聊天气泡把 AI 回复中的 Markdown 渲染为相应的富文本结构（标题层级、列表、代码块、加粗/斜体、行内代码、引用、链接、远程图片、只读表格），普通用户看到的是结构化排版，而非原始记号。

**Why this priority**: Markdown 渲染影响**每一条 AI 消息**的阅读体验，是覆盖面最广的体验缺陷；和 P2/P3 完全独立，单独落地即可显著提升日常使用感受。

**Independent Test**: 与 Agent 进行一次普通对话，AI 回复包含至少一个标题、一个有序列表、一个代码块和一处加粗文本；观察气泡显示——标题字号变大、列表带项目符号、代码块以等宽字体并带浅底色块、加粗显示为粗体；不需要打开新对话或触发压缩即可完整验证本故事。

**Acceptance Scenarios**:

1. **Given** AI 回复内容包含 `# 一级标题` 与 `## 二级标题`，**When** 消息出现在聊天气泡，**Then** 用户看到层级化的标题排版，而非原始 `#` 字符
2. **Given** AI 回复包含 ` ``` 代码块 ``` `，**When** 渲染完成，**Then** 代码块以等宽字体、带视觉容器（边框或浅色底）独立展示，原始三个反引号不可见
3. **Given** AI 回复包含 `**重要**` 与 `*斜体*`、行内代码 `` `value` ``、有序/无序列表，**When** 渲染完成，**Then** 各元素都按 Markdown 语义呈现，不出现裸记号
4. **Given** AI 回复内容不包含任何 Markdown 记号（纯文本），**When** 渲染完成，**Then** 气泡显示与今天的纯文本完全一致，不出现多余空白或样式
5. **Given** 用户消息（不是 AI 回复）含有形似 Markdown 的字符（如反引号或星号），**When** 该消息渲染，**Then** 用户消息保持原样不被解析为富文本，避免用户输入被错误格式化
6. **Given** AI 回复包含 Markdown 链接 `[label](https://example.com)`，**When** 消息出现在聊天气泡，**Then** 用户看到带链接视觉样式的 `label` 文本且原始 Markdown 记号不可见；点击该文本不会打开浏览器或触发外部导航
7. **Given** AI 回复包含 Markdown 图片 `![alt](https://example.com/image.png)`，**When** 消息出现在聊天气泡，**Then** 用户看到远程图片内容或加载失败后的 `alt` 降级文本；点击图片不会打开浏览器或触发外部导航
8. **Given** AI 回复包含 GitHub 风格 pipe table，**When** 消息出现在聊天气泡，**Then** 用户看到按行列排版的只读表格，原始 `|` 分隔语法不可见且表格内容不可编辑

### User Story 2 - 压缩后的旧聊天记录仍可回看 (Priority: P2)

长会话触发上下文压缩后，被内部标记为 archived 的早期消息仍存在于持久化存储中，但当前聊天界面只展示压缩后保留的窗口，用户**看不到**自己几小时前与 Agent 的具体对话内容。本故事要求聊天界面从用户视角呈现一条**连续的聊天时间线**：用户滚动历史记录时，能像查看普通聊天记录一样看到压缩前发送过的用户消息与助手回复，不需要理解"归档消息"或"压缩消息"等内部概念；界面不得把这些旧消息做成单独区域、不得显示"已归档"/"已压缩"标签、不得用分隔条或特殊底色把旧消息与当前消息分区。

**Why this priority**: 缺失对历史对话的可见性会让用户对系统状态产生强烈不信任；但只有触发过压缩的长会话用户会感受到，覆盖面比 P1 窄，因此排在 P1 之后。

**Independent Test**: 启动一次会话，连续对话直至触发上下文压缩（或人为触发一次压缩）→ 打开会话时初始看到最近 10 条用户消息与助手对话回复 → 向上滚动聊天框逐页加载更早历史 → 应能看到压缩前的用户消息与助手对话回复按原时间顺序出现在同一条聊天记录中（按发送方区分，但不出现归档/压缩分区或标签，工具调用与工具结果不作为普通聊天记录展示）；本故事的验证不依赖 P1 的 Markdown 渲染，也不依赖 P3 的 Toggle 行为。

**Acceptance Scenarios**:

1. **Given** 当前会话已发生过一次压缩（旧消息仍存在于存储中），**When** 用户打开/切换到该会话并滚动到聊天框顶部，**Then** 用户看到压缩前的用户消息与助手对话回复按原时间顺序出现在同一条聊天记录中
2. **Given** 聊天框同时包含压缩前旧消息和当前未压缩消息，**When** 用户视觉浏览，**Then** 这些消息以相同聊天气泡样式连续呈现，不出现"归档"、"压缩"、分隔条、特殊底色或其它分区提示
3. **Given** 压缩前旧消息中包含工具调用 / 工具结果配对，**When** 渲染完整聊天记录，**Then** 工具调用与工具结果不作为普通聊天记录展示；未压缩消息的现有工具展示行为不变
4. **Given** 会话从未发生过压缩，**When** 用户打开聊天框，**Then** 聊天记录展示与今天完全一致（不引入空容器、状态提示或多余分隔）
5. **Given** 可回看的旧消息体积很大（例如压缩前旧消息总长度超过若干屏），**When** 用户打开会话并滚动浏览，**Then** 初始只展示最近 10 条用户消息与助手对话回复，向上滚动时分页加载更早历史；滚动与输入保持流畅，不阻塞当前对话交互

### User Story 3 - 新对话/欢迎界面不展示"免确认"Toggle (Priority: P3)

004-auth-toast 引入了对话窗口顶栏的"免确认" Toggle，用于已启动 Agent 的具体对话会话。但目前在**新对话入口**和**欢迎界面**上同样展示了该 Toggle——这两个场景下没有正在跑的 Agent，开关不会作用于任何具体请求，反而误导用户以为它是全局或预设性的开关。本故事要求"免确认" Toggle 仅在**当前对话已启动过 Agent 会话后**可见，并在该对话后续期间持续可见；欢迎界面、新建会话起始态与清空后的会话不展示该控件。

**Why this priority**: 这是 UI 误导而非功能性故障——Toggle 在错误位置被点击也不会影响任何工具执行（因为没有 Agent 在跑），但视觉上让用户误解了开关的作用域。优先级低于影响实际可读性的 P1 和影响数据可见性的 P2。

**Independent Test**: 启动应用 → 停留在欢迎界面，观察顶栏：不应出现"免确认" Toggle；点击"新对话"进入空会话起始态：不应出现 Toggle；当用户发送第一条消息（或以其他方式启动 Agent 会话）后，Toggle 应可见，并在本轮回复结束后仍保持可见。无需 Markdown 渲染或完整历史回看支持即可独立验证。

**Acceptance Scenarios**:

1. **Given** 应用启动后停留在欢迎界面（尚未进入任何会话），**When** 用户查看主窗口顶栏区域，**Then** "免确认" Toggle 不可见
2. **Given** 用户从历史会话切换到"新对话"且尚未发送消息，**When** 用户查看对话窗口顶栏，**Then** "免确认" Toggle 不可见
3. **Given** 用户在新对话中发送第一条消息触发 Agent 启动，**When** 当前对话进入已启动 Agent 会话状态，**Then** "免确认" Toggle 显示在顶栏，并在该轮回复结束后仍持续可见，行为与 004-auth-toast 中描述一致
4. **Given** 用户从一个运行中的会话切换回欢迎界面，**When** 用户查看顶栏，**Then** Toggle 重新隐藏，不留残影或失效控件

### Edge Cases

- **Markdown 渲染中包含 HTML 或脚本片段**：AI 回复若混入 `<script>` 或 raw HTML，渲染层 MUST 不执行任何脚本、不直接渲染裸 HTML 标签，避免引入 XSS 风险；未识别记号 MUST 安全降级为纯文本
- **Markdown 链接目标**：AI 回复中的 Markdown 链接 MUST 只作为带样式文本展示，点击时 MUST NOT 打开浏览器、访问本地文件、执行脚本或触发任何外部导航
- **Markdown 图片目标**：AI 回复中的 Markdown 图片 MAY 渲染远程 `http(s)` 图片资源；图片 MUST NOT 可点击或触发外部导航；本地文件、脚本协议、裸 HTML 图片标签或其它非远程图片目标 MUST 安全降级为 alt 文本或纯文本
- **Markdown 渲染流式输出**：AI 回复以流式逐字到达气泡时，未闭合的 Markdown 记号（半截代码块、未结束的加粗）MUST 在到达完整记号前以"安全降级"方式展示，不出现样式残影或抖动
- **压缩边界与完整聊天记录冲突**：完整聊天记录渲染 MUST 与现有 `_adjust_boundary_for_tool_pairs` 等压缩边界规则保持一致；工具调用/结果等内部消息不能以孤立、半截或重复形态出现在用户聊天记录中
- **压缩摘要不可见**：`role="summary"` / `message_type="compressed"` 等用于上下文压缩的内部摘要 MUST NOT 作为普通聊天消息展示给用户
- **旧消息与"清空对话"的关系**：当用户主动清空当前会话或开启新对话时，旧消息 MUST 一并消失，不在新会话中残留
- **Toggle 在会话生命周期边界的瞬态**：用户在欢迎界面、新对话起始态、已启动 Agent 的对话、清空后的会话之间切换时，Toggle 的可见性状态 MUST 与目标视图严格对齐，不能出现"先短暂可见再消失"或"应可见却未出现"的瞬态
- **大规模旧消息的性能边界**：极长会话累计大量旧消息时，完整聊天记录 MUST 采用按需分页加载；初始展示最近 10 条用户消息与助手对话回复，用户向上滚动时再拉取更早历史
- **现有 `IntentConfirmationUI` / `ToolExecutionDialog` / 普通 Toast** 不在本 feature 改动范围
- **顶栏其它控件不受影响**：隐藏 Toggle MUST 仅作用于"免确认" Toggle 一个控件，顶栏其余区域（标题、状态、其他按钮）布局不变形

## Requirements *(mandatory)*

### Functional Requirements

#### Story 1 — AI 回复 Markdown 渲染

- **FR-001**: AI 回复在聊天气泡中展示时，系统 MUST 将其按 Markdown 语法解析并渲染为对应的富文本结构（至少包含标题 `#`–`######`、有序列表、无序列表、加粗、斜体、行内代码、代码块、引用 `>`、链接样式文本、远程图片、GitHub 风格 pipe table、分隔线）
- **FR-002**: 用户消息（非 AI 回复）MUST 不进行 Markdown 解析，保持纯文本展示，避免误把用户输入的反引号、星号当作格式化记号
- **FR-003**: 渲染层 MUST 安全处理 AI 回复中的潜在脚本与裸 HTML：MUST NOT 执行任何脚本，MUST NOT 直接渲染未声明的 HTML 标签；未支持或不安全的内容 MUST 降级为纯文本
- **FR-004**: AI 回复在流式输出过程中，未闭合的 Markdown 记号 MUST 不导致明显的样式抖动或大段重排；最终消息收敛后渲染结果 MUST 与一次性传入的渲染结果在视觉上一致
- **FR-005**: 不含任何 Markdown 记号的纯文本 AI 回复 MUST 在视觉上与变更前一致，不引入额外间距、字号或边框
- **FR-006**: Markdown 链接 MUST 只渲染为带链接视觉样式的文本，MUST NOT 提供点击打开、浏览器跳转、本地文件访问或脚本执行能力；Markdown 图片 MAY 渲染远程 `http(s)` 图片资源，但图片 MUST NOT 可点击或触发导航，本地文件、脚本协议和非远程图片目标 MUST 安全降级

#### Story 2 — 压缩后的旧聊天记录可回看

- **FR-007**: 当前会话存在已被内部归档（压缩前移出活跃上下文）的用户消息或助手对话回复时，聊天框 MUST 将这些旧消息与当前未压缩消息按原 `sequence` 合并为同一条连续聊天时间线展示
- **FR-008**: UI MUST NOT 把内部归档状态做成用户可见概念；MUST NOT 显示独立归档区、"已归档"、"已压缩"、分隔条、特殊底色或其它区分旧消息/当前消息的视觉提示
- **FR-009**: 完整聊天时间线 MUST 按时间顺序、按发送方（用户 / 助手）渲染用户消息与助手对话回复，遵循与现有聊天气泡一致的发送方区分规则
- **FR-010**: 工具调用、工具结果和压缩摘要等内部消息 MUST NOT 作为普通聊天记录展示；未压缩消息的现有工具展示行为不变
- **FR-011**: 当会话从未发生过压缩时，聊天框 MUST 与今天的历史记录展示一致，不引入空容器、状态提示或多余分隔
- **FR-012**: 压缩前旧消息中的用户消息与助手回复 MUST 默认完整展示原文，不因内部归档状态做每条消息折叠或点击展开交互
- **FR-013**: 用户开启新对话或清空当前会话时，旧消息 MUST 立即清空，MUST NOT 在新会话中残留旧会话内容
- **FR-014**: 聊天框打开存在大量历史的会话时，系统 MUST 初始展示最近 10 条用户消息与助手对话回复，并在用户向上滚动时分页加载更早历史；分页加载 MUST 保持同一连续时间线，不显示归档/压缩分区

#### Story 3 — 新对话/欢迎界面隐藏免确认 Toggle

- **FR-015**: 应用停留在欢迎界面（未进入任何具体会话）时，对话窗口顶栏 MUST NOT 展示"免确认" Toggle
- **FR-016**: 用户进入新对话起始态（已选定"新对话"但尚未启动 Agent 会话）时，对话窗口顶栏 MUST NOT 展示"免确认" Toggle
- **FR-017**: 一旦当前对话已启动过 Agent 会话，对话窗口顶栏 MUST 持续展示"免确认" Toggle，直到用户进入新对话起始态、欢迎界面或清空当前会话；其行为 MUST 完全沿用 004-auth-toast 中定义的同步语义（与浮层"全部允许"双向同步、新对话复位等）
- **FR-018**: Toggle 显示/隐藏切换 MUST 不破坏顶栏其余控件的位置与样式，MUST NOT 引入闪烁、布局抖动或残留失效控件

### Key Entities

- **AI Reply Message**：通过同一聊天气泡组件展示的非用户 AI 对话回复；其内容字段可能包含 Markdown 文本，渲染层负责将其转换为富文本展示；该实体本身的存储结构/字段由现有会话模型决定，本 feature 不改写存储，也不按具体 Agent 类型分支
- **Historical Chat Message（历史聊天消息）**：用户视角下属于当前会话聊天历史的一条用户消息或助手对话回复；其中一部分可能在存储中被内部标记为 archived，但该内部状态不应改变其用户可见形态
- **Agent Session State（运行态标识）**：决定"免确认" Toggle 是否应可见的 UI 状态——应能区分"无会话/欢迎"、"新对话起始态"、"已启动过 Agent 的具体会话"、"清空后的会话"等状态

### Constraints & Compatibility

- **CC-001**: 现有压缩边界处理（`CompressionHandler._adjust_boundary_for_tool_pairs`）与孤立 tool 结果兜底（`_cleanup_orphan_tool_results`）的行为 MUST 不被本 feature 改动；完整历史回看只读取现有数据，不改变压缩输入/输出契约
- **CC-002**: 004-auth-toast 中"免确认" Toggle 与浮层"全部允许"的双向同步、新对话复位等语义 MUST 在本 feature 后保持完全一致；本 feature 仅控制控件的**可见性**，不变更其行为
- **CC-003**: 聊天气泡的 Markdown 渲染 MUST NOT 改变现有用户消息渲染路径，MUST NOT 影响普通 Toast、确认浮层、`IntentConfirmationUI`、`ToolExecutionDialog` 等其他 UI 组件
- **CC-004**: 渲染层 MUST 不执行 AI 回复中的脚本或裸 HTML，避免引入 XSS / 注入风险
- **CC-005**: 现有跨线程信号、Worker 阻塞确认机制（004-auth-toast 引入）MUST 不被本 feature 改动
- **CC-006**: 若现有 UI 可访问接口不能直接提供完整历史消息，允许在业务层 / Service 增加最小只读接口暴露压缩前旧消息；UI MUST NOT 直接调用 Repository，且该接口 MUST NOT 改变存储 schema、压缩输入/输出契约或现有恢复逻辑

## Architecture Impact *(Mexemplar-specific)*

### Layer Impact

- [x] **UI** (`src/ui/`) — 聊天气泡新增 Markdown 渲染、聊天容器按原时间线展示完整聊天记录、对话窗口顶栏对"免确认" Toggle 加可见性控制
- [x] **Business** — 旧消息读取优先复用现有业务 / 上下文管理接口；如现有接口不足，可新增最小只读 Service / 业务接口暴露完整历史消息
- [ ] **Execution** — 不受影响
- [x] **Data** — 受只读 Repository 查询接口影响；不新增表、列、迁移，不改变 SQLite schema
- [ ] **Recording** — 不受影响
- [ ] **Utils** — 不受影响

### Agent Impact

- 受影响的 Agent：所有通过同一聊天气泡组件展示的非用户 AI 对话回复；实现不按 Assistant / PM / Programmer / Trial 等具体 Agent 类型分支
- 工具/handler：无变更
- System prompt：无变更
- Orchestrator dispatch：无变更

### Data Store Impact

- SQLite：新增或调整只读 Repository 查询路径读取压缩前旧消息；不新增表、列、迁移，不改变 schema。DuckDB：无变更
- Config (`unified_config`)：不新增配置项；Markdown 渲染与完整历史回看默认始终启用

### Event Impact

- 新增/变更事件：本 feature 以 UI 内部信号 / 现有会话状态读取实现，不引入跨模块 blinker 事件

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一次包含标题、列表、代码块、加粗、行内代码、链接、远程图片、GitHub 风格 pipe table 的 AI 回复，**100%** 元素以富文本形态展示，原始 Markdown 记号在用户视图中不可见，表格以只读行列结构展示，且链接/图片点击 **0** 次触发外部导航
- **SC-002**: 不含 Markdown 记号的纯文本 AI 回复，渲染前后视觉对比无可识别差异（字号、行高、间距一致）
- **SC-003**: 对一段持续到触发压缩的长会话，聊天框 **100%** 展示压缩前旧用户消息与助手对话回复，并与当前未压缩消息按原时间顺序组成同一条连续聊天记录；**0** 条工具调用/工具结果/压缩摘要作为普通聊天消息可见
- **SC-004**: 发生过压缩和从未压缩的会话都不显示"归档"、"已压缩"或任何内部状态提示；用户只看到连续聊天记录
- **SC-005**: 在欢迎界面、新对话起始态、已启动过 Agent 的具体会话、清空后的会话四类状态下，"免确认" Toggle 的可见性正确率 **100%**（应可见时 100% 出现，应隐藏时 100% 不出现）
- **SC-006**: 切换状态（欢迎 ↔ 已启动 Agent 的会话、已启动 Agent 的会话 ↔ 新对话、已启动 Agent 的会话 ↔ 清空后会话）时，Toggle 显隐切换帧内完成，不出现视觉闪烁、布局抖动或残留控件
- **SC-007**: 极长会话（≥ 1000 条旧消息）完整历史回看时，聊天框初始展示最近 10 条用户消息与助手对话回复；首屏加载耗时 ≤2s，滚动或输入期间单次 UI 阻塞 ≤100ms，向上滚动可分页拉取更早历史
- **SC-008**: AI 回复包含潜在脚本/裸 HTML 片段或非远程图片目标时，**0** 次脚本被执行，**0** 次裸 HTML 标签被原样渲染为活动元素，**0** 次本地文件或脚本协议图片被加载

## Assumptions

- AI 回复内容由 Agent 层产出，其文本中允许出现 Markdown 记号（无需 Agent 端额外约定即可被 UI 端识别）
- "已启动过 Agent 的具体会话" / "欢迎界面" / "新对话起始态" / "清空后的会话"四类 UI 状态可由现有视图栈或会话存在性判断，无需新增专门状态字段
- 004-auth-toast 中"免确认" Toggle 的内部状态、与浮层的双向同步、新对话复位行为继续生效，且复位入口与本 feature 的"新对话"边界一致
- UI 端可在内部消费"已归档/压缩前旧消息"与"当前未压缩消息"的区分来合并数据，但该区分不得暴露为用户可见分区；若现有 `ContextManager` 与会话存储接口无法直接暴露完整历史消息，可新增最小只读业务层 / Service 接口，但不改存储 schema 或压缩契约
- 压缩前旧消息与当前未压缩消息使用同一渲染管线（即旧 AI 回复也应享有 Story 1 的 Markdown 渲染）；旧用户消息同样保持纯文本
- 用户消息保持纯文本展示与今天行为一致；Markdown 渲染仅作用于 AI 回复
- 渲染库选型与具体实现方案在 `/speckit.plan` 阶段决定；本 spec 不绑定具体技术栈
- Markdown 渲染与完整历史回看是默认体验能力，不提供用户可关闭配置
- 压缩前旧消息默认完整展示用户消息与助手回复原文，不因内部归档状态提供每条消息折叠/展开交互
- 极长会话默认以最近 10 条用户消息与助手回复作为初始窗口，向上滚动分页加载更早历史；分页加载不改变历史消息的原文展示规则
- Markdown 链接只作为带样式文本展示，不提供点击打开外部目标的能力
- Markdown 图片允许渲染远程 `http(s)` 图片资源，但不提供点击打开外部目标的能力；图片加载失败或目标不安全时显示 alt 文本或纯文本
- Markdown 表格支持 GitHub 风格 pipe table，并渲染为只读表格
- Markdown 渲染跟随聊天气泡组件能力，不按具体 Agent 类型分支；用户消息和工具消息仍不解析
