## User Scenarios & Testing *(mandatory)*

调度中心给现有办公助理加三样东西：**三种触发方式**（立即 / 一次性定时 / 周期）、**执行记录**（用户可看的历史）、**完成通知**（Toast + 桌面通知）。它**不是新系统**，是现有任务调度（task_collaboration）的升级：到点开一个主助理会话让它全权处理，跑完喊用户、记一笔。

### User Story 1 - 立即触发：现在就帮我做一件事 (Priority: P1)

用户在对话里说「这条事现在就帮我做」，主助理理解后创建一个**立即**任务，经确认卡核对后立刻点燃一个无人值守的主助理会话去执行；做完后用户收到通知，能在调度中心看到这次执行记录。

**Why this priority**: 这是「定时唤醒 agent」最小可独立交付的闭环——触发 → 执行 → 通知 → 记账——不依赖周期 / 待办等任何后续故事，单独成立即可验证整套链路通不通。

**Independent Test**: 在对话中提一个立即任务，确认后观察会话被点燃、执行、完成通知送达、历史出现一条 succeeded 记录。

**Acceptance Scenarios**:

1. **Given** 用户在对话中提出一个明确的立即任务，**When** 主助理调用创建工具，**Then** 弹出确认卡展示标题 / 指令 / 「立即执行」，用户确认后任务落库并马上触发一个 scheduled 会话。
2. **Given** 一个立即任务已确认，**When** scheduled 会话执行完成（会话静默且全部成功），**Then** 用户收到完成通知（Toast + 桌面通知，app 运行时），调度中心历史新增一条 succeeded 记录。
3. **Given** 用户在确认卡上点取消 / 超时 / 停止，**When** 任意一种放弃发生，**Then** 任务不落库（fail-closed，不产生悬空任务）。

---

### User Story 2 - 一次性定时：到点再做 (Priority: P1)

用户说「明天下午 3 点整理本周会议纪要」，主助理解析时间并创建**一次性定时**任务，确认卡核对（防「9 点」听成 21 点），到点自动触发执行并通知。

**Why this priority**: 「定时」是本功能相对立即的核心增量，与 US1 同属最小闭环的触发维度，验证「到点唤醒」这条时间轴。

**Independent Test**: 创建一个 1–2 分钟后到点的一次性任务，等到点后确认会话被触发、执行、通知与历史。

**Acceptance Scenarios**:

1. **Given** 用户给出一个未来时刻的一次性任务，**When** 主助理解析并展示确认卡，**Then** 卡片用人类可读方式展示时刻与指令，确认后落库的下次触发时刻与展示一致。
2. **Given** 一次性任务到达触发时刻且 app 运行中，**When** 调度中心到点，**Then** 触发一次 scheduled 会话；执行完成后通知用户并记历史。
3. **Given** 一次性任务已成功触发一次，**When** 执行结束，**Then** 任务进入终态，不再重复触发。

---

### User Story 3 - 周期任务：按规律重复做 (Priority: P2)

用户说「每天 9 点查一下竞品价格」或「每周一 8 点整理周报」，创建**周期**任务，按规律滚动触发；错过补跑、撞上次未完成则跳过。

**Why this priority**: 周期是「自动化中枢」的价值放大器，但建立在 US1/US2 的单次触发链路之上，故 P2。它额外带来 misfire / 重入两个调度特有问题域。

**Independent Test**: 创建一个「每隔 1 分钟」的周期任务，观察连续两次滚动触发；构造上次未完成，观察本次被跳过并记 skipped。

**Acceptance Scenarios**:

1. **Given** 一个活跃周期任务，**When** 每个周期时刻到达，**Then** 触发一次 scheduled 会话，结束后下次触发时刻按规律滚动到下一个未来时点。
2. **Given** app 未运行导致错过若干个周期，**When** app 启动恢复，**Then** 只补跑最近一次错过的触发，然后滚动到下一个未来时点（不补跑全部历史）。
3. **Given** 到点时上一次触发仍未结束（会话未静默），**When** 本次触发时刻到达，**Then** 本次跳过、历史记一条 skipped（不堆积并发）。

### User Story 4 - 从待办接入：把待办变成 AI 替我做的事 (Priority: P2)

用户在待办条目上发起动作（接入语义复用既有确认卡），指令框预填待办标题 + 描述、**允许当场补全**（待办标题通常太短不足以当指令），确认后建立一个**一次性**任务；完成后待办显示「上次执行」但不自动划掉。

**Why this priority**: 待办是用户最初表述的触发源，但澄清后明确它是「触发源之一」而非待办增强。它复用 US2 的一次性链路，额外验证「不改待办表」的边界。

**Independent Test**: 从一条真实待办发起接入，编辑指令后确认，等执行完成，确认待办未被自动改状态、只显示上次执行结果。

**Acceptance Scenarios**:

1. **Given** 用户在某条待办上发起接入动作，**When** 确认卡弹出，**Then** 指令框预填该待办的标题 + 描述，且用户可以当场编辑 / 补全；任务类型只能是「一次性定时」。
2. **Given** 一个待办来源的一次性任务已执行完成，**When** 用户回到待办，**Then** 待办显示「上次执行：时间 + 成功 / 失败」，但**待办本身不被自动标记完成**（判断权留给用户）。
3. **Given** 待办来源任务正在配置，**When** 用户尝试把它设为周期任务，**Then** 被拒绝（待办来源恒为一次性）。

---

### User Story 5 - 无人值守安全与人工接管 (Priority: P2)

scheduled 会话在用户不在场时跑：未授权的高危动作立即按拒绝处理（不空等超时）、半路反问时通知用户接管、失败时用户能从历史进入会话接着聊。用户可为单个任务显式开启「免确认」（默认关闭），开启后该任务的 scheduled 会话内高危动作自动放行。

**Why this priority**: 「让 AI 在人不在时自主干活」是授权面最大的点，必须有确定性的 fail-closed 边界与人工接管通道，否则功能不可安全上线。它独立于具体触发类型。

**Independent Test**: 创建一个会触发高危动作的 scheduled 任务（未开免确认），触发后确认高危动作被立即拒绝并在汇报中列出；再创建一个反问场景，确认 run 停在「需接管」并通知。

**Acceptance Scenarios**:

1. **Given** 一个**未开启免确认**的 scheduled 任务触发，**When** 其会话执行中遇到高危确认，**Then** 该高危动作立即按拒绝处理（不等默认超时），任务继续其余部分并在汇报中列出被跳过的动作。
2. **Given** 一个 scheduled 会话需要用户回答才能继续，**When** 主助理反问，**Then** 本次 run 进入「需接管」状态并发通知；用户从调度中心历史进入该会话接着聊后任务继续推进。
3. **Given** 一个**用户显式开启免确认**的任务（仅创建确认卡勾选或详情页开关），**When** 其 scheduled 会话遇高危动作，**Then** 自动放行（仅影响该任务、仅 scheduled 会话），且决策记入既有确认审计日志；其他用户正在聊的会话不受任何影响。

### User Story 6 - 调度中心管理屏：一览、审视、回收 (Priority: P2)

用户有一个「调度中心」主屏，统一看到所有定时任务（周期 / 一次性 / 待办来源）及其状态、下次触发、上次结果；开启免确认的任务在**列表层一眼可见**并可随时回收；空态有创建指引；scheduled 会话不混进普通聊天屏，统一进调度中心历史、能点进去接着聊。

**Why this priority**: 管理与可见性是「埋雷式」定时任务的可控性前提——尤其免确认授权清单必须像系统权限总览一样可审视。它承载所有前序故事的观测与回收入口。

**Independent Test**: 创建若干任务（含一个开免确认的），打开调度中心确认列表信息齐全、免确认任务醒目；把 scheduled 会话与聊天屏对照确认隔离；从历史点进一个会话确认可继续对话。

**Acceptance Scenarios**:

1. **Given** 存在多个不同类型 / 状态的任务，**When** 用户打开调度中心，**Then** 列表展示每条任务的标题、状态、调度描述、下次触发时刻、上次执行结果；未跑过的标「还没跑过」。
2. **Given** 存在开启了免确认的任务，**When** 用户查看列表，**Then** 这些任务在列表层带醒目标记；用户可在任务详情页关闭该开关收回授权。
3. **Given** 调度中心没有任何任务，**When** 用户打开空面板，**Then** 面板给出创建指引（引导去对话创建并附例句），不让用户面对空白无从下手。
4. **Given** 一个 scheduled 会话存在，**When** 用户看 AI Assistant 聊天屏，**Then** 该会话不出现在聊天屏列表；它只在调度中心历史可见，点进去能查看详情并接着聊。

### Edge Cases

- **app 未运行时过点**：既不触发也不通知；重启后按 misfire 策略补跑最近一次（一次性同样补跑，用户显式交代的事不丢）。须向用户说明该预期。
- **暂停期间过点**：不补跑。恢复时一次性已过点置 expired；周期直接滚动到下一个未来时点。
- **同任务重入**：上次触发未结束、本次又到点 → 本次跳过、记 skipped（不堆积）。
- **待办源消失**：引用的待办被删除或被用户手动标记完成 → 任务作废（expired 并标原因），worker 到点与「现在跑一次」均不触发；Repository 暂时读取失败不得误判为删除。
- **完成判定误报 / 漏报**：首轮主助理回合返回 completed ≠ 任务完成（委派 durable
  非阻塞、后台仍在跑）；含失败 / 取消的任务图不被当成全成功。须等会话真正静默
  （无活跃主助理 worker、无未消费回流、关联任务图全终态）才报完成。
- **跨会话真并发**：用户正在聊的会话与 scheduled 会话可同时各跑各的——per-task 免确认与全局进程状态必须严格隔离，互不波及。
- **高危动作误授权**：免确认只能由用户显式 UI 操作开启，LLM 无法经工具参数或对话话术自行开启 / 诱导设置。
- **时间解析歧义**：「9 点」「3 点」类歧义须在确认卡用人话展示并等用户确认，避免跑到点才发现理解错。

## Requirements *(mandatory)*

### Functional Requirements

**触发与会话**

- **FR-001**: 系统 MUST 支持三种触发方式——立即（对任意任务「现在跑一次」的动作）、一次性定时（到点跑一次）、周期（按规律滚动）。其中「立即」是动作而非任务类型，使「对周期任务现在跑一次」可表达。
- **FR-002**: 定时 / 立即触发 MUST 通过新建一个标记为 scheduled 的主助理会话来执行——把任务指令作为一条消息投递给它，主助理像处理用户消息一样全权处理（判复杂度、拆任务图、协作、回流），调度中心**不**自行派执行体、**不**拆任务、**不**决定派谁。
- **FR-003**: scheduled 会话投递时 MUST 附带无人值守提示（引导主助理自主干完、少触发需用户介入的动作）；该提示为 advisory，fail-closed 由机制硬保证。
- **FR-004**: 触发后系统 MUST 复用现有任务协作内核推进执行（durable 执行、lease 恢复、裁定回流、通信通道、任务图调度），本特性 MUST NOT 改变该内核的执行 / 通信 / 恢复语义；仅允许 CC-003 登记的行为保持型公共图终态函数抽取。

**创建与确认**

- **FR-005**: 创建定时任务的唯一入口 MUST 是主助理在对话中调用专用工具（立即 / 一次性 / 周期统一弹确认卡）；调度中心 UI 本身不持有创建能力。
- **FR-006**: 所有定时任务创建 MUST 经用户确认卡落地——核对标题 / 人类可读时间 / 指令原文、提供取消入口；用户确认后才落库，超时 / 取消 / 停止均不创建。
- **FR-007**: 确认卡 MUST 让用户显式勾选该任务是否开启「无人值守免确认」（默认不勾，附风险说明）；该开关事后可在任务详情页修改。

**周期与调度**

- **FR-008**: 第一批周期支持 MUST 至少包含：每隔 N（分钟 / 小时）、每天某时、每周某天某时、工作日；不引入完整 cron / rrule。
- **FR-009**: 调度 MUST 由一个值守机制承担（周期扫描「下次触发时刻 ≤ 当前 ∧ 任务活跃」+ 事件唤醒响应立即触发），在桌面 sidecar 启动时拉起、关闭时停止。
- **FR-010**: 错过触发（app 未运行等）MUST 补跑最近一次，然后滚动到下一个未来时点；暂停期间过点的不补跑（一次性置 expired，周期滚动）。
- **FR-011**: 到点时若上一次触发仍未完成，本次 MUST 跳过并记 skipped；不排队、
  不并行同任务。该约束 MUST 能抵御 worker / fire-now 并发触发，不能只靠先读后写。

**完成判定与通知**

- **FR-012**: 「完成」MUST 定义为 scheduled 会话静默（无活跃主助理 worker、
  无未消费回流、关联任务图全终态）；不得在首轮主助理回合 completed 即报完成、
  不得只等任务图根完成（防漏报失败终态）。runtime / 回流 / 图状态查询未知时必须
  fail-closed 延后，不能当作“无图且成功”。
- **FR-013**: 静默且全成功 → 标 succeeded 并发完成通知；静默且含失败 → 标 failed 并发带原因的通知；run 需用户回答 → 标「需接管」并发接管通知（不标失败、不悬空）；skipped 不通知只记历史。
- **FR-014**: 通知 MUST 含应用内 Toast 与桌面系统通知（app 运行时）；app 未运行时既不触发也不通知。

**待办接入**

- **FR-015**: 待办作为触发源之一 MUST 以外部引用方式接入（引用待办 id），创建时取该待办标题 + 描述作为可编辑指令底稿，并把用户在确认卡核定后的实际指令独立持久化；每次触发前 MUST 只读校验待办仍存在且未完成，执行核定后的指令；**不得修改待办表结构**。
- **FR-016**: 待办来源任务 MUST 恒为一次性（不支持周期）；待办被删除或手动标记完成时，对应任务作废不再触发。
- **FR-017**: 待办来源任务执行完成后 MUST NOT 自动修改待办状态；只在待办侧展示「上次执行」结果，是否标记待办完成由用户决定（结果页可提供调用既有待办接口的「标记完成」按钮）。

**管理与可见性**

- **FR-018**: 系统 MUST 提供调度中心主屏，统一管理所有任务：列表展示标题 / 状态 / 调度描述 / 下次触发 / 上次结果，行内支持暂停 / 启用 / 现在跑一次 / 删除。
- **FR-019**: 开启免确认的任务 MUST 在**列表层**带醒目标记（可一览、可回收），详情页提供事后开关。
- **FR-020**: 调度中心空态 MUST 提供创建指引（引导去对话创建并给例句）。
- **FR-021**: scheduled 会话 MUST 从 AI Assistant 聊天屏列表排除，只在调度中心历史可见；历史条目点进去 MUST 能查看会话详情并接着对话。
- **FR-022**: 任务删除 MUST 走软删，历史 run 与关联会话保留可追溯。

**安全与边界**

- **FR-023**: 无人值守 MUST fail-closed：未开启免确认任务的 scheduled 会话中，高危确认立即按拒绝处理（不等默认超时）；结构化澄清与反问等待既有超时 fail-closed 托底，反问等待转「需接管」通知。
- **FR-024**: per-task 免确认 MUST 满足四重限定——仅 scheduled 会话 / 仅该任务 / 默认关闭 / 只能由用户显式 UI 操作开启；且 MUST NOT 改变进程级全局免确认状态、MUST NOT 影响其他用户会话。
- **FR-025**: `unattended_auto_approve` 字段 MUST NOT 作为创建 / 更新定时任务工具的参数存在（LLM 无法经工具调用自行开启）；只能经确认卡勾选或详情页开关写入。

### Key Entities *(include if feature involves data)*

- **Scheduled Task（定时任务 / 派工单）**：用户埋下的一条「到点让 AI 做某事」的指令。关键属性：来源（直接指令文本 / 引用待办）、确认卡核定后的实际执行指令、标题、触发类型（一次性 / 周期）及调度参数、状态（活跃 / 暂停 / 完成 / 过期）、是否开启无人值守免确认、下次 / 上次触发时刻。删除为软删。
- **Scheduled Task Run（执行记录）**：一次触发产生的一条执行账目。关键属性：关联的定时任务与会话、起止时间、状态（运行中 / 成功 / 失败 / 需接管 / 跳过）、汇报摘要。会话细节复用既有会话消息，不重复存储。
- **Session 来源（会话来源标记）**：会话新增「来源」属性区分「用户手动开」与「定时任务触发」；后者额外关联触发它的定时任务。

### Constraints & Compatibility *(include when relevant)*

- **CC-001**: 待办接入 MUST NOT 修改 `user_todos` 表结构（门卫测试守住）。
- **CC-002**: 待办来源任务（`source_type=todo`）MUST 恒为一次性，不支持周期（门卫测试守住），以保住待办「完成」语义不被周期条目污染。
- **CC-003**: 本特性 MUST NOT 修改现有任务协作内核的执行 / 通信 / 恢复决策，
  保持零回归；定时 / 立即触发一律经「新建主助理会话」复用既有路径。只允许两处
  行为保持型观察接缝：把既有两处图终态判定抽到
  `task_collaboration/graph_terminal.py`，以及 graph scheduler 首次全终态时额外 emit
  含 `session_id` 的内部观察事件；“首次”去重只约束 observer emit，不得门控 root
  收口或父侧 reentry，二者瞬时失败后必须保持可重试；观察者失败不得阻断既有父侧
  回流。内核 MUST NOT 反向依赖 scheduling。
- **CC-004**: 无人值守 MUST fail-closed（FR-023）；不得退回 prompt 软约束或乐观等待超时。
- **CC-005**: per-task 免确认属**受控例外**——现行全局硬规则要求「免确认只允许是进程会话级内存状态、不得持久化」。本特性持久化免确认是用户显式拍板的例外，转正式 spec 时 MUST 同步在 constitution / AI 入口文档落例外条款，四重限定（FR-024）+ 工具参数门卫（FR-025）由架构门卫测试守住，不得静默违反。
- **CC-006**: scheduled 会话第一批 MUST NOT 参与 brain Segment 沉淀（周期任务大量重复会话会污染大脑记忆与招募信号）。
- **CC-007**: 创建 / 更新定时任务的工具 MUST 仅对主助理可用（对话入口）；调度中心本身不持有创建能力。
- **CC-008**: 面向前端的事件 MUST 经 UI Event Registry 注册为 typed envelope 发出，不允许裸事件名或未注册 payload 走 SSE；后端内部跨模块通知走 blinker。
- **CC-009**: 配置 / 凭证 MUST 走 `UnifiedConfigManager`；不得硬编码、不得新增明文 secret。
- **CC-010**: 桌面通知插件 capabilities MUST 审慎授权，遵循最小权限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户能用一句自然语言在对话中创建定时任务，确认卡所展示的时间 / 指令与落库后实际触发行为一致（时间解析零歧义，经确认卡核对）。
- **SC-002**: 立即、一次性、周期三种触发都按设定时机执行——立即几乎瞬时、一次性到点、周期按规律滚动；可经短周期（如每隔 1 分钟）任务在分钟级验证。
- **SC-003**: 任务执行完成后用户在 app 运行时收到通知，且通知能区分成功 / 失败 / 需接管三种结局；skipped 不打扰用户。
- **SC-004**: 用户能在调度中心一览全部任务的状态 / 下次触发 / 上次结果；开启免确认的任务在列表层一眼可见且可一键回收。
- **SC-005**: app 关闭期间错过的任务在重启后被补跑最近一次；用户显式交代的一次性任务不因 app 未运行而丢失。
- **SC-006**: 任何未由用户显式授权的 scheduled 任务，其高危动作都不会在用户不在场时被执行（立即拒绝），且该拒绝不会污染用户正在进行的其他会话。
- **SC-007**: 失败或需用户接管的任务，用户能从调度中心历史进入对应会话、通过继续沟通使其完成或返工（人工接管是第一批唯一的纠偏与重试通道）。
- **SC-008**: 从待办接入的任务执行不污染待办列表——不自动改待办状态、不引入周期条目；待办列表仍只承载一次性的人的事。

## Assumptions

- **命名**：中文名定为「调度中心」（设计文档 §12 倾向、承载完整平台语义）；与既有 `graph_scheduler` / 「100% 调度」的词汇重叠靠模块文档点明区隔，不改既有命名。
- **周期规则细节**：第一批支持每隔 N（分 / 时）、每天某时、每周某天某时、工作日；工作日定义、时区 / DST 存储（UTC vs 本地）、跨日边界等留 plan 决定。
- **全局并发上限**：第一批只做 per-task 重入控制（D9），不做多不同任务同时触发的全局会话数上限；多不同任务并发默认允许（runtime 已是 per-session 门控）。
- **桌面通知**：需新装 Tauri 通知插件，capabilities 最小授权范围留 plan；app 未运行时不触发不通知，补跑是唯一救济——该预期须在 UI 向用户说明。
- **待办入口 UI 形态**：待办条目上是按钮还是右键菜单留 plan（接入语义已由 FR-015~FR-017 定完，只剩这一处交互细节）。
- **会话来源枚举**：第一批只区分 `user` / `scheduled`；既有讨论类会话（028）是否也归类、聊天屏如何处理留 plan。
- **per-task 免确认粒度**：第一批为粗放单档——开启即该任务所有高危动作放行（文件删除 / 命令执行 / 对外发送不细分）；细粒度权限矩阵留后续批次。
- **创建 / 编辑表单**：第一批不做表单，创建走对话 + 确认卡，修改 = 删除重建（重建成本低）；若实际使用中改动频繁，再把编辑表单提进后续批次。
- **自动失败重试**：第一批不做系统自动重试，统一走人工接管通道（SC-007）。
- **外部消费者**：项目为单人家用、未发布、无外部脚本 / API 消费者，spec 不预留 deprecation 双发兼容。
