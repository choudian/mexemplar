# Feature Specification: 主助理对话透明与可控

**Feature Branch**: `014-assistant-chat-transparency`
**Created**: 2026-06-03
**Status**: Completed
**Input**: User description: "这个页面以及文档"（指 AI 助手主屏的对话体验，以及设计文档 `docs/design/assistant_chat_transparency_design.md`）

## 概述

把现在"黑盒"的主助理，变成**看得见、停得下、接得上**的透明助理：用户在等待时心里有数、随时能干预、被打断的活儿还能接着干。功能落在 AI 助手主屏的对话界面，覆盖运行时输入门控、可中断停止（含其派出的子任务）、可原地编辑的单条排队、实时可折叠的过程时间线、子任务可观测卡片与详情、以及对暂停子任务的"继续任务"。

## Clarifications

### Session 2026-06-03

- Q: 排队消息遇上助理反问（回合以"等待用户回答"结束）时如何处理？ → A: 照常自动发出排队消息（作为对反问的回应发出）。
- Q: 排队消息在用户切换到其它会话再切回后是否保留？ → A: 保留——排队消息归属其所在会话，跨会话切换不丢弃。
- Q: 历史回合若已被压缩/概要化，其过程如何展示？ → A: 一律展示——压缩过的以规整概要形式呈现（复用"之前的对话内容"折叠样式），不隐藏、不报错。
- Q: "停止"如何可度量、重复点击如何处理？ → A: UI 约 200ms 内进入"停止中"反馈，在当前步骤返回后的下一个安全节点生效，重复点击幂等。
- Q: 过程区域里的"推理 / 思考过程"应展示到什么粒度？ → A: 尽量展示完整模型推理与完整工具结果，仅靠现有敏感字段过滤兜底。
- Q: 过程明细的历史回看是否必须与运行时展示同等完整？ → A: 必须；历史回看应尽量同等完整，若既有记录不足，应允许新增持久化过程明细。
- Q: 如果完整过程内容里包含内部机制术语，用户可见过程区域应如何处理？ → A: 原样展示；为完整透明允许内部机制术语出现在过程区域。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运行时不被误唤醒，并且随时能停 (Priority: P1)

助理正在处理任务时，用户不会再不小心发消息把它打断或重复唤醒；同时用户能随时点"停止"中断当前这件活儿——**包括它派出去正在跑的子任务也一起停**，不会出现"主的停了、子的还在偷偷跑"。停止后对话回到可继续状态，已经产出的内容不丢。

**Why this priority**: 这是用户最初提出的痛点（运行时还能发消息唤醒）与最核心的控制能力。没有它，用户对一个跑起来就停不下、还能被误触的助理缺乏基本信任。单独实现即可交付价值。

**Independent Test**: 发起一个会持续一段时间的任务，验证运行期间无法再次发送/唤醒；点击停止后对话在数秒内回到就绪态；若该任务已派出子任务，子任务同样停下并标记为已暂停；对话历史保留已产生的内容。

**Acceptance Scenarios**:

1. **Given** 助理正在处理一条任务，**When** 用户尝试再发一条消息，**Then** 系统不把它当作新的唤醒立即执行（输入进入"它在忙"的受控状态）。
2. **Given** 助理正在处理任务且界面显示"正在处理"，**When** 用户点击"停止"，**Then** 当前回合在下一个安全节点停下，对话回到就绪态，且不丢失已产生的内容。
3. **Given** 助理已把活儿派给一个正在运行的子任务，**When** 用户点击"停止"，**Then** 该子任务也停下并显示为"已暂停"。
4. **Given** 助理在等待用户回答它的反问（waiting_for_user），**When** 用户查看输入框，**Then** 输入框可用，用户能正常回答（此状态不算"忙"，不被门控）。

### User Story 2 - 它忙的时候，我可以先把下一句想好（排队） (Priority: P2)

助理还在忙时，用户能先把下一条消息写好，它会排队、等这一回合结束自动发出。**只排一句**；这条始终可以原地编辑（改措辞、往后追加），不用重敲。整个输入框进入"排队态"，双击即可进入编辑；编辑时不会外发，用户按回车或光标移开（失焦）才算编辑完成、恢复待发。中途点停止时，排队那条退回普通草稿，由用户重新决定。

**Why this priority**: 显著减少等待与重复输入，是高频体验提升。依赖 P1 的运行态判定，但可在其之上独立交付与验证。

**Independent Test**: 在助理运行期间写一条消息让其排队，验证回合自然结束后自动发出；验证排队那条可双击编辑、编辑期间不会被发出、回车/失焦后恢复待发；验证再写不会新增第二条而是改同一条；验证点停止后排队消息退回草稿。

**Acceptance Scenarios**:

1. **Given** 助理正忙、用户写好了一条下一步消息，**When** 用户提交它，**Then** 该消息进入"排队待发"，并在助理空闲时自动发出，无需用户再次手动发送。
2. **Given** 已有一条排队消息处于"排队态"，**When** 用户双击输入框，**Then** 进入编辑态，可修改/追加该条内容，且此期间不会被发出。
3. **Given** 用户正在编辑排队消息，**When** 用户按回车或点击别处使输入框失焦，**Then** 视为编辑完成，消息恢复"排队待发"。
4. **Given** 已有一条排队消息，**When** 用户在同一处再写内容，**Then** 仍只有一条生效待发（改的是同一条，不产生第二条、不另起空框）。
5. **Given** 有一条排队消息且助理仍在运行，**When** 用户点击停止，**Then** 排队消息退回为普通草稿，不自动发出。

### User Story 3 - 看得见主助理自己的思考过程 (Priority: P2)

主助理怎么想的、调用了什么、中间拿到什么结果，会**实时**显示在对话里。这段过程**默认折叠**，用户想看就展开细看，不想看就收着；最终回复照常正常显示。过程区域限定高度、内部可滚动，不会把页面撑得很长。历史会话也能展开回看这段过程。

**Why this priority**: 透明带来信任，是用户明确要求的"放心"。可独立于排队/子任务交付与验证。

**Independent Test**: 发起一个任务，验证助理的中间推理与动作随执行实时出现在一个默认折叠的区域内；展开可看到推理、调用与结果；最终回复单独正常显示且不重复；区域超出限定高度时内部出现滚动条；重开该历史会话仍可展开回看。

**Acceptance Scenarios**:

1. **Given** 助理正在处理任务，**When** 它进行推理或采取动作，**Then** 这些过程项实时出现在该回合的过程区域内。
2. **Given** 过程区域存在，**When** 用户未操作，**Then** 它默认保持折叠、不自动展开；用户可手动展开/收起。
3. **Given** 过程项较多超出限定高度，**When** 用户展开查看，**Then** 区域内部出现滚动条，页面整体不被撑长。
4. **Given** 一个已结束的历史会话，**When** 用户重新打开它，**Then** 仍可展开回看该回合的过程。

---

### User Story 4 - 看得见它派出去的子任务在干什么 (Priority: P2)

助理把活儿分给"子助手"时，对话里出现一张带动效的**卡片**，让用户一眼知道"这有个子任务在跑"，并显示它的任务与状态（运行中/已完成/已暂停）。用户**双击卡片**可展开详情，看这个子助手自己的完整过程（包含它调用的工具）。子任务信息归属到当前对话；重连或重开会话时能取到权威列表。

**Why this priority**: 把"100% 调度"产生的子任务从黑盒变可见，是 P5（继续任务）的前提，本身也独立提供价值。

**Independent Test**: 发起一个会派子任务的请求，验证对话里出现子任务卡片并实时反映其状态；双击卡片可看到该子任务的完整过程（含工具）；子任务卡片显示在发起它的当前对话中；断开重连或重开会话后仍能看到该子任务及其状态。

**Acceptance Scenarios**:

1. **Given** 助理把任务派给一个子助手，**When** 子助手开始运行，**Then** 当前对话中出现一张子任务卡片，显示其任务与"运行中"状态。
2. **Given** 子任务卡片存在，**When** 用户双击该卡片，**Then** 展开详情，显示该子助手自己的完整过程，包含它调用的工具与结果。
3. **Given** 子任务运行结束或被暂停，**When** 状态变化发生，**Then** 卡片状态相应更新为"已完成"或"已暂停"。
4. **Given** 用户重连或重新打开包含子任务的会话，**When** 界面加载，**Then** 能取到该会话子任务的权威列表与状态，而非凭猜测。

---

### User Story 5 - 被打断/暂停的子任务，能接着干 (Priority: P3)

被用户停下来的子任务以"已暂停"留在卡片上。用户可以点**"继续任务"**让它接着做；有补充想说的可以写上一起带过去。对用户而言这就是"让助理把刚才那件事接着做完"——本质上是唤醒主助理、由主助理去续跑那个子任务，而不是用户直接操纵子任务。续跑结果走主助理的正常回复回到对话里。

**Why this priority**: 依赖 P1（产生暂停态）与 P4（看见并定位子任务）。是闭环价值的收尾，但优先级低于"看见"和"停得下"。

**Independent Test**: 停止一个正在跑子任务的回合使其暂停；在卡片上点"继续任务"（可带补充消息）；验证主助理被唤醒并把该子任务续跑完成，结果作为正常回复出现；验证子任务正在运行时"继续任务"不可用；验证只能继续属于当前对话的子任务。

**Acceptance Scenarios**:

1. **Given** 一个因停止而处于"已暂停"的子任务，**When** 用户点击"继续任务"，**Then** 主助理被唤醒并接着把该子任务做完，结果作为正常回复出现在对话里。
2. **Given** 用户在"继续任务"时填了补充消息，**When** 续跑发生，**Then** 该补充消息被一并带入续跑。
3. **Given** 一个仍在运行中的子任务，**When** 用户查看其卡片，**Then** "继续任务"不可用（仅对已暂停的子任务可用）。
4. **Given** 一个不属于当前对话的子任务标识，**When** 触发继续，**Then** 系统拒绝，不泄露或操纵他人会话的子任务。

### Edge Cases

- **正在等用户回答时不算"忙"**：助理结束并向用户反问后，输入必须可用，门控只针对"正在处理（running）"。
- **协作式停止的延迟**：停止是"停在当前这一步之后"；若正卡在某一次较慢的步骤内，会等那一步返回后立即停（不做硬杀式瞬时中断）。点击停止 MUST 立即进入"停止中"过渡反馈；生效前重复点击停止保持幂等，避免用户以为没生效或触发重复取消。
- **停止不等于失败**：用户主动停止应使会话进入可续跑的暂停态，而不是被当作错误。
- **排队消息与停止的交互**：自动发出只针对"已提交排队"的消息；"编辑中"的消息即便此刻助理空闲也不外发；停止后排队消息退回草稿。
- **继续任务未生效**：若点了"继续任务"但主助理实际未续跑目标子任务，须给用户明确兜底提示，而非静默无反应。
- **历史回合已压缩**：被压缩/概要化的历史回合展开时以规整概要展示其过程，不隐藏、不报错、不为此补充持久化。
- **过程项暴增**：单回合过程项很多时，过程区域内部滚动，不撑长页面；过程区域为完整透明的受控例外，允许原样展示过程内容中的内部机制术语（如 archive/compression/message_type/event sequence/segment 等）。
- **重连缺口**：事件流出现缺口或会话不匹配时，按权威快照刷新子任务列表与过程，而不是凭内部事件名猜测。
- **停止遇上 pending 高危确认**：若停止时回合正卡在高危确认等待中，停止 MUST 将该确认 fail-closed 当拒绝并唤醒回合，使停止即时生效，同时不破坏 CC-001 确认协议（first-decision-wins / expires_at）。
- **失败回合的排队**：回合以 failed 结束时，排队消息与"被停止"一致退回普通草稿、不自动发出。
- **非助理流程不受影响**：技能教学/试用等非助理执行链路在本特性下行为不变。

## Requirements *(mandatory)*

### Functional Requirements

**运行时输入门控（US1）**

- **FR-001**: 当助理处于"正在处理"状态时，系统 MUST 阻止用户发出会再次唤醒助理执行的新消息。
- **FR-002**: 当助理处于"等待用户回答（waiting_for_user）"状态时，系统 MUST 允许用户正常输入并回答，不施加门控。
- **FR-003**: 输入控件的可用/不可用 MUST 由助理真实运行状态驱动，而非仅由一次发送请求的瞬时状态驱动。

**停止与深度取消（US1）**

- **FR-004**: 助理"正在处理"时，用户 MUST 能随时触发"停止"中断当前回合。
- **FR-005**: 停止 MUST 同时作用于该回合派出的、正在运行的子任务（深度取消），使其一并停下。
- **FR-006**: 停止 MUST 为协作式：在下一个安全节点生效，绝不采用强制杀进程/线程的瞬时中断（点击停止的即时反馈见 FR-006a）。
- **FR-006a**: 用户点击停止后，系统 MUST 立即进入可见的"停止中"过渡反馈；在停止生效前，重复点击停止 MUST 幂等（不重复取消、不报错）。
- **FR-006b**: 若停止发生时该会话存在 pending 高危确认（助理回合正阻塞在确认等待中），停止 MUST 将该确认 fail-closed 当作"拒绝"处理并唤醒回合到下一个取消检查点，使停止即时生效；此过程 MUST 保留既有高危确认同步确认协议（first-decision-wins / expires_at 不被破坏，见 CC-001）。
- **FR-007**: 用户主动停止 MUST 被视为可恢复的暂停而非错误；被停止的会话与子任务 MUST 保留已产生的工作、可后续继续。
- **FR-008**: 停止后对话 MUST 回到可继续/就绪态，且已产生的内容 MUST 保留在对话历史中。

**排队下一条（US2）**

- **FR-009**: 助理忙时，用户提交的下一条消息 MUST 进入"排队待发"，并在该回合**成功结束**或**以向用户反问（等待回答）而结束**时自动发出，无需用户再次手动发送——这两种情形下已提交排队的消息都作为下一条消息发出。回合**失败（failed）或被用户停止（cancelled）**时，排队消息 MUST 退回为普通草稿、不自动发出（见 FR-014）。
- **FR-010**: 系统 MUST 对每个会话仅保留**一条**生效待发的排队消息；用户继续输入 MUST 修改同一条，而不是新增第二条或另起空输入框。
- **FR-010a**: 排队消息 MUST 归属其所在会话，并在用户切换到其它会话后再切回时予以保留（不因会话切换而丢弃）。
- **FR-011**: 排队消息 MUST 可原地编辑：整个输入框进入"排队态"；双击进入"编辑态"，并 MUST 提供可见的进入编辑提示与键盘可达入口（不以双击为唯一入口）。
- **FR-012**: 处于"编辑态"时，消息 MUST NOT 被发出，即使此刻助理已空闲。
- **FR-013**: 用户按回车或使输入框失焦 MUST 被视为编辑完成，消息恢复"排队待发"。
- **FR-014**: 用户停止当前回合、或当前回合以失败（failed）结束时，排队消息 MUST 退回为普通草稿，不自动发出。
- **FR-015**: 自动发出 MUST 仅针对"已提交排队"的消息；"编辑态"的消息不参与自动发出。

**主助理过程透明（US3）**

- **FR-016**: 对每个助理回合，系统 MUST 在对话中实时呈现助理可取得的完整过程（模型推理/过程文本、采取的动作、动作结果），并在既有敏感字段过滤后尽量展示完整工具结果，不主动摘要化省略可展示内容。
- **FR-017**: 过程区域 MUST 默认折叠、不自动展开，用户可手动展开/收起。
- **FR-018**: 助理的最终回复 MUST 照常正常显示，且 MUST NOT 在过程区域中重复出现。
- **FR-019**: 过程区域 MUST 限定高度，超出时内部滚动，不撑长整页。
- **FR-020**: 历史会话 MUST 可展开回看其各回合的过程：详细步骤仍在时展开看全过程；该回合已被压缩/概要化时，MUST 以**规整的概要形式**展示（复用既有"之前的对话内容"折叠样式），不隐藏、不报错，且**不要求为此补充持久化**。

**子任务可观测（US4）**

- **FR-021**: 助理把任务派给子助手时，系统 MUST 在当前对话中以卡片呈现该子任务，显示其任务描述与状态（运行中/已完成/已暂停/失败）。
- **FR-022**: 子任务卡片 MUST 实时反映其状态变化，运行中 SHOULD 有可感知的动效。
- **FR-023**: 用户双击子任务卡片 MUST 能展开其详情，显示该子助手自己的完整过程，包含它调用的工具与经既有敏感字段过滤后的完整结果；卡片 MUST 提供可见的"查看详情"提示与键盘可达入口（不以双击为唯一入口）。
- **FR-024**: 子任务信息 MUST 归属并显示在发起它的当前对话中。
- **FR-025**: 重连或重新打开会话时，系统 MUST 能取到该会话子任务的权威列表与状态。

**继续暂停的子任务（US5）**

- **FR-026**: 处于"已暂停"的子任务卡片上，系统 MUST 提供"继续任务"操作。
- **FR-027**: "继续任务" MUST 通过唤醒主助理、由主助理去续跑该子任务来实现，而非让用户直接操纵子任务执行（保持"100% 调度"）。
- **FR-028**: 用户 MAY 在"继续任务"时附加补充消息；若提供，该消息 MUST 被一并带入续跑。
- **FR-029**: 子任务正在运行时，"继续任务" MUST 不可用。
- **FR-030**: 系统 MUST 校验子任务归属，只允许继续属于当前对话的子任务，并拒绝对非己出会话的访问或操纵。
- **FR-030a**: "继续任务"触发后，系统 SHOULD 校验目标子任务确实从"已暂停"转为"运行中"；若主助理实际未续跑该子任务，系统 MUST 给用户明确的兜底提示，而非静默无反应。

**跨场景**

- **FR-031**: 除过程区域中原样展示的过程内容外，所有面向用户的文案、状态、空态、错误信息 MUST NOT 暴露内部机制术语（如 archive/compression/message_type/event sequence/causation/segment/subagent dispatch 等）；过程区域 MAY 为完整透明原样显示这些术语。
- **FR-032**: 事件流出现缺口或会话不匹配时，系统 MUST 以权威快照刷新展示，而非依据内部事件名猜测。

### Key Entities

- **回合（Turn）**：一次"用户消息 → 助理过程 → 最终回复"的完整片段；承载该回合的过程项与子任务，以及运行状态。
- **过程项（Activity Step）**：助理或子助手在一回合内的单步活动，类型为 推理 / 工具动作 / 工具结果；可归属于主助理或某个子任务。
- **子任务（Subagent Task）**：助理委派出的一个执行单元，含任务描述、状态（运行中/已完成/已暂停/失败）、自身过程（含工具）与产出；归属于发起它的对话。
- **排队消息（Queued Message）**：当前唯一一条待发的下一条消息，及其状态（排队态 / 编辑态）。
- **运行状态（Run State / Progress）**：助理回合的对外状态（空闲 / 正在处理 / 等待用户 / 已停止 / 成功 / 失败），驱动输入门控与界面展示。

### Constraints & Compatibility

- **CC-001**: MUST 保留既有高危确认的同步确认协议与会话级"免确认"语义，不得因本特性回归（确认浮层、first-decision-wins、expires_at 等不被破坏）。
- **CC-002**: MUST 保持办公助理"100% 调度"约束：主助理不直接执行任务，"继续任务"也经由主助理调度子任务完成。
- **CC-003**: 取消 MUST 为协作式且类型安全：不得把用户主动停止与不可恢复错误混为一谈，也不得用硬杀线程实现中断。
- **CC-004**: 面向前端的新事件 MUST 经公开 UI 事件契约注册后以受控载荷发出；前端 MUST NOT 依据内部事件名或未注册载荷做展示决策。
- **CC-005**: 非助理执行链路（技能教学/学习/试用：PM/Programmer/Trial）MUST 零行为变化。
- **CC-006**: 大脑沉淀数据"永不物理删除"等既有数据约束 MUST 不被本特性破坏（本特性以读取既有历史为主，不新增物理删除路径）。
- **CC-007**: 当前为单用户、未发布阶段，无外部脚本/API 消费者；本特性 MUST NOT 为外部兼容性预留 deprecation/双发等额外范围。

## Architecture Impact *(Mexemplar-specific)*

- [x] **Desktop API Bridge** (`src/desktop_api/`) — 停止/子任务列表/子任务过程的入口，过程与子任务生命周期事件的 UI 事件注册与投影
- [x] **Business** (`src/business/`) — 协作式取消原语、Agent 循环中的取消检查与过程事件、编排层对"已停止"结果与续跑的处理
- [ ] **Execution** (`src/execution/`)
- [x] **Data** (`src/data/`) — 仅经既有 `MessageRepository` / `WorkflowTransitionRepository` / `SessionRepository` **只读**重建历史过程与子任务列表；**不新增持久化、无新表/迁移**（与下文 Data Store Impact、FR-020 一致）
- [ ] **Recording** (`src/recording/`)
- [x] **Utils** (`src/utils/`) — 新增供投影的后端事件

### Agent Impact

- 受影响 Agent：**Assistant**（及其派出的临时子代理 / 专员的可观测与续跑）；PM / Programmer / Trial **不受影响**。

- 系统提示：基本无需变更（被停止/暂停的子任务线索以可读结果留存于上下文供续跑）。
- 编排调度：新增对"用户主动停止 → 可恢复暂停"结果的处理；续跑仍经主助理调度。

### Data Store Impact

- **SQLite**：无新增表/迁移；子任务列表与过程由既有 `MessageRepository` / `WorkflowTransitionRepository` / `SessionRepository` 经 Repository 边界**只读**重建；历史回合若已被压缩，则以规整概要展示，不为此补充持久化。
- **Config**：可能引入少量可调阈值占位（如停止生效检查的节点），Settings UI 暂不暴露。
- **Secrets**：无新增敏感字段。

### Event Impact

- 新增后端通知事件：主助理/子助手过程步骤、子任务生命周期（开始/结束/暂停）。
- 新增公开 UI 事件：过程时间线事件、子任务卡片/状态事件；`assistant.progress` 增加"已停止"状态取值。
- 新增 UI 入口（非事件）：停止、子任务列表、子任务过程详情。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 助理"正在处理"期间，用户无法再次发送会唤醒它的新消息——误唤醒发生率为 0；而"等待用户回答"状态下输入 100% 可用。
- **SC-002**: 用户点击停止后 UI 约 200ms 内进入"停止中"反馈；当前回合在当前步骤返回后的下一个安全节点停止并回到就绪态；抽样验证中 100% 的停止操作不会留下"主停子未停"的残留，且重复点击停止幂等。
- **SC-003**: 排队消息在助理空闲后自动发出，用户无需再次手动发送；"编辑态"的排队消息在任何情况下都不会被提前发出（0 例提前外发）。
- **SC-004**: 对每个助理回合，用户都能查看到助理与每个被委派子任务的过程（含经既有敏感字段过滤后的工具结果）：运行时为完整过程，历史回看为全过程或（已压缩时）规整概要；过程默认折叠，不会把页面撑长（超出即内部滚动）。
- **SC-005**: 被停止的子任务可被"继续任务"续跑并完成，用户无需重新描述该任务；续跑结果以正常回复呈现。
- **SC-006**: 停止/中断后，对话历史 100% 保留已产生的内容（无内容丢失）。
- **SC-007**: 非助理流程（技能教学/学习/试用）在本特性上线前后行为一致——回归用例 100% 通过。
- **SC-008**: 除过程区域中原样展示的过程内容外，面向用户的普通界面文案中不出现内部机制术语（archive/compression/segment/event sequence 等）——非过程区域文案审查 0 命中。

## Assumptions

- 用户在 AI 助手主屏与会话交互；排队/草稿归属其所在会话，跨会话切换予以保留；它们是前端临时意图、不持久化到后端，应用/窗口关闭后不再保留为待发。
- "停止"为协作式中断；用户接受其在当前步骤返回后即时生效，而非瞬时硬中断。
- 助理委派为同一执行链路内的同步调度，子任务深度有限（子任务/专员不再向下委派），故深度取消可覆盖其当前正在运行的子任务。该"同线程同步委派"是深度取消的**承重不变量**，由门卫测试守护——一旦委派改走线程/异步即需重审取消机制。
- 过程透明覆盖运行时与历史回看；历史回合若已被压缩/概要化，则以规整概要展示，**不为此补充持久化**（无新增表/迁移）。
- 既有会话生命周期、暂停/恢复语义、UI 事件契约机制保持可用，本特性在其之上扩展。
- 当前为单用户、未发布阶段，无外部消费者；不为外部兼容预留额外范围。
