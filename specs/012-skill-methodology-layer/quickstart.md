## Story P2: 通过 assistant 创建方法论 + 编辑闭环

### 验证 SC-002 / SC-003 / SC-008 / SC-009 / SC-010 / SC-019 / SC-021 / SC-022 / SC-023 / SC-025

1. **触发创建**:
   - 与 assistant 对话："帮我整理上周做的周报，看看流程"
   - 完成对话后让 segment 沉淀（关闭窗口或空闲触发）
   - 对 assistant 说："把刚才那套做周报的流程做成方法论"
   - 预期：assistant 调 `create_skill_methodology` → 入库 → 回复"已新增方法论：周报生成方法论"
   - 验收：方法论屏新增卡片（30 秒内）

2. **方法论详情查看**:
   - 点击该卡片打开详情
   - 确认看到：名称、描述、trigger_conditions list（≥1 条）、required_tools list、正文 Markdown、素材来源（标 archive zone）

3. **编辑保存（普通方法论）**:
   - 在编辑器中改 description
   - 点击保存
   - **预期：无 UI 二次确认弹窗**，立即生成 v2，前端浮层提示"已生成 v2"
   - 列表卡片 version 字段刷新到 2

4. **编辑保存（受保护方法论 "如何创建方法论"）**:
   - 在方法论列表找到"如何创建方法论"
   - 进入编辑器改正文任意字符
   - 点击保存
   - **预期：触发高危确认弹窗**，提示"修改此内置方法论将影响所有后续方法论创建行为，确定？"
   - 拒绝 → 保存取消
   - 确认 → 走 supersede 接力出 v2，新版本 origin = `user_edit`，受 FR-027a 保护沿链传播

5. **软删除（无装备者）**:
   - 对当前 active 方法论选"软删除"
   - 走 FR-020 高危确认弹窗（无装备者时也走，因为 P3 后 assistant 本体已装备）
   - 确认 → 方法论落 `soft_deleted` 终态，列表不再可见

6. **软删除受保护方法论**:
   - 在"如何创建方法论"卡片
   - **预期：软删除按钮不可见**（FR-027a 隐藏）

7. **物理 DELETE 阻断**（守卫测试覆盖）:
   - 执行 `pytest tests/guardrails/test_skill_no_physical_delete.py -v`
   - 全部通过：API / Repository / 直连 SQL 三路径阻断

8. **`origin` 封闭枚举**（守卫测试）:
   - 执行 `pytest tests/guardrails/test_skill_origin_closed_enum.py -v`
   - 5 个合法枚举 + 非法值拒绝 + `external_import` 本期暂禁用 全部通过

9. **Seed fail-open**（守卫测试）:
   - 执行 `pytest tests/guardrails/test_skill_seed_fail_open.py -v`
   - 三场景（seed 缺失 / 内容空 / IO 错误）都用 fallback 入库且应用启动不阻塞

## Story P3: 装备方法论给 specialist

### 验证 SC-004 / SC-005 / SC-013 / SC-014 / SC-015 / SC-017 / SC-018 / SC-020 / SC-024 / SC-026

1. **新建 specialist 默认全装备**:
   - 在 SpecialistScreen 新建一个 specialist "Foo"
   - 进入其装备方法论面板
   - **预期**：当时所有 active 非 `system_bootstrap` 方法论已默认装备（按创建时间升序）；"如何创建方法论"**未**装备到 Foo（FR-014a 例外）

2. **新方法论入库默认全装备传播**:
   - 通过 assistant 创建一个新方法论"代码评审方法论"
   - 检查所有已存在 specialist 与 assistant 本体的装备清单
   - **预期**：每个 specialist 与 assistant 本体的装备清单末尾追加"代码评审方法论"

3. **assistant 本体装备面板**:
   - 在 SpecialistScreen 顶部找到"Assistant（主助理本体）"卡片
   - 点入装备面板
   - **预期**：可多选 / 调序 / 卸下；卡片不可删除不可重命名

4. **Token 计量条**:
   - 在装备面板顶部找到 token 计量条
   - 勾选/卸下方法论
   - **预期**：实时更新数字（前端本地估算），超过 4096 黄色、超过 8192 红色
   - 不阻断保存（FR-016a 仅作展示）

5. **system prompt 注入**:
   - 让 assistant 派活给 Foo
   - 打开 Debug Inspector 查看 Foo 的 system prompt
   - **预期**：含"equipped_skills" YAML block，每条方法论的 id + name + description + trigger_conditions list；**不**含 body markdown

6. **load_skill_methodology 工具**:
   - Foo 执行任务时调 `load_skill_methodology(skill_id=<某条装备的方法论>)`
   - **预期**：工具 result 为 SKILL.md 形态文本（YAML frontmatter + Markdown body）
   - 该方法论的 `loaded_count` +1（查 SkillScreen 列表卡片确认）

7. **同轮多次 load 不被拒**:
   - Foo 在同一轮内连续调 `load_skill_methodology` 5 次（同/不同 skill_id）
   - **预期**：全部成功；每次 `loaded_count` +1，无去重窗口（SC-024）

8. **派活决策不读方法论**（守卫测试）:
   - 执行 `pytest tests/guardrails/test_skill_dispatch_no_methodology_signal.py -v`
   - 断言 assistant 派活路径代码不 import / 不调用 SkillService / 不读 brain_skill_equipment

9. **强制软删除装备的方法论**:
   - 选一份被多个 specialist 装备的方法论
   - 点"软删除"
   - 走 FR-020 高危确认弹窗，展示"以下专员装备了它：Foo, Bar..."
   - 确认 → 单事务内裁剪装备关系 + 落 `soft_deleted`；前端 specialist 卡片自动刷新

10. **装备关系永不物理删除**（守卫测试）:
    - 执行 `pytest tests/guardrails/test_skill_no_physical_delete.py::test_equipment_no_physical_delete -v`
    - 卸下 / 强制裁剪 / supersede 切版本三路径均标 unequipped 不删行；再装备新建一行不复用历史

11. **正文不在 system prompt**（守卫测试）:
    - 执行 `pytest tests/guardrails/test_skill_no_body_in_system_prompt.py -v`
    - 断言 assistant / specialist system prompt 100% 不含任何方法论的 body_markdown

## Story P4: 方法论修订与溯源

### 验证 SC-006 + FR-011 / FR-011a / FR-039

1. **assistant 调工具 supersede**:
   - 对 assistant 说"把'周报生成方法论'改一版，让它多看 failure zone 的失败案例"
   - assistant 调 `create_skill_methodology(mode='supersede', target_skill_id=<v1 id>, ...)` 产出 v2
   - **预期**：旧版 v1 → superseded；新版 v2 → active；所有装备者的装备关系切到 v2

2. **版本链回看**:
   - 进入审计视图，看版本链
   - **预期**：v1 与 v2 节点都展示，含完整正文 + 与上一版的 diff 高亮
   - 切换"完整正文" / "diff" 两种展示

3. **素材降权显示**:
   - 在某方法论详情看素材来源列表
   - 软删除其中一条 segment 的来源 entry（通过 BrainScreen）
   - 回到该方法论详情
   - **预期**：素材项灰显但仍可看到 segment ID 与 summary 快照

4. **并发 supersede first-writer-wins**（集成测试）:
   - 执行 `pytest tests/integration/test_skill_supersede_transaction.py -v`
   - 模拟两个并发 supersede 流程作用于同一 active，断言：
     - 链最终为单向无分叉（X → v_a → v_b）
     - 每步在单事务内（崩溃整体回滚）
     - 装备关系最终全部指向 v_b

5. **装备关系审计**（双向历史）:
   - 在某方法论详情打开"装备历史"
   - **预期**：列出该方法论曾被哪些装备者装备又卸下，含 equipped_at / unequipped_at / unequipped_reason
   - 反向：在 specialist 审计页打开该 specialist 的装备历史
   - **预期**：列出该 specialist 曾装备过的方法论 + 时间区间

## 故障排查

- **应用启动后 SkillScreen 列表为空**:
  - 检查 v12 migration 是否已应用：`sqlite3 ... "SELECT version FROM schema_version"` 应返回 12
  - 检查 `brain_skills` 表内是否至少有"如何创建方法论"行：`SELECT name, origin, status FROM brain_skills`
  - 应有一条 `("如何创建方法论", "system_bootstrap", "active")`；如果没有 → 检查 logs 看 bootstrap 是否走了 fallback 或异常

- **assistant 调 create_skill_methodology 报 `skill_source_segment_wrong_zone`**:
  - 检查传入的 segment 对应的 `brain_memory_entries.zone` 是否在 `{archive, failure}` 内
  - 该错误期望——只有 archive / failure 分区的 segment 可作素材（FR-024）

- **装备清单 token 计量条显示数字过大**:
  - 该方法论 description 或 trigger_conditions 文本过长 → 在编辑器内精简
  - 阈值可调整：`brain.skill.token_budget.warn_threshold` / `danger_threshold` 配置 key

- **`skills_referenced` 没有 +1**:
  - 检查 reply 元数据是否真的包含 `skills_referenced` 字段（在 Debug Inspector 查 message log）
  - 检查 chain_root 是否已被 soft_deleted（fail-soft 静默跳过路径）
