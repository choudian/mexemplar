## Clarifications

### Session 2026-04-27

- Q: "全部允许 / 免确认"开启后，自动放行范围应该是什么？ → A: 当前会话内 Assistant 的全部高危工具（`write_file` / `edit_file` / `exec`）后续请求自动放行
- Q: 启用"全部允许 / 免确认"时，已经排队但尚未展示的确认请求应该怎么处理？ → A: 当前请求放行，队列中尚未展示的 Assistant 高危请求立即自动放行，后续新请求也自动放行
- Q: 确认浮层里的"关键参数摘要"应展示到什么细度？ → A: 展示工具名与目标路径/命令首行等关键字段；长参数截断，不展示完整文件内容
- Q: 对用户的确认决策是否需要新增可观测日志？ → A: 新增脱敏结构化日志，记录 request_id、工具名、决策、来源、耗时与摘要；不记录完整参数或文件内容
- Q: 用户是否可以不点三个决策按钮而手动关闭确认浮层？ → A: 不允许手动关闭；确认浮层只能通过"全部允许" / "同意" / "拒绝"或超时结束

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 单次确认改为非阻塞浮层 (Priority: P1)

用户在与 Assistant Agent 对话过程中，Agent 触发高危工具（写入/编辑文件、执行命令）时，主窗口右下角出现一个非阻塞的浮层，列出本次将要执行的动作摘要（工具名 + 关键参数），并提供三个按钮：**全部允许 / 同意 / 拒绝**。用户点"同意"放行本次，点"拒绝"取消本次；浮层关闭，主窗口在等待期间不被任何模态对话框遮挡，用户随时可以浏览聊天记录、滚动页面、打开侧边栏。

**Why this priority**: 这是当前最强用户痛点——`QMessageBox.question` 抢走整个窗口的焦点并阻塞 UI，体验突兀。把它改成非阻塞 Toast 即可显著降低打断感，且不依赖后续 P2/P3 也能独立交付价值。

**Independent Test**: 启动应用 → 与 Assistant 对话 → 让 Agent 执行 `write_file` → 观察右下角浮层出现，主窗口其余区域仍可点击；分别验证"同意/拒绝"对应行为。无需"全部允许"和顶栏 Toggle 即可完整验证本故事。

**Acceptance Scenarios**:

1. **Given** Assistant Agent 调用 `write_file` 写入 `/tmp/foo.txt`，**When** UI 收到确认请求，**Then** 主窗口右下角显示浮层，文案包含工具名 `write_file` 与目标路径 `/tmp/foo.txt`，主窗口其它控件可正常交互
2. **Given** 浮层已显示，**When** 用户点击"同意"，**Then** 浮层关闭，Worker 收到放行结果并继续执行该工具，本次确认不影响后续请求
3. **Given** 浮层已显示，**When** 用户点击"拒绝"，**Then** 浮层关闭，Worker 收到拒绝结果且工具不执行
4. **Given** 浮层已显示且无人操作，**When** 等待时间超过既定超时阈值，**Then** 浮层自动关闭，Worker 按"拒绝"语义处理（与现有超时行为对齐）

---

### User Story 2 - 会话级"全部允许"快捷通道 (Priority: P2)

用户在一次连续对话中执行批量文件改造（例如让 Agent 连续修改十几个文件），不希望对每一次写操作都点"同意"。浮层上的"全部允许"按钮一键开启会话级豁免：本次会话内后续所有 Assistant 高危工具请求（`write_file` / `edit_file` / `exec`）自动放行，不再弹浮层。开始一个新对话时该豁免自动复位为关闭，避免跨会话遗留。

**Why this priority**: 解决"决策疲劳"是 P1 之上的体验增量。可在 P1 落地后独立追加，不影响 P1 的最小可用性。

**Independent Test**: 在同一会话连续触发 10 次 `write_file`：首次浮层出现→用户点"全部允许"，后续 9 次应不再弹浮层并直接放行；新建对话后再次触发 `write_file`，浮层应再次出现。

**Acceptance Scenarios**:

1. **Given** 浮层显示且当前会话从未启用过"全部允许"，**When** 用户点击"全部允许"，**Then** 当前请求放行，且后续同会话内所有高危确认请求被自动放行（不弹浮层）
2. **Given** 当前会话已启用"全部允许"，**When** 用户开启一个新对话，**Then** 系统自动复位该状态为关闭，新对话首个高危操作重新触发浮层
3. **Given** 当前会话未启用"全部允许"，**When** Worker 触发高危请求，**Then** 浮层正常弹出（行为与 Story 1 相同，证明 Story 2 的开关默认关闭、不破坏 Story 1）
4. **Given** 当前会话仍有已显示或排队中的 Assistant 高危确认请求，**When** 用户开启一个新对话，**Then** 这些未决请求按拒绝/超时语义收敛并从旧会话清空，且不会泄漏到新对话中展示

---

### User Story 3 - 顶栏 Toggle 与浮层状态双向同步 (Priority: P3)

用户希望在不等浮层弹出的情况下，主动从对话窗口顶栏开启/关闭"免确认"模式。顶栏 Toggle 与浮层"全部允许"共享同一会话级状态：任一处变化，另一处的可视状态立刻同步。新对话时与"全部允许"一并复位为关闭。

**Why this priority**: 顶栏入口是体验上的"主动控制"补充，对核心流程非必需，但能让有经验的用户更快进入"信任模式"。落地顺序排在 P1/P2 之后即可。

**Independent Test**: 顶栏点击 Toggle → 状态变为开启 → 触发 `write_file` 不弹浮层并直接放行；再切回关闭 → 触发 `write_file` 浮层重新出现。反向：浮层"全部允许"被点击后，顶栏 Toggle 在同帧或下一帧内显示为开启状态。

**Acceptance Scenarios**:

1. **Given** 顶栏 Toggle 显示为关闭，**When** 用户点击 Toggle 切换为开启，**Then** 后续高危请求被自动放行，浮层不再出现
2. **Given** 浮层显示且用户点击"全部允许"，**When** 浮层关闭后用户查看顶栏，**Then** 顶栏 Toggle 已显示为开启状态（视觉同步）
3. **Given** 顶栏 Toggle 显示为开启，**When** 用户点击 Toggle 切换为关闭，**Then** 后续高危请求重新触发浮层；若此时正在显示的浮层不受影响（仍按用户当前选择处理）

---

### Edge Cases

- **多 Worker 并发请求**：同一时刻多个高危确认请求到达 UI 线程时，系统按到达顺序排队展示浮层，前一个浮层关闭后下一个再显示；任何请求都不能丢失，每个请求都得到一次用户决策或一次超时
- **排队中开启"全部允许"**：用户在某个确认浮层上点击"全部允许"或通过顶栏 Toggle 开启"免确认"后，当前请求放行，确认队列中尚未展示的 Assistant 高危请求立即按自动放行处理，不再逐个展示；之后新到达的同会话 Assistant 高危请求也自动放行
- **普通 Toast 与确认浮层共存**：现有用于成功/错误提示的普通 Toast（自动消失型）与确认浮层独立管理，互不覆盖；普通 Toast 不会因为确认浮层占用屏幕角落而被吞掉
- **超时与 Worker 阻塞对齐**：浮层超时关闭的时间不晚于 Worker 阻塞等待的超时阈值，避免出现 Worker 已按"拒绝"返回但浮层还在挂着的反差
- **会话切换时存在未决确认**：如果用户在旧会话仍有已显示或排队中的确认请求时切换到新对话，所有未决请求都按超时/拒绝语义收敛，不得在新对话中继续展示或等待
- **"全部允许"的安全可见性**：开启状态下界面应给出可见提示（顶栏 Toggle 高亮 / 文案变化），让用户随时知道当前处于"无确认"状态
- **手动关闭限制**：确认浮层不提供普通关闭按钮，也不响应点击浮层外区域关闭；它只能通过"全部允许" / "同意" / "拒绝"或超时结束，确保每个请求都有明确决策结果
- **非 Assistant Agent 的工具确认**：PM Agent / Trial Agent 走 `IntentConfirmationUI`，不受本 feature 影响

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 当 Assistant Agent 调用受确认管控的高危工具（当前包含 `write_file` / `edit_file` / `exec`）时，系统 MUST 在主窗口右下角显示非阻塞浮层并要求用户决策
- **FR-002**: 浮层 MUST 是非模态的——出现期间用户对主窗口其它控件的输入 MUST 不被阻塞
- **FR-003**: 浮层 MUST 显示足够上下文信息（至少工具名 + 关键参数摘要），使用户在不查看代码的前提下能做出决策；摘要 MUST 包含目标路径或命令首行等关键字段，长参数 MUST 截断，且 MUST NOT 展示完整文件内容
- **FR-004**: 浮层 MUST 提供三个按钮："全部允许" / "同意" / "拒绝"，每个按钮的语义与本规范定义一致
- **FR-005**: 用户点击"同意" MUST 仅对当前一次确认请求放行，不影响后续请求
- **FR-006**: 用户点击"拒绝" MUST 仅对当前一次确认请求拒绝，不影响后续请求
- **FR-007**: 用户点击"全部允许" MUST 既放行当前请求，又使本次会话内 Assistant 的后续全部高危确认请求（`write_file` / `edit_file` / `exec`）被自动放行（不再弹浮层）
- **FR-007a**: 当"全部允许"或顶栏 Toggle 开启时，系统 MUST 将确认队列中尚未展示的 Assistant 高危请求立即按自动放行处理，不再逐个展示这些已排队请求
- **FR-008**: 系统 MUST 在用户开启新对话时自动复位"全部允许"状态为关闭
- **FR-009**: 对话窗口顶栏 MUST 提供"免确认"开关，与"全部允许"内部状态双向同步（任一处改变，另一处的可视/语义状态同步更新）
- **FR-010**: 浮层 MUST 设置超时机制；超时时间不晚于现有 Worker 阻塞确认超时阈值，超时按"拒绝"语义关闭
- **FR-011**: 多个并发确认请求 MUST 被全部处理（按到达顺序排队展示），任何请求都不能因为同时出现而被丢失
- **FR-012**: 确认浮层与普通 Toast（成功/错误提示）MUST 独立管理生命周期，二者 MUST 互不覆盖、互不导致对方提前消失
- **FR-013**: 当"全部允许"或顶栏 Toggle 处于开启状态时，UI MUST 给出可见提示，让用户知道当前会话处于"无确认放行"模式
- **FR-014**: 现有的 `IntentConfirmationUI`（PM/Trial Agent）和 `ToolExecutionDialog`（手动填参数对话框）MUST 不受本变更影响
- **FR-015**: 系统 MUST 为每次 Assistant 高危确认决策写入脱敏结构化日志，字段至少包含 `request_id`、工具名、决策结果（同意/拒绝/超时/自动放行）、决策来源、等待耗时与关键参数摘要；日志 MUST NOT 记录完整工具参数或完整文件内容
- **FR-016**: 确认浮层 MUST NOT 提供普通关闭按钮，也 MUST NOT 因点击浮层外区域而关闭；每个确认请求只能通过"全部允许" / "同意" / "拒绝"或超时结束
- **FR-017**: 当用户在旧会话仍有已显示或排队中的 Assistant 高危确认请求时开启新对话，系统 MUST 将这些未决请求按拒绝/超时语义收敛并清空，且 MUST NOT 让旧会话请求泄漏到新对话

### Key Entities

- **AuthConfirmationRequest（确认请求）**：由 Worker 线程发起的一次高危工具确认请求，包含请求标识、工具名、参数摘要、发起时间；UI 完成决策或超时后回写结果，唤醒 Worker
- **AutoApproveScope（会话级豁免状态）**：当前会话是否启用"全部允许"的开/关状态；开启后覆盖 Assistant 的全部高危工具（`write_file` / `edit_file` / `exec`）；其生命周期等于一次对话；新对话开始时复位
- **AuthToastSurface（确认浮层）**：UI 层用于呈现单次确认请求的浮层组件，承载工具名、关键参数摘要与三按钮；关键参数摘要只展示目标路径或命令首行等关键字段，不展示完整文件内容；组件不提供普通关闭入口，只通过三种用户决策信号或超时结束

### Constraints & Compatibility

- **CC-001**: 现有 Worker → UI 的跨线程信号机制（基于 pyqtSignal 的 request_id 隔离 + Event 等待）MUST 保持不变；本 feature 仅替换 UI 端的展示形态，不改变线程模型
- **CC-002**: 高危工具的判定与现有清单一致，本 feature 不扩展也不收缩"哪些工具需要确认"
- **CC-003**: 浮层超时时间 MUST 不晚于 Worker 阻塞超时；二者关系应为同步收敛，不允许 UI 仍挂着但 Worker 已按超时返回
- **CC-004**: 普通 Toast（自动消失提示）行为不变；本 feature 引入的浮层与普通 Toast 通过独立的生命周期管理共存
- **CC-005**: “新对话”边界 MUST 同时复位会话级自动放行状态并清空旧会话未决确认，不允许跨会话保留确认 UI 或等待态

## Architecture Impact *(Mexemplar-specific)*

### Layer Impact

- [x] **UI** (`src/ui/`) — 新增确认浮层组件、改写 mixin 中的确认请求处理槽、对话顶栏新增 Toggle、QSS 新增样式
- [x] **Business** (`src/business/`) — `builtin_general_tools` 中新增"会话级豁免"开关与复位接口
- [ ] **Execution** — 不受影响
- [ ] **Data** — 不受影响
- [ ] **Recording** — 不受影响
- [ ] **Utils** — 不受影响

### Agent Impact

- 受影响的 Agent：**Assistant**（高危工具调用的 UX 替换）；PM / Programmer / Trial 不受影响
- 工具/handler：高危工具的内部调用流程与参数不变，仅其前置确认 UI 改变；不新增工具
- System prompt：无需变更
- Orchestrator dispatch：无需变更

### Data Store Impact

- SQLite / DuckDB：无变更
- Config (`unified_config`)：无新增配置键（"全部允许"是会话级内存状态，不持久化）
- Secrets：无新增

### Event Impact

- 新增/变更事件：本次以函数级状态 + UI 内部信号实现，**不引入跨模块 blinker 事件**；如确实需要跨模块同步顶栏 Toggle 与豁免状态，优先在 UI 层用回调直连两个入口

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 浮层弹出期间，用户在主窗口其它区域的点击响应延迟 ≤ 100ms（与无浮层时无明显差异），证明非阻塞特性
- **SC-002**: 在同一会话内连续触发 10 次高危操作，开启"全部允许"后用户无需再做任何点击决策即可全部放行
- **SC-003**: 新对话开启后，前一会话的"全部允许"100% 失效——新对话的首次高危操作必然弹出浮层
- **SC-004**: 顶栏 Toggle 与浮层"全部允许"双向同步成功率 100%（任一处状态变化，另一处可视状态同帧或下一帧内同步）
- **SC-005**: 在 5 个 Worker 同时发起确认请求的压测下，所有请求都被排队展示并得到一次决策或一次超时，无请求丢失
- **SC-006**: 浮层超时关闭时间与 Worker 阻塞超时阈值的差值 ≤ 1 秒（确保不会出现"UI 还在挂、Worker 已超时"或反之的状态错位）
- **SC-007**: 同意、拒绝、超时、自动放行四类决策路径均产生 1 条结构化日志，日志字段完整且不包含完整工具参数或完整文件内容

## Assumptions

- 现有跨线程确认机制（`register_confirm_mechanism` + `set_confirm_result` + `_pending_confirms` + Event）保持稳定，本 feature 不重构其线程模型
- 现有 Worker 阻塞超时（120 秒，常量 `_CONFIRM_TIMEOUT`）作为浮层超时对齐的基线
- "高危工具"定义沿用 `write_file` / `edit_file` / `exec`；扩展高危集合不在本 feature 范围
- "会话/新对话"以现有"新对话"入口作为分界点（即触发现有对话清空逻辑的入口），无需为本 feature 引入新的会话语义
- 浮层视觉沿用警示色调（琥珀/黄系），与现有成功绿、错误红的提示色形成区分，避免误识别
- 浮层与普通 Toast 出现位置都在主窗口右下角；二者通过独立通道管理，不复用同一全局单例
- 多并发请求采用"排队展示"（FIFO）策略——这是 UX 最稳妥的默认；如果未来产品决定改为"合并展示"或"替换最新"，将作为后续迭代而非本 feature 一部分
- 顶栏 Toggle 落地位置在对话窗口顶栏右侧（非主窗口全局菜单），与对话上下文绑定，避免给用户造成"全局开关"的误解
