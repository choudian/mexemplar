# Exemplar 架构讨论记录 v1

## 讨论背景

当前项目架构存在多个问题，开发者感到困惑不知如何继续。本文档记录了对这些问题的讨论和初步结论。

## 一、待解决问题清单（按优先级分层）

### 第一层：架构核心（决定项目能不能做成）
1. **Agent 不像 Agent**——缺少分析数据的工具，缺少思考过程，一次性出代码不现实
2. **Agent Loop 怎么设计**——循环结构、流转逻辑
3. **Agent 长短期记忆**——怎么做
4. **录制数据够不够用**——现有采集方式能否支撑 Agent 完成代码开发
5. **采集通道局限性**——插件拿不到的数据怎么办（CDP 不想用，因为绑定 Chrome 太死）

### 第二层：工程质量（决定项目能不能健康迭代）
6. **测试与流程割裂**——单元测试通过不代表端到端流程能跑通
7. **文档混乱**——文档多但有用的少，缺乏组织

### 第三层：对外表达（决定别人能不能理解你在做什么）
8. **UI 术语不亲民**——界面上的概念生涩难懂
9. **README 表达不清**——别人看了不明白项目要做什么

## 二、当前架构的核心问题

### 现有 Agent 流程（线性、一次性）

```
intent_analysis → intent_confirmation → code_generation → END
```

问题：
- 这是一条直线，不是循环
- 代码生成和试用（tool_trial/）完全割裂，Agent 生成完代码就"下班了"
- 确认放错了位置——用户没看到代码运行结果前很难给有价值的反馈
- Agent 缺少对录制数据的深度利用，只拿到压缩后的摘要就盲写代码

### 应该有的结构：两个循环

```
┌─────────────────────────────────────────────┐
│            循环1: 需求确认                     │
│                                              │
│  录制数据 → Agent 分析目标 → 跟用户对话确认     │
│                ▲                  │           │
│                └── 没对齐 ────────┘           │
│                                              │
│                    对齐了 ─────────────────────┼──┐
└─────────────────────────────────────────────┘  │
                                                  ▼
┌─────────────────────────────────────────────┐
│            循环2: 代码迭代                     │
│                                              │
│  代码生成 → 试用执行 ──→ 报错 → 自动修复 ──┐   │
│     ▲                                    │   │
│     └────────────────────────────────────┘   │
│     ▲           │                            │
│     └── 用户反馈 ┤                            │
│        "结果不对" │                            │
│                  ├── 没问题 → 保存为工具 ✅     │
└─────────────────────────────────────────────┘
```

**以上为早期设计，已被以下更新版本替代。**

### 更新后的完整流程

```
产品经理 Agent ←→ 用户确认需求（循环，分类分批问）
       │         停止条件：Agent 觉得够了 或 用户说够了
       ▼ 输出需求 + 参数
程序员 Agent → 分析录制数据 → 写代码 → 生成工具（待验证状态）
       │
       ▼
用户试用（自然语言对话 → 提取参数 → 执行工具 → 展示结果）
       │
       ├── 成功 × 3 → 工具发布 ✅
       │
       └── 失败 → 用户以对话形式反馈
                  → 产品经理 Agent 分诊（统一对外角色）
                    ├── 代码问题（需求明确但没实现到位）
                    │     → 恢复程序员 Agent 会话 + 反馈信息
                    │     → 程序员修代码
                    │     → 替换旧版本，成功次数清零
                    │
                    └── 需求问题（需求本身不清楚或有误）
                          → 恢复产品经理 Agent 会话
                          → 跟用户重新确认需求
                          → 然后重写代码
```

### 关键设计决策

1. **两个循环不是连续的**——代码生成后工具进入列表，用户随时试用，试用和生成之间可能隔很久
2. **两个 Agent 的会话都必须能保存和恢复**——因为试用反馈可能在生成之后很久才发生
3. **产品经理是统一对外角色**——用户始终跟产品经理对话，不需要自己判断问题该找谁
4. **产品经理做分诊**——对比用户反馈和原始需求，判断是代码问题还是需求问题
5. **试用通过对话进行**——用户用自然语言表达，Agent 从对话中提取参数调用工具，而不是让用户填表单
6. **试用成功3次后发布**——工具修改后成功次数清零
7. **需求确认分类分批提问**——不一次全问也不一个一个问
8. **停止条件双向**——Agent 觉得够了或用户说够了，任一方都可以结束需求确认

## 三、两个 Agent 分工

### 决策：拆分为两个 Agent

不用一个 Agent 从头做到尾，而是分成两个角色各司其职：

- **产品经理 Agent**：负责循环1（需求分析），像一个懂产品的人做需求调研
- **程序员 Agent**：负责循环2（代码开发），拿到需求后自己去录制数据里挖技术细节

### 为什么拆分

- 一个 Agent 又要像产品经理思考又要像程序员写代码，prompt 很难调，两种思维模式互相干扰
- 各自职责清晰，prompt 聚焦
- 现实中也是产品经理写需求交给开发，信息损耗通过规范化交接来降低

### 交接内容

产品经理 Agent 输出给程序员 Agent 的是：

1. **清晰的最终目标**——例如"用户希望百度搜索某个关键词，获取前100条详情页的内容"
2. **参数列表**——哪些是变量（用户每次使用时输入），哪些是固定值

参数信息包含：
- 参数名
- 描述（是什么）
- 录制时用的值（程序员可用来做测试）
- 是固定值还是变量（由产品经理跟用户确认）

注意：可选值范围（如下拉框的所有选项）不需要产品经理给出，程序员自己去页面数据里看就行。产品经理只需确认这个字段是写死还是参数化。

### 参数化的职责分配

- **主要参数由产品经理确定**——产品经理跟用户聊，用户知道哪些值每次都变
- **技术参数由程序员补充**——如翻页数量、超时时间等偏技术的配置项
- 不需要一次搞全，允许程序员在开发过程中追加

## 四、产品经理 Agent 的工具集（阶段一：需求分析）

### 设计思路

产品经理 Agent 的人设是一个**懂需求分析的产品经理**，不是程序员。它关心的是用户的真实场景和痛点，不是技术实现。

如果让一个人来做这件事，他会：看一遍用户操作 → 心里形成猜测 → 跟用户确认 → 用户纠正 → 再看某些细节 → 再确认... 循环直到理解透彻。

核心能力：**看、猜、问、再看**。

### 工具列表

| # | 工具 | 用途 | 说明 |
|---|------|------|------|
| 1 | 查看操作流程概览 | 了解用户从哪到哪，做了几步，每步什么操作，页面跳转轨迹 | URL 变化作为概览的一部分，不需要单独工具 |
| 2 | 查看操作元素详情 | 某一步操作的目标元素是什么，属性、文本内容 | 元素上的文本（如按钮叫"查询"）已足够理解操作语义，不需要看网络请求 |
| 3 | 查看元素上下文 | 兄弟元素、父容器、周围文本内容 | 判断是列表页还是详情页，发现可能的列表操作模式 |
| 4 | 查看页面截图 | 最直观的理解方式，多模态分析 | **非常规手段**，两种触发方式：(1) 多轮对话对不齐时 Agent 自动触发兜底；(2) 用户主动要求"你看看截图" |
| 5 | 跟用户对话 | 把分析结果转化为用户能懂的问题去确认 | Agent 的能力边界是提出有依据的问题，而不是替用户做决定 |

### 关于截图工具（#4）的成本控制

- 截图走多模态，token 消耗大、响应慢
- 正常情况下 1/2/3 的文本数据够用，成本低速度快
- 截图是兜底手段，不是常规手段

### 关于网络请求

- 需求分析阶段**不看网络请求**
- 原因：有的网站点一下出100个请求，噪声太大
- 元素文本内容已足够理解操作语义（网站上的文字是给真人用户看的，不会含糊不清）
- 网络请求留给程序员 Agent 在代码开发阶段使用

### 列表操作的识别策略

- Agent 通过查看元素上下文（工具#3），发现周围有结构相似的兄弟元素时，**怀疑**是列表操作
- 不确定就直接问用户："你是想对列表里的每一项都做这个操作，还是只针对你点的这几个？"
- 不需要 Agent 自己做复杂的列表检测算法

### 录制数据需求

以上工具对录制数据的要求：
- 操作序列（类型、时间戳、URL）——已有
- 元素属性和文本——已有（dom_element）
- 兄弟元素/上下文——已有（sibling_snapshots），需确认够不够细
- 页面截图——已有
- **下拉框/选择框的所有选项**——需要确认录制时是否采集了，这对参数化很重要

## 五、程序员 Agent 的工具集（阶段二：代码开发）

程序员 Agent 拿到需求 + 参数列表后，自己去录制数据里挖技术细节，决定技术方案，编写代码。

### 工作流程

1. 先看操作流程——用户做了什么
2. 逐步看每步操作产生的数据——网络请求、DOM 结构等
3. 基于数据判断技术路线——能走 API 就走 API，API 不行（如请求加密）就走浏览器自动化
4. 写代码

### 工具列表

| # | 工具 | 用途 |
|---|------|------|
| 1 | 查录制数据 | 一个工具覆盖所有数据查询需求（操作流程、网络请求、DOM、页面结构等），Agent 想看什么就查什么 |
| 2 | 语法校验 | 验证代码有没有语法错误和导入问题。不是真正执行（执行需要用户参数，属于试用阶段的事） |

### 关键设计：不拆分多个查询工具

早期曾考虑将数据查询拆成多个工具（操作流程概览、网络请求列表、请求详情、DOM 详情、页面结构概览），但最终决定合为一个工具。原因：拆成多个工具等于让 LLM 去选工具，增加复杂度。查什么、怎么分析本来就是 Agent 自己的事，一个灵活的查询工具就够了。

### 关键设计：需求常驻上下文

需求和参数列表**不是工具**，而是始终在上下文里的锚点。原因：
- 程序员写代码过程中需要反复回看需求
- 做成工具按需查看会有遗忘风险
- 需要定期对照检查当前操作是否偏离最终目标，防止钻进技术细节后跑偏

### 录制数据的新需求：页面骨架

程序员需要查看页面整体结构（类似 F12 DevTools 的 Elements 面板），因此录制时需要存储**页面骨架**：

- **存什么**：标签名、class、id、关键属性、层级关系、文本内容
- **存的时机**：每次用户操作后，如果 DOM 发生了变化就存一份（因为 SPA 单页应用中大量操作不跳转页面但 DOM 会变）
- **文本内容**：直接存，不截断（页面上的元素文本本身就是短的，不会太大）
- **数据量**：可控，骨架信息不大

### 顶层设计原则：上下文精准控制

> **这是整个 Agent 架构最关键的设计原则**

在有限的上下文窗口里，放对的信息。放多了 LLM 被噪声干扰效果变差，放少了信息不足做不出好判断。

这个原则贯穿整个 Agent 系统：
- 查录制数据时按需查字段，不是 `SELECT *`，避免不需要的大字段占上下文
- 短期记忆的引用机制——大块数据用指针引用，按需加载
- 产品经理分类分批提问——不一次把所有问题塞给用户
- 程序员不需要全局记忆——不放无关信息
- 产品经理给程序员的交接信息——只给需要的，不给所有分析过程

**上下文控制是当今 Agent 成功与否的关键。**

## 六、Agent Loop 设计

### 参考项目

参考了 nanobot（D:\work\code\opensource\nanobot\nanobot\agent）的 Agent 架构设计。nanobot 的核心 Loop 不到 80 行代码，支撑完整的多轮对话、工具调用、子 Agent、记忆管理。

### 核心 Loop：简单的 while 循环

废掉 LangGraph，自己实现。核心结构与 nanobot 一致：

```
while not done and iteration < max_iterations:
    response = llm.chat(messages, tools)
    if response.has_tool_calls:
        执行工具 → 结果加回 messages → 继续
    else:
        输出结果 → 结束
```

**不需要状态机。** 复杂度应该在 Agent 的能力上（工具、prompt、记忆），不在 Loop 本身。Loop 就是个调度器，越简单越好调试。

### 用户交互：靠消息历史串联，不在 Loop 内部暂停

LangGraph 用 interrupt 机制在 Loop 内部暂停/恢复。我们不需要这么做。

每一轮用户交互就是一次独立的 Loop 调用：
```
用户触发 → PM Agent 分析录制数据 → 调用"问用户"工具 → Loop 结束
                                                        ↓
用户回答 → 新消息进来 → PM Agent 看到历史上下文 → 继续分析 → 再问或结束
```

靠消息历史自然串联上下文，比 LangGraph 的 interrupt 简单得多。

### 双 Agent 统一框架

两个 Agent 用**同一套 Loop 代码**，只是配置不同（prompt、工具集）。不为每个 Agent 单独写代码。

### 双 Agent 调度

**PM Agent 是统一对外角色，也是调度者。** 不加额外的协调层。

- 用户始终跟 PM 对话
- PM 决定什么时候把任务交给程序员
- 以后要加新 Agent 角色，通过通用的 Agent 注册/派发机制扩展（类似 nanobot 的 SubagentManager 模式）

### PM 与程序员的交接

**需求确认完毕后，PM 展示需求摘要让用户确认，用户确认后再派发给程序员。** 以对话方式确认，不用按钮。PM 的 prompt 约束它必须展示摘要并等用户确认后才能派发。

交接数据为**结构化 JSON**：

```json
{
  "goal": "百度搜索关键词，获取前100条结果的详情页内容",
  "recording_id": "xxx",
  "parameters": [
    {
      "name": "keyword",
      "description": "搜索关键词",
      "recorded_value": "Python 教程",
      "type": "variable"
    }
  ]
}
```

### 代码 Review

程序员 Agent 写完代码后，加一层 LLM Review 做质量保证：

- **不是一个独立 Agent**，就是一次 LLM 调用——Review 不需要工具、不需要循环、不需要记忆
- Review 只关注硬伤（逻辑错误、参数漏用、明显 bug），不管代码风格
- **最多打回 3 次**，超过直接入库（pending 状态），后面还有用户试用兜底
- 打回时带修改意见，反馈给程序员 Agent 的上下文

### Agent 之间的衔接

Agent 之间的衔接方式尚未最终确定。初步方向：

- **不用 pipeline 等硬编码流程**——太死，不够灵活
- **事件机制是候选方向**——每个 Agent 完成后发事件，监听器决定下一步。数据（如 review 反馈）通过事件携带
- 具体方案待实现时细化

### 完整流程

```
用户触发录制 → 录制完成

→ PM Agent Loop（独立运行）
    → 分析录制数据 → 跟用户确认需求（多轮对话）
    → 需求确认完毕 → 展示摘要 → 用户确认
    → 输出结构化 JSON（目标 + 参数列表）
    → PM Loop 结束

→ 程序员 Agent Loop（独立运行）
    → 接收需求 JSON → 分析录制数据 → 写代码
    → LLM Review（最多打回3次）
    → 工具入库（pending 状态）
    → 程序员 Loop 结束

→ 用户试用（可能隔很久）
    → 成功 ×3 → 工具发布
    → 失败 → PM Agent Loop（新的独立运行）
        → 分诊：代码问题 or 需求问题
        → 代码问题 → 恢复程序员 Agent Loop（带上反馈）
        → 需求问题 → 恢复 PM Agent Loop → 重新确认 → 再派程序员
```

## 六-b、Agent 记忆机制

### 记忆分类

不按传统的"短期/长期"分，而是按实际需求分：

**短期记忆（单次任务执行内）**
- 当前任务过程中的思考、推理、每一步执行的结果
- 执行结果采用**引用机制**——记忆中只保留摘要和引用指针，需要看具体内容时（如1000行代码、大段执行输出）再去加载引用的原始数据
- 目的：解决上下文窗口不够用的问题，避免大块数据占满记忆

**长期记忆**
- **会话级**：某次完整任务的所有上下文（用户下达的任务、模型的反馈、任务执行过程的摘要）
- **全局级**：暂不实现，等项目跑通有真实用户数据后再加

### 记忆的使用范围

| Agent | 短期记忆 | 会话级长期记忆 | 全局级长期记忆 |
|-------|---------|--------------|--------------|
| 产品经理 | ✅ 当前对话的上下文 | ✅ 这个工具的需求历史、修改记录 | 📋 暂不实现 |
| 程序员 | ✅ 当前写代码的思考链 | ✅ 这个工具的历次修改和试用反馈 | ❌ 不需要全局视野 |

### 短期记忆：引用机制

**核心思路**：Agent 的回复文字保留（天然就是摘要），工具返回的大块原始数据在 N 步之后替换成指针。

替换前：
```
Agent: 我来查一下这个页面的网络请求
Tool result: {完整的 200KB 响应数据...}
Agent: 发现这个 API 返回了 JSON，里面有个 data 字段包含列表数据
```

替换后：
```
Agent: 我来查一下这个页面的网络请求
Tool result: [引用#1 - 可通过 load_reference(1) 查看]
Agent: 发现这个 API 返回了 JSON，里面有个 data 字段包含列表数据
```

- **触发时机**：固定步数（默认 3 步），可配置
- Agent 需要回看细节时，调用 `load_reference` 工具加载原始数据
- 不需要额外 LLM 调用生成摘要，Agent 自己的分析文字就是摘要

### 会话级记忆：消息类型系统

对话历史存库，每条消息带**类型标签**。类型是可扩展的，初步识别出以下几类：

- **普通消息**——Agent 回复、用户输入，正常保留
- **压缩消息**——标记了"这条是对第 X-Y 条消息的摘要"，被摘要的原始消息可归档
- **引用消息**——工具返回结果被替换成指针，原始数据存在外部

类型不限于以上三种，具体有哪些类型、怎么命名，等实现时从实际需求倒推。

加载上下文时根据类型决定处理方式：
- 普通消息直接加载
- 压缩消息直接加载（本身就是精简的）
- 引用消息加载指针形式，Agent 需要时再用工具取原始数据

### 关键决策

1. **全局记忆暂不实现**——等项目跑通、有真实用户数据后再加
2. **引用机制是短期记忆的核心设计**——大块数据不进上下文，按需加载
3. **消息类型可扩展**——不写死三种，留好扩展口

## 七、录制数据与采集通道

### 采集通道结论：扩展路线，不需要 CDP

- 当前使用 Chrome 扩展（content_script + background service worker）采集数据
- 早期曾用 CDP + Native Host 方案，后因浏览器兼容性切换到纯扩展方案
- **扩展覆盖所有 Chromium 系浏览器**（Chrome、Edge、Brave、Arc、Opera），与 CDP 覆盖范围一致
- 当前扩展已能采集之前 CDP 采集的所有数据，没有能力退化
- **结论：不需要引入 CDP**

### 扩展的能力边界

**能拿到的：**
- DOM 事件/元素/属性（content_script）
- DOM 树快照（dom_serializer.js）
- 兄弟元素上下文（sibling_snapshots）
- 页面截图（chrome.tabs.captureVisibleTab）
- 网络请求 URL/method/type/请求头/请求体（webRequest API）
- 响应头、状态码（webRequest API）
- **响应体（response body）**——通过 content_script 中 monkey-patch fetch/XMLHttpRequest 实现

**拿不到的：**
- **WebSocket 消息帧**——只能看到握手，消息内容拿不到
  - 解决方案：与 fetch/XHR 同样思路，monkey-patch WebSocket 构造函数即可
  - 优先级低，等遇到 WebSocket 重度依赖的场景再加
- 非 fetch/XHR 的响应体（浏览器直接发起的页面加载、图片加载等）——一般不需要

### 录制数据够不够用

**产品经理 Agent——够用。** 所需数据（操作序列、元素详情、兄弟元素上下文、截图）全部已有。

**程序员 Agent——大体够用，有两个明确缺口：**

#### 缺口1：下拉选项采集

用户录制时只选了一个值，但参数化需要知道所有可选值。

- 原生 `<select>` 的 `<option>` 虽在 DOM 中，但受 DOM 树序列化深度限制可能被截断
- 自定义下拉组件（div + ul/li 模拟）只有展开时才渲染到 DOM，操作完成后选项列表已移除，DOM 快照拿不到
- **解决方案**：在用户交互触发下拉展开时，专门采集所有选项的 text + value
- 需要覆盖的控件类型：原生 `<select>`、自定义下拉组件（通过 ARIA role="listbox" + 结构相似兄弟元素启发式识别）
- Radio 按钮组、Checkbox 组不需要特殊处理，所有选项始终在 DOM 中

#### 缺口2：DOM 树快照深度不够

- 当前 `dom_serializer.js` 的 `capturePageDOM` 使用 maxDepth=5
- 现代网站 DOM 嵌套常超过 10 层，5 层不足以让程序员 Agent 看到完整的页面结构
- **解决方案**：加大 maxDepth，数据量增大可接受

### 总结

| 项目 | 状态 |
|------|------|
| 采集通道 | ✅ 扩展路线够用，不需要 CDP |
| 产品经理 Agent 所需数据 | ✅ 全部已有 |
| 程序员 Agent 所需数据 | ⚠️ 需补充下拉选项采集 + 加大 DOM 树深度 |
| WebSocket 支持 | 📋 方案明确，按需添加 |
