# 技能组合规划草案

> 日期：2026-04-10
> 范围：技能管理 / 技能组合 / Assistant 调用
> 定位：讨论稿，先定产品定义，再决定实现方式

---

## 一、当前核心判断

这件事现在最大的分歧，不是“能不能做”，而是要把它定义成什么：

- 工具集 / 工具箱
- 工作流

我现在更建议的结论是：

**不要二选一。对外统一叫“技能组合”，内部支持两种模式。**

也就是：

- 用户看到的是一个更大的技能
- 系统内部可以按不同模式执行这个技能

这样可以避免一开始就把产品锁死成：

- 纯工具箱，太松
- 纯工作流，太重

---

## 二、推荐定义

### 2.1 统一概念：技能组合

产品层统一用一个概念：

- **技能组合**

它本质上就是：

**由多个已有技能组成的、更大的可调用能力。**

这个能力对用户来说仍然像一个普通技能：

- 可以命名
- 可以描述用途
- 可以保存
- 可以展示
- 可以被 Assistant 调用

### 2.2 内部分两种模式

虽然产品上统一叫“技能组合”，但内部建议区分两类：

#### 1. 范围型技能组合

更接近“有边界的工具箱”。

特点：

- 用户圈定一组技能
- 用户定义这个组合大概能解决什么问题
- 模型在这个范围里自主选择和组合
- 不要求用户显式配置顺序

适合场景：

- 一组能力围绕同一个任务域
- 每次执行未必都要用到全部成员技能
- 更像“场景技能包”

#### 2. 顺序型技能组合

更接近“轻量工作流”。

特点：

- 内部存在较明确的执行先后
- 某一步通常依赖前一步结果
- 更强调稳定性和可复现
- 可以由系统推荐顺序，也可以允许后续人工调整

适合场景：

- 查数据 -> 生成内容 -> 执行动作
- 明显存在前置依赖
- 需要比较稳定的产出

---

## 三、已确定的产品方向

### 3.1 V1 不做纯工作流产品

第一版不建议把它做成：

- 画流程图
- 拖节点
- 配分支
- 配条件
- 强制排顺序

原因：

- 太技术
- 太重
- 普通用户会被吓退
- 很容易把产品带成低代码编排平台

这不是当前阶段最需要的。

### 3.2 V1 也不做完全无约束的自由工具箱

如果只是让用户随便勾几个技能，然后完全交给模型现场发挥，也会有问题：

- 模型不一定稳定
- 同一个目标可能每次走法不一样
- 失败后很难解释到底为什么这么调
- 一旦涉及强依赖顺序，容易出错

所以 V1 也不能是完全放飞的“自由工具箱”。

### 3.3 V1 推荐方案

我建议第一版定成：

**技能组合 = 有范围约束的工具箱，必要时可切成顺序型。**

换句话说：

- 默认模式是 `范围型`
- 创建组合时允许用户直接选择是否使用 `顺序型`
- `推荐顺序` 仅在 `顺序型` 下出现
- 不默认要求用户配置顺序

这条路最平衡。

## 四、用户心智建议

用户创建技能组合时，不应该让他觉得自己在“设计流程”。

更好的感受应该是：

> 我把几个相关技能打包成一个更大的能力，以后直接用这个大技能做事。

所以用户主路径建议只保留这些动作：

1. 选几个已有技能
2. 给这个组合起名字
3. 写一句这个组合是做什么的
4. 填写适用场景说明
5. 选择是否允许 Assistant 调用
6. 选择模式：范围型 / 顺序型
7. 保存

高级能力先藏起来，不要一开始就暴露：

- 执行顺序
- 参数映射
- 失败策略
- 必经步骤
- 可跳过步骤

---

## 五、顺序问题怎么处理

这是这次最关键的问题。

### 5.1 不能把“用户不配顺序”理解成“系统不需要顺序”

很多技能组合在真正执行时，内部还是会有先后关系。

比如：

- 先查
- 再生成
- 最后执行

所以顺序并没有消失，只是不一定让用户来配。

### 5.2 不建议把最终顺序完全交给模型

如果完全交给模型决定：

- 体验很轻
- 但稳定性不够
- 调试困难
- 同样的组合可能每次行为不一致

这适合开放探索，但不适合要落到产品能力的场景。

### 5.3 也不建议默认把顺序全部交给用户

如果要求用户显式排顺序：

- 复杂度立刻上升
- 产品会变得很像流程编辑器
- 普通用户理解成本太高

### 5.4 推荐中间方案

建议顺序采用：

**系统推荐，必要时用户确认。**

也就是：

1. 用户先只选技能
2. 如果组合是 `顺序型`，并且用户勾选了 `生成推荐顺序`，系统再根据技能能力、依赖关系、描述语义生成推荐顺序
3. 默认允许用户在创建时选择是否采用顺序型
4. 只有 `顺序型` 才展示推荐顺序相关设置
5. 一旦用户确认过，就把这个顺序保存下来

这个方案的好处：

- 用户门槛低
- 系统可控
- 模型有发挥空间
- 结果更稳定

## 六、推荐的双模策略

### 6.1 范围型

范围型是已确定的 V1 默认模式。

它的定义可以是：

> 用户圈定一组技能和一个目标范围，模型在这个范围内择机调用。

特点：

- 不要求全部成员技能都执行
- 不要求用户配置显式顺序
- 更适合 Assistant 使用
- 更像“场景能力包”

但为了避免完全失控，范围型仍然要有清晰边界：

- 只允许使用当前会话中用户选定的技能或技能组合
- LLM 可以自主选择调用哪个或哪些成员技能
- 如果这些成员技能都不需要，也可以不调用
- 内置工具可以使用，但优先级最低，只作为兜底

也就是说：

- 对外轻
- 对内有边界

### 6.2 顺序型

顺序型适合那些已经比较稳定的大动作。

它的定义可以是：

> 技能组合内部存在一个相对固定的执行顺序，系统按这个顺序或接近这个顺序执行。

特点：

- 更稳定
- 更可复现
- 更适合强依赖任务
- 更容易做内部执行日志和问题定位

### 6.3 两者关系

我建议不是把它们做成两个完全不同的产品，而是：

- 同一个“技能组合”对象
- 带一个 `mode`

比如：

- `range`
- `ordered`

其中：

- `range`：偏工具箱
- `ordered`：偏工作流

---

## 七、数据模型建议

我还是建议技能组合独立于现有 `Tool`。

原因：

- 现有 `Tool` 更适合作为原子技能
- 教学 / 试用 / 发布链路默认它是单体能力
- 技能组合后面会有自己的模式、成员关系、顺序信息

建议新增一个实体：

- `skill_compositions`

第一版字段建议：

- `composition_id`
- `name`
- `description`
- `scenario_description`
- `status`：`draft / published / offline`
- `mode`：`range / ordered`
- `assistant_enabled`
- `needs_review`：`true / false`
- `created_at`
- `updated_at`

成员关系建议单独建表，而不是塞 JSON：

- `skill_composition_members`
- 字段建议：`composition_id`、`tool_id`、`selected_order`、`execution_order`

这里的关键点是：

- 技能与技能组合是多对多关系
- 成员关系建议走独立关系表
- V1 同一技能在同一技能组合中只能出现一次
- `selected_order` 表示用户选择成员技能时形成的顺序，主要用于 UI 展示和弱信号保留
- `execution_order` 表示顺序型下推荐或最终确认后的执行顺序
- `range` 模式下，`execution_order` 可以为空
- `mode` 用来决定执行策略
- `scenario_description` 建议必填，供 Assistant 发现和理解用途
- `needs_review` 用于标记成员技能发生变更后该组合需要人工复核

补充说明：

- `range` 模式下，`selected_order` 仍然可以保留，主要表示用户选择顺序
- `range` 模式不依赖 `execution_order`
- `ordered` 模式下，真正执行以 `execution_order` 为准

---

## 八、执行模型建议

建议新增一个统一入口，例如：

- `CompositeSkillExecutor`

这层做的事不是跑“流程图”，而是运行“技能组合”。

执行时可以按模式分支：

### 8.1 `range` 模式

执行逻辑更偏：

- 先理解目标
- 再判断哪些成员技能适合调用
- 严格限制在当前会话已选择的技能 / 技能组合边界内
- 只有所选能力不足以完成任务时，才降级使用内置工具
- 最后汇总结果

这里“内置工具优先级最低”的实现建议是：

- 执行器先只暴露当前会话中用户选定的技能 / 技能组合
- 只有判定这些能力不足以完成任务时，才追加内置工具作为兜底能力

范围型的失败策略建议明确为：

- 选哪些能力、是否切换到其它成员能力，由 Agent 判断
- 超时、异常、最大重试次数这类硬边界由执行器统一控制
- Agent 可以在成员能力范围内重新尝试其它路径
- 但不允许无界重试或越权调用未选能力

### 8.2 `ordered` 模式

执行逻辑更偏：

- 按最终确认后的顺序执行
- 每一步拿到结果后，由 Agent 自由整理成下一步参数
- 对每一步做结果记录

补充说明：

- 这里的结果传递不做固定结构约束
- 交由 Agent 根据上一步结果和下一步参数要求自由整理
- 如果前一步没有可供消费的输出，说明这个组合设计通常存在问题
- Agent 仍然可以尝试继续完成任务
- 如果最终无法继续完成，则停止执行并明确提示用户当前组合不合适
- 无论最终是否勉强完成，都要在结果中标记该组合设计存在问题

顺序型的 V1 默认失败策略建议为：

- 单步失败后，先允许 Agent 在当前步骤内做一次本地恢复尝试
- 如果恢复失败，则默认停止后续依赖步骤，不继续硬往下串
- 最终结果里要明确标记失败步骤、停止原因，以及该组合设计是否存在问题

### 8.3 执行快照

虽然 V1 允许直接编辑已发布技能组合，但执行时建议采用快照思路：

- 每次执行开始时，先读取并冻结当前技能组合定义和成员关系
- 本次执行全程使用这份快照
- 执行中途即使用户编辑了技能组合，也只影响后续新执行，不影响当前运行

这样可以降低“线上编辑”和“正在执行”之间的一致性风险。

V1 的快照深度建议为：

- 冻结技能组合元数据
- 冻结成员关系和执行顺序
- 同时读取并冻结成员技能当前的定义信息（名称、描述、参数 schema、执行入口）

但这里的“冻结”先只针对本次运行的内存执行计划：

- 不要求把完整快照持久化成历史版本
- 也不要求引入正式的版本系统

### 8.4 并发执行

V1 建议允许同一个技能组合被并发执行，但边界要写清楚：

- 每次执行都有独立的运行上下文
- 每次执行都基于自己的内存快照
- 技能组合层不额外做全局互斥

需要明确的限制是：

- 成员技能本身是否支持并发，仍由成员技能自己的实现能力决定
- 技能组合层只保证组合定义和上下文隔离，不额外承诺成员技能的并发安全

## 九、Assistant 集成建议

这一块反而很清楚。

Assistant 不需要知道用户创建的是“工具箱”还是“工作流”。

它只需要知道：

- 这是一个可调用技能
- 它叫什么
- 它大概擅长做什么
- 它需要哪些输入

所以建议：

- 原子技能继续作为基础 Tool 暴露
- 技能组合作为虚拟 Tool 暴露
- 对 Assistant 来说，二者都是能力

注册机制建议单独走一层适配，而不是复用原子技能的发布链路：

- 原子技能仍走现有 Tool 注册链路
- 技能组合从 `skill_compositions` 读取后，经由一层适配器生成虚拟 `ToolDefinition`
- 会话组装可用能力时，同时拉取原子技能和已发布的技能组合

虚拟 Tool 的 function calling schema 建议 V1 固定成：

- `task`：必填，表示当前要完成的任务描述
- `context`：选填，补充上下文说明

命名建议：

- 内部 function name 使用带前缀的稳定名称，例如 `comp_<short_id>`
- 对用户展示仍然使用技能组合名称
- 如果原子技能与技能组合同名，内部靠不同前缀规避冲突

也就是说，Assistant 调用技能组合时，不直接暴露成员技能的参数集合，
而是把“任务描述”传给技能组合，再由内部执行器和 Agent 去做成员技能选择与参数整理。

会话边界补充：

- 会话里可用的能力集合，由“用户显式选择的技能 + 用户显式选择的技能组合”共同决定
- Assistant 不能越过这个集合随意调用其它外部技能
- 只有内置工具保留低优先级兜底权限

内部差异只体现在执行器上：

- 原子技能直接执行
- 技能组合进入 `CompositeSkillExecutor`

## 十、UI 建议

### 10.1 命名

对外建议叫：

- 技能组合

不建议叫：

- 工作流
- 编排
- 流程设计器

### 10.2 创建页

第一版建议做成“组合器”，不是“流程编辑器”。

主界面只要：

- 技能列表
- 已选成员
- 名称
- 描述
- 适用场景说明（必填，支持一键生成后再修改）
- 是否允许 Assistant 调用
- 模式选择：范围型 / 顺序型（可直接选）

高级设置再折叠起来：

- 推荐顺序（仅顺序型）

“适用场景说明”的一键生成建议基于下面信息生成初稿：

- 组合名称
- 组合描述
- 已选成员技能的名称和描述
- 当前模式（`range` / `ordered`）

### 10.3 默认交互

默认建议：

- 新建时默认 `范围型`
- 用户可在创建时直接切到 `顺序型`
- 只有 `顺序型` 才看到系统生成的推荐顺序

### 10.4 `顺序型` 的顺序交互建议

你这边已经明确了一个很重要的交互前提：

- 用户在选择成员技能时，本身就天然带有一个选择先后

所以顺序型不需要让用户再额外从零排一次。

建议交互如下：

1. 用户按自己的理解依次选择成员技能
2. 顺序型里提供一个勾选项：`生成推荐顺序`
3. 如果用户勾选了这个选项，保存时由模型生成一个推荐顺序
4. 用户可以基于这个推荐顺序再手动调整

当前已确定：

- **先做方式 B**

也就是：

- 顺序型里给一个勾选项：`是否生成推荐顺序`
- 不默认自动打断用户
- 更可控，也更适合第一版

---

### 10.5 “试一下”交互建议

“试一下”不只是一个按钮，还需要一个明确的执行上下文。

建议第一版这样定义：

- 用户点击 `试一下`
- 输入一段任务描述（可选再补一段上下文）
- 系统为这次试用创建一个临时、隔离的执行上下文
- 执行逻辑与正式运行一致，但不会额外触发发布、副作用写回等流程
- 结果展示以“最终结果 + 关键提示 + 顺序型步骤摘要”为主

这样它既能参考现有技能列表里的“试用”心智，又能适配技能组合更复杂的执行过程。

这里“隔离”的 V1 定义建议写清楚：

- 默认是真执行，不是 dry-run
- 组合状态不会因为“试一下”自动变化
- 不额外引入组合层的发布、副作用写回、状态迁移

但要明确一个现实边界：

- 如果成员技能本身会操作浏览器、写数据库或触发外部动作，试用时仍会真实执行
- 组合层本身不提供额外的副作用屏蔽能力
- 如果后续需要无副作用试用，需要成员技能自身支持 sandbox / mock / dry-run

## 十一、MVP 建议

### 11.1 第一版一定做的

- 从已发布技能中选择多个成员技能
- 创建技能组合
- 技能组合支持 `range` 和 `ordered` 两种模式
- 默认创建为 `range`
- 系统可为 `ordered` 生成推荐顺序
- 技能组合单独放一个 Tab 管理
- 技能组合支持增删改
- 技能组合与技能是多对多关系
- Assistant 可以发现并调用技能组合
- 适用场景说明必填，支持一键生成后修改
- 支持“试一下”
- 支持发布
- 组合列表支持下线、删除
- 只做内部执行记录，不单独做运行记录展示页

### 11.2 第一版不做的

- 拖拽流程图
- 分支 / 循环 / 条件节点
- 复杂参数映射编辑器
- 补偿回滚
- 组合嵌套组合
- 重新走一遍教学 / 试用 Agent
- 发布前强制试跑成功

## 十二、当前已确定结论

目前已经定下来的方向：

1. **对外统一概念叫“技能组合”。**
2. **内部不要在“工具箱”和“工作流”之间硬二选一。**
3. **技能组合支持两种模式：范围型、顺序型。**
4. **V1 默认做范围型，创建时可切到顺序型。**
5. **推荐顺序只在顺序型里出现。**
6. **技能组合单独放一个 Tab 管理。**
7. **技能与技能组合是多对多关系。**
8. **模式选择在创建时直接可选，不藏到高级设置。**
9. **顺序型下，用户选择成员技能时的先后顺序可以作为弱信号。**
10. **顺序型的推荐顺序可以作为一个显式可选项，而不是默认强打断。**
11. **会话边界内，只允许调用用户选中的技能 / 技能组合；内置工具低优先级兜底。**
12. **适用场景说明是必填项，支持一键生成后由用户修改。**
13. **`ordered` 模式中，上一步结果如何传给下一步，由 Agent 自由整理。**
14. **支持“试一下”和“发布”，但不要求试过才能发布。**
15. **技能组合相关数据表命名定为 `skill_compositions`。**
16. **`range` 模式下，不关心有没有用到成员技能，只关心任务是否完成。**
17. **“选择技能 / 选择技能组合”的会话入口本轮先不做，标记为 TODO。**
18. **`试一下` 的产品心智参考技能列表里的试用：用户试过没问题即可直接发布。**
19. **组合列表支持直接下线、删除。**
20. **发布后的技能组合先允许直接编辑线上版本，不做草稿覆盖发布版。**
21. **技能下线只限制被 `published` 状态的技能组合引用。**

这个方向的好处是：

- 对普通用户足够轻
- 对系统执行足够稳
- 不会把产品带成低代码平台
- 后续也能自然演进成更强的顺序型技能组合

## 十三、成员技能变更规则

这一块你已经给了比较明确的规则，建议直接按下面落：

### 13.1 删除技能

- 如果某个技能已经被技能组合引用，则不能直接删除
- 用户必须先把它从组合中移除，或者先删除相关组合

### 13.2 下线技能

- 规则与删除一致
- 如果技能仍被某个 `published` 状态的技能组合引用，则不能直接下线
- 如果只被 `draft` 或 `offline` 状态的技能组合引用，则允许下线

### 13.3 改名技能

- 允许改名
- 改名后提示哪些组合引用了这个技能
- 组合成员关系不变，不需要强制用户处理

### 13.4 参数或行为变更

- 如果成员技能的参数定义或行为发生变化，提示用户哪些组合受影响
- 由用户决定是否同步这些变化到对应技能组合中
- 第一版不做自动同步

提示时机建议明确为两层：

- 技能保存成功时，立即提示当前改动影响了哪些技能组合
- 同时给受影响的技能组合打上持久化标记，例如 `needs_review`

这样即使用户当场忽略提示，后续回到技能组合列表时也还能看到待处理状态

`needs_review` 的清除规则建议明确为：

- 用户打开技能组合并保存一次后自动清除
- 第一版不额外增加“确认已知晓”之类的单独动作

## 十四、范围型与顺序型的执行语义

你这次补充后，一个关键点已经很清楚了：

- 顺序型不是“只是保存一个顺序”
- 顺序型的本质是：**前一个工具的结果要整理成后一个工具的参数，再继续往下执行**

也就是说，顺序型更接近：

- LLM 做协调和参数整理
- Tool 真正完成动作

可以把这件事理解成：

**LLM 是润滑油 / 协调者，技能本身才是动作执行者。**

### 14.1 范围型

范围型更偏工具箱语义。

执行时的理解方式可以是：

- 本次任务只加载这组范围内的技能
- LLM 在这个范围内自主选择该用哪个或哪些技能
- 不要求所有技能都被调用
- 如果最终判断这些技能都不需要用，也可以不调用
- 不要求存在固定结果结构

所以范围型更像：

- 限定可用能力范围
- 由 LLM 自主选择和使用

更准确地说，这里的“自主组合”更接近：

> LLM 可以选择哪个或者哪些工具去完成这个任务；如果这些工具都不需要，也没问题，只要最终能完成用户任务即可。

这里“结果好不好”不由系统做强定义，更多由用户感知。

范围型里的能力选择和路径切换可以交给 LLM 判断，但超时、异常、最大重试次数等硬边界仍由执行器统一控制，具体口径以 8.1 为准。

### 14.2 顺序型

顺序型更偏工作流语义。

执行时的理解方式可以是：

1. 先匹配到这个技能组合
2. 按顺序执行成员技能
3. 每一步拿到结果后，由 LLM 进行整理
4. 将整理后的结果作为下一个技能的参数
5. 一直执行到结束

所以顺序型不是完全自由调用，而是：

- 有相对固定的步骤链
- LLM 负责衔接和参数转换
- Tool 负责具体执行

补充一个已确定规则：

- 如果某一步没有可供后续消费的输出，Agent 仍然可以尝试继续完成任务
- 如果最终无法继续完成，就需要明确提示用户当前这个技能组合不合适
- 无论最终任务是否勉强完成，都应该让用户知道这个组合设计存在问题

### 14.3 执行类型判定

这一点现在已经明确：

**Assistant 调用技能组合时，执行方式直接由用户选择的组合类型决定。**

也就是：

- `range` 模式：只加载这组 Tool，让 LLM 自主选择是否调用、调用哪些
- `ordered` 模式：按顺序执行，LLM 负责结果整理和参数衔接

这里不再由系统临时猜测“更像工具箱还是更像工作流”，而是以组合定义为准。

## 十六、组合状态建议

结合这轮讨论，技能组合的状态和动作建议先做得直接一些：

- `draft`
- `published`
- `offline`

推荐动作：

- 草稿态：`试一下`、`发布`、`删除`
- 发布态：`试一下`、`下线`、`编辑`
- 下线态：`试一下`、`重新发布`、`删除`

这里的“试一下”可以直接参考现有技能列表里的“试用”心智：

- 用户先跑一次
- 如果结果没问题，就直接发布
- 不需要再引入更重的审核流或额外状态机

这些点定下来之后，实现方案就可以进一步细化了。
