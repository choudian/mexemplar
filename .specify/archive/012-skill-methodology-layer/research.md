## D1: Token 计量条估算公式

**Decision**: 前端本地估算，公式：
```
estimated_tokens = ceil(equipment_listing_section_char_count / 4 * 1.2)
```
- 分母 4：英文每 token ≈ 4 字符（OpenAI tiktoken 与 Anthropic claude-tokenizer 经验值）
- 安全系数 1.2：保守上估，覆盖中文密集场景（中文 1 字符 ≈ 0.7-1 token，1.2 系数足以兜底）
- 不走 backend round-trip：避免装备 UI 每次勾选/调序触发后端调用

阈值（写入配置 `brain.skill.token_budget.warn_threshold` / `danger_threshold`，默认即用）：
- **绿色（健康）**: < 4096 tokens
- **黄色（警示）**: 4096–8191 tokens
- **红色（危险）**: ≥ 8192 tokens

**Rationale**:
- 4096 是大多数 LLM 上下文窗口的 1/8 量级，留余地给消息、tool result、压缩 buffer
- 8192 是单一上下文段的合理上限，超过即明显挤占 messages 序列空间
- 阈值偏保守，让用户在尚未触发实际崩溃时就能看到红色信号

**Alternatives Considered**:
- ❌ 每次后端调用计算 token：增加 round-trip latency，且后端也只能用同样估算公式（除非真正调 tokenizer）
- ❌ 调真实 tokenizer（如 tiktoken）：引入新依赖，但本场景对精度要求低，估算足够
- ❌ 不设阈值染色，纯展示数字：违背 FR-016a "按阈值分段颜色"要求

**实施位置**: `frontend/src/components/TokenBudgetMeter.tsx`，阈值从 `useSettingsStore` 读取（settings 在 P3 引入 `brain.skill.token_budget.*` 占位配置，但 Settings UI 本期不暴露）

## D2: Seed 文件位置与 Fail-Open Fallback 文本

**Decision**:
- Seed 文件路径：`src/business/brain/seed/how_to_create_skill_methodology.md`
- 配置 key：`brain.skill.seed_file_path`（默认即上述路径，可被 `UnifiedConfigManager` 覆盖）
- Fallback 文本：硬编码在 `SkillBootstrapService._FALLBACK_BODY` 常量，约 200 字 Markdown
- 读取失败时的 toast 文案："如何创建方法论 seed 文件读取异常（{原因}），已用 fallback 版本，请检查 seed 文件或在方法论屏编辑修复"

**Seed 文件内容大纲**（详细正文由实施阶段写出）:
1. 何时调 `create_skill_methodology`（用户对话里说"做成方法论"/"沉淀这套流程"等）
2. 怎么填字段（5 个字段语义 + trigger_conditions list 必须 ≥1 条）
3. 素材 zone 限制（仅 archive / failure，必须 ≥1 条）
4. **判重义务**（FR-027 / Edge Case "同名/同触发条件冲突"）：调工具前先扫装备清单，名称重合先阻断、触发场景重合先与用户对齐
5. **load 节制义务**（FR-017b / FR-027）：装备者调 `load_skill_methodology` 前先读 trigger_conditions list 判断触发场景命中再 load，不应单轮无差别 load 全清单

**Fallback 文本内容**:
```
# 如何创建方法论（系统应急 fallback）

⚠️ 该方法论的 seed 文件未能正确加载，当前为系统应急 fallback 版本。
请联系开发者修复 seed 文件，或在方法论屏手动编辑此条以恢复完整指引。

最低限度的判重义务：调用 create_skill_methodology 之前，先扫描你
system prompt 里的方法论装备清单，如果发现名称或触发场景与已有方法论高度重合，
必须先在对话里与用户对齐"要不要合并/择一"再决定是否产出新方法论。
```

**Rationale**:
- 路径放在 `src/business/brain/seed/` 而非 `docs/` 是因为 seed 是代码逻辑依赖（migration 引用），不是文档
- Fallback 在 `_FALLBACK_BODY` 类常量而非单独 fallback 文件——单独文件会引入第二个失败点
- Fallback 文本保留判重义务的最小骨架，保证 assistant 在 fallback 状态下仍不会失控产出重复方法论

**Alternatives Considered**:
- ❌ Seed 文件放在 `frontend/public/` 或运行时下载：复杂度提升，本期单用户产品无价值
- ❌ Fallback 为空字符串：违背 FR-027b "fallback 文本明确写出请联系开发者"
- ❌ Migration 阻塞应用启动直到 seed 修复：FR-027b 明确要求 fail-open 不阻塞启动

## D3: Supersede 链根归一化算法

**Decision**: `SkillRepository.resolve_chain_root(skill_id) → root_skill_id`
- 算法：从 `skill_id` 沿 `superseded_by` 指针**反向遍历**——查找哪个其它 skill 行的 `superseded_by` 指向当前 skill；如果找到则递归上溯，否则当前 skill 就是链根候选
- 实际实现：维护 `parent_id` 字段（被谁 supersede 出来）效率更高，避免反查
- 缓存：内存 LRU cache（capacity 256），按 skill_id 缓存 root_skill_id；supersede 写入时主动 invalidate 受影响链

**实施细节**: schema 新增 `parent_skill_id` 字段（被 supersede 出来时父版本的 id）+ 索引；链根判定 = `parent_skill_id IS NULL` 的节点。`origin` 字段在每个版本节点独立记录，不传播；链根判定不读 `origin`，而是结构上的"无父"。

**Rationale**:
- "链根 origin" 概念在 spec 中频繁用于判定保护（FR-027a）、默认装备例外（FR-014a）、计数继承（FR-041a）；高频读取要求高效
- 反向遍历 `superseded_by` 在并发 supersede 场景下不稳定（first-writer-wins 让链可能瞬时分叉再合并）；正向 `parent_skill_id` 是不可变的"出生"关系，更稳定
- 缓存让重复查询 O(1)，supersede 频次不高时 invalidate 开销可忽略

**Alternatives Considered**:
- ❌ 在每个版本上冗余存"链根 id"字段：节省查询但 supersede 时需要 propagate 更新到所有后续版本，违背"链根稳定不变"语义
- ❌ 每次查询都从当前节点反查：复杂度 O(链长)，且并发场景下需要事务隔离避免读到中间态

## D4: 装备清单段 YAML 渲染格式

**Decision**: 装备清单段在装备者 system prompt 中以独立 YAML block 注入，每条方法论一个二级 key：

```yaml
# 你已装备的方法论清单（按装备顺序）：
equipped_skills:
  - id: skl_abc123
    name: 周报生成方法论
    description: 把本周工作素材按"成果-阻塞-下周计划"三段式整理
    trigger_conditions:
      - 用户在请求做周报、月报、季报或复盘类总结时
      - 用户说"按上周素材整理一份"这种语义同型的请求
  - id: skl_def456
    name: 代码评审方法论
    description: 按"逻辑正确性-边界条件-命名清晰度-测试覆盖"四步走查
    trigger_conditions:
      - 用户请求评审一段代码或一个 PR 时
      - 用户说"看看这块写得对不对"类语义请求时
```

**装备者使用提示**（在 YAML block 前的 system prompt 指令段中说明）：
> 当你判断本轮用户请求触发了上述任一方法论的 trigger_conditions，调用 `load_skill_methodology(skill_id)` 工具拉取该方法论完整正文后再按其步骤行事。你不应该单轮内无差别 load 整个装备清单——按 trigger_conditions 判断后选择性 load。

**Rationale**:
- YAML list 原生形态保留 list 语义，LLM 易于按结构理解
- 每条方法论独立块让 LLM 可清晰跨方法论判断
- 与 Anthropic Agent Skills SKILL.md frontmatter 形态部分对齐（name / description / when_to_use ↔ trigger_conditions）

**Alternatives Considered**:
- ❌ JSON array：可读性差，LLM 处理 YAML 与人类文档语义场景更优
- ❌ Markdown table：trigger_conditions list 在 table 单元格里很难展示
- ❌ 拼成单串 description："损耗 list 语义"违背 FR-006 "trigger_conditions 渲染为 YAML list 原生形态"

## D5: `load_skill_methodology` 工具 Result Format

**Decision**: 工具 result 为 SKILL.md 标准文本（YAML frontmatter + Markdown body），由 handler 在 result 生成时把内部 list 转换为 frontmatter 期望的形态：

```markdown
---
name: 周报生成方法论
description: 把本周工作素材按"成果-阻塞-下周计划"三段式整理
when_to_use: |
  - 用户在请求做周报、月报、季报或复盘类总结时
  - 用户说"按上周素材整理一份"这种语义同型的请求
allowed-tools:
  - desktop.read_recording
  - text_editor
---

# 周报生成方法论

## 步骤 1: 收集素材
...

## 步骤 2: 三段式整理
...
```

- `when_to_use`: trigger_conditions list 用 YAML literal block scalar（`|`）保留多条形态
- `allowed-tools`: required_tools list 直接渲染为 YAML list
- frontmatter 后跟 `# {name}` 一级标题 + body Markdown

**Rationale**:
- 对齐 [Anthropic Agent Skills 开放规范](https://agentskills.io) SKILL.md 形态，便于未来 FR-042/043 导出导入对接
- frontmatter 字段名采用规范约定（`name` / `description` / `when_to_use` / `allowed-tools`），与本 spec 内部字段名对齐
- 内部 list / 外部 frontmatter list scalar，转换发生在工具 handler 层

**Alternatives Considered**:
- ❌ JSON form：不对齐规范，LLM 友好度差
- ❌ 拼成纯 Markdown 无 frontmatter：丢失结构化字段语义

## D6: `/skills` 路由 Redirect 策略

**Decision**: 前端路由层处理，不在 backend：
- `routes.tsx` 内识别旧 URL 模式（`/skills`、`/skills?category=*`）并通过 `useEffect` + `replaceState` 切到新路径
- 新路径方案：保留 `/skills` 词位给方法论（不引入 `/tools`），用 route id `skills` 指向新 `SkillMethodologyScreen`，原 Tool 三屏改用 route id `tools` / `tool-teaching` / `tool-compositions`
- 等价路由表（用户视角）：
  | 旧 URL | 新 URL | 含义 |
  |--------|--------|------|
  | `/skills` | `/skills` | 现在指方法论列表 |
  | `/skills?category=pending` | `/tools?status=pending` | Tool 三屏（pending） |
  | `/skill-teaching` | `/tool-teaching` | Tool Teaching 屏 |
  | `/skill-compositions` | `/tool-compositions` | Tool Composition 屏 |

**Rationale**:
- 前端处理 redirect 与现有 `routes.tsx` 设计一致
- 用 route id 区分而非目录重命名，最小化 PR diff（避免 100+ import path 改动）

**Alternatives Considered**:
- ❌ Backend 在 desktop API 层做 redirect：本应用是 SPA，路由都在前端，backend 不参与
- ❌ 物理删除 `screens/skills/` 目录重新命名 `screens/tools/`：diff 噪音巨大，PR 评审难

## D7: `skills_referenced` 元数据嵌入位置（与 010 同构）

**Decision**: 复用 010 已有的 `reply_to_user` 工具 schema 扩展：
- assistant_tools.py 内 `REPLY_TO_USER_SCHEMA` 新增 `skills_referenced: list[str]` 字段（与既有 `memory_entries_referenced` 并列）
- `reply_to_user` handler 在调用 `BrainRepository.batch_update_referenced_counts`（memory_entries）的同时，调用 `SkillReferenceCounterService.batch_increment(skills_referenced)`

- 字段缺失或格式错误 → 静默跳过本轮（不报错不重试，与 `memory_entries_referenced` 同模式）
- supersede 链根归一化：`SkillReferenceCounterService` 内部对每个传入 skill_id 调 `SkillRepository.resolve_chain_root` 归一化后 +1；同一轮内多条引用归一化指向同一 chain root 仍按 1 次计

**Rationale**:
- 与 010 `memory_entries_referenced` 同构契约——同样的失败静默策略、批量 +1 模式、相同的测试守卫风格
- 用户已熟悉这种契约，开发者维护成本低

**Alternatives Considered**:
- ❌ 引入独立的 `report_skill_used` 工具：违背 FR-041 "不引入独立的上报工具"
- ❌ 走后台 worker 异步聚合：违背 FR-041 "不走后台 worker 异步聚合"
- ❌ "装备即引用"兜底：违背 FR-041 "不做装备即引用的兜底"

## D8: Tool 改名最小 diff 边界

**Decision**: 保留所有 Python 代码内的 `skills_*` 词不变（API path、router 文件名、Repository 类名、变量名都保留），只改下列三处面向用户的：
1. **前端导航文案**：`routes.tsx` 内 `label` / `shortLabel` 改 "Tool" 系列
2. **前端屏内文案**：`SkillListScreen.tsx` / `TeachingScreen.tsx` / `CompositionListScreen.tsx` 标题 / 按钮 / 空态 / 提示改 "Tool" 系列
3. **对外 UI 事件名**：`skills.changed` → `tools.changed`（UI Event Registry + emit 调用点）；blinker `skills_changed` → `tools_changed`

**理由细节**:
- 物理目录 `frontend/src/screens/skills/` 不重命名 → 避免上百个 import path 改动
- API path `/api/skills/...` 不重命名 → backward compat、避免 backend / frontend 联动改
- Python 类名 `SkillsService` 不重命名 → 内部代码 vocabulary
- 新增的方法论资产用全新命名空间 `/api/skills/methodology/...` + `SkillService`（无 's'，与现有 `SkillsService` 区分）+ 前端 `SkillMethodologyScreen`

**Rationale**:
- "面向用户的"和"面向开发者的"两套 vocabulary 解耦——用户看到的就是 Tool/Skill，开发者代码里仍用现有 Identifier 减少 diff
- 与 PR 风险控制对齐："文案改名 + 事件改名"是低风险高价值的清理，配合 P1 独立交付节奏

**Alternatives Considered**:
- ❌ 全面物理重命名（目录 / 文件 / 类名 / API path）：PR diff 巨大，评审难，与 CC-005 "现有工具技能业务行为不得回归" 冲突风险高
- ❌ 仅改文案不改事件名：FR-003 明确要求 `skills.* → tools.*` 整体改名

## D9: Bootstrap 时机与"如何创建方法论"装备关系初始化

**Decision**:
- Migration v12 末尾步骤：
  1. 调 `SkillBootstrapService.load_seed_or_fallback()` 拿到 body 文本（fail-open）
  2. 用直接 SQL INSERT 把"如何创建方法论"作为 `origin = system_bootstrap` 的第一条 active skill 写入 `brain_skills`（version=1，无 parent_skill_id）
  3. 同时 INSERT 一条装备关系到 `brain_skill_equipment`：`(equipped_entity = 'assistant'，skill_id = 上述 id，status = 'active'，equipped_at = now，equipped_order = 0)`
  4. **不**装备给任何 specialist（即使迁移时已有 specialist 存在，亦遵循 FR-014a 例外规则跳过）
- 应用启动时再次检查（`SkillBootstrapService.ensure_bootstrap_skill()`）：
  - 如果链根 origin = `system_bootstrap` 的链上当前 active 版本仍为 fallback 文本（与 `_FALLBACK_BODY` 常量字符串相等），且 seed 文件本次启动可读 → 自动 supersede 用真实 seed 内容覆盖（origin = `system_bootstrap`，因为来源仍是 seed）；这是 FR-027b 的"修复后自动覆盖"路径
  - 如果链上当前 active 版本已是 user_edit 接力出的 v2+（即 parent_skill_id IS NOT NULL 链上存在 origin = `user_edit` 节点）→ **不**自动覆盖，尊重用户修订（FR-027b 明确约束）
- Fallback 路径触发 UI toast 通过 `skill.changed` 事件 + 特殊 payload key `bootstrap_fallback_used = true` 通知前端，前端展示 non-blocking toast

**Rationale**:
- Migration 内一次性写入比应用启动时延迟写入更稳定
- 自动 supersede 覆盖只在"尚未被用户修订"的窄场景生效，符合 FR-027b "尊重用户修订"

**Alternatives Considered**:
- ❌ 应用每次启动时强制覆盖：会破坏用户对内置方法论的修订
- ❌ 永不自动覆盖（仅靠用户手动编辑）：开发者修复 seed 后没有自愈路径

## D10: 并发 Supersede 接力的事务隔离

**Decision**: SQLite 事务级别使用默认 `DEFERRED`，但 supersede 路径开启 `BEGIN IMMEDIATE`（写锁前置），保证两个并发 supersede 流程不会同时获取写锁；后到者在写锁等待期间读到 first-writer 已提交的新 active 版本，自动以新 active 作为基线接力（FR-011a first-writer-wins）

实施细节：
- `SkillService.supersede(target_skill_id, new_payload)` 包成单事务：
  1. `BEGIN IMMEDIATE`（拿写锁）
  2. 重新读 `target_skill_id` 当前 active 链根 + 当前 active 版本
  3. 如果 active 版本与传入 `target_skill_id` 不同（说明 first-writer 已抢先 supersede）→ 把 `target_skill_id` 替换为新 active 版本作为新 base
  4. 旧 active → superseded（更新 status）
  5. 插入新 active（parent_skill_id = 上一步旧 active id）
  6. 装备关系切换（旧 active 上所有 status=active 行标 unequipped + reason='supersede_transfer'；新 active 插入对应 status=active 行）
  7. 继承计数（loaded_count / referenced_count / last_referenced_at）
  8. `COMMIT`
- 任何步骤异常 → 整事务回滚，调用方收到错误 → 可重试

**Rationale**:
- SQLite 单写者模型 + IMMEDIATE 锁保证 first-writer-wins 自然成立
- 单事务保证 "supersede + 装备关系切换" 原子性

**Alternatives Considered**:
- ❌ 乐观锁 + 版本号 CAS：SQLite 单写者下退化为悲观锁，无收益
- ❌ 分多个事务（先 supersede skill 再切装备关系）：违背 FR-011 "在同一事务里"
